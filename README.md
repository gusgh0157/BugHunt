# BugHunt — C++ 버그 추적 실습

버그가 **일부러 심어진** 작은 게임 코드 모음입니다.

- **1부: 호출 스택 입문 (랩 1~8)**: 프로그램이 죽은 순간 **호출 스택**을 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 심화 (랩 9~20)**: 메모리 오류, 미초기화, 레이스 등 증상이 덜 친절한 버그들. 데이터 중단점, ASan 같은 도구를 씁니다.
- **3부: 흐름 추적 (랩 21~28)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 디버거가 알아서 멈춰 주지 않으므로, 직접 중단점을 걸고 처음부터 한 줄씩 따라갑니다.
- **4부: 컨테이너 (랩 29~35)**: 표준 컨테이너와 알고리즘이 "규칙대로" 움직였는데 기대와 다른 경우. 연산 전후의 컨테이너를 펼쳐 비교합니다.
- **5부: 포인터 오용 (랩 36~42)**: 같은 포인터 버그가 Debug, Release, ASan에서 각각 어떻게 다르게 보이는지 비교하며 추적합니다. 람다 캡처의 수명도 다룹니다.
- **6부: 멈춤 (랩 43~47)**: 크래시도 오답도 없이 프로그램이 **굳는** 무한루프와 데드락. 모두 중단, 스레드 창, 병렬 스택으로 멈춘 곳을 찾습니다.
- **7부: 성능 (랩 48~53)**: 결과는 맞는데 **느린** 코드. 디버거 대신 **프로파일러**로 시간을 쓰는 곳을 찾습니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1·2부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 3·4부는 **직접 멈춘 곳에서부터 값을 확인하며**, 5부는 **세 구성에서 실행해 증상을 비교하며**, 6부는 **굳은 순간 모두 중단으로 멈춰 세운 곳에서부터**, 7부는 **프로파일러의 핫 경로에서부터** 추적하세요. 다 고쳤으면 `grade.bat`으로 채점합니다.
>
> 각 부가 어떤 버그 종류를 다루고 무엇이 빠져 있는지는 아래 [다루는 버그 한눈에 보기](#다루는-버그-한눈에-보기)에 있습니다.

# 1부: 호출 스택 입문

## 호출 스택이 뭔가요?

함수가 함수를 부르면, 컴퓨터는 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.

```
printPlayer        ← 맨 위: 지금 실행 중인 함수 (여기서 죽었다)
showProfile        ← printPlayer를 부른 함수
openFriendList     ← showProfile을 부른 함수
cs01_profile
main               ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

## 호출 스택 창 사용법

| 하고 싶은 것 | 방법 |
|---|---|
| 호출 스택 창 열기 | 디버깅 중 **Ctrl+Alt+C** (또는 메뉴 디버그 → 창 → 호출 스택) |
| 지역 변수 창 열기 | **Alt+4** (디버그 → 창 → 지역) |
| 다른 프레임으로 이동 | 호출 스택 창에서 줄을 **더블클릭** → 코드 창이 그 함수의 "호출한 줄"로 이동하고, 지역 창이 **그 함수의 변수**로 바뀜 |
| 숨겨진 STL/시스템 함수 보기 | 호출 스택 창 우클릭 → **외부 코드 표시** |

호출 스택 창의 한 줄은 이렇게 생겼습니다.

```
BugHunt.exe!lab1::showProfile(const std::string & name) 줄 40
└ 모듈 ┘  └ 네임스페이스::함수 ┘ └── 매개변수 ──┘     └ 소스 줄 ┘
```

- **노란 화살표**: 지금 멈춘 곳 (맨 위 프레임)
- **초록 화살표**: 다른 프레임을 더블클릭했을 때, "여기서 위 함수를 불렀다"는 위치
- **[외부 코드]**: STL, Windows 등 내 코드가 아닌 부분. 대부분 건너뛰고 **내 코드가 처음 나오는 줄**부터 보면 됩니다.

## 디버거가 멈추는 세 가지 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| "예외가 발생함: 읽기 액세스 위반" 같은 팝업 | 잘못된 포인터 등. 그 줄에서 바로 멈춤 | 호출 스택 창 열기 |
| **Debug Assertion Failed!** 창 | STL 등이 "이건 잘못됐어"라고 검사에 걸림 | **다시 시도(Retry)** 클릭 → (중단점 메시지가 나오면 "중단") → 호출 스택 창 열기 |
| "처리되지 않은 예외" / abort() | `throw`된 예외를 아무도 안 잡음 | 디버거가 throw 지점에서 멈춤 → 호출 스택 창 |

## 추적 4단계 (모든 랩 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 그 프레임의 지역 창에서 이상한 값(nullptr, 0, 엄청 큰 수, 음수...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다. 호출 스택은 "잘못한 곳"으로 거슬러 올라가는 길입니다.

각 랩을 풀 때 아래 기록표를 채워 보세요.

```
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

## 힌트 보는 법

힌트는 각 랩 소스 파일 **맨 아래**에 `#pragma region`으로 접혀 있습니다.

# 3부: 흐름 추적 (크래시 없음)

1·2부에서는 프로그램이 죽어 주었습니다. 디버거가 "여기야"라고 멈춰 주니 호출 스택을 거슬러 올라가기만 하면 됐죠.
실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **숫자 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 3부는 반드시 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되어 사용할 수 없음"으로 보입니다.

## 흐름 추적 4단계 (3부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `streak`는 2여야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다. 기대가 없으면 틀린 값을 봐도 지나친다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** 프로그램 맨 처음이 아니라, [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** F10으로 넘기며 값을 확인한다. 달라진 줄이 함수 호출이면 그 함수 안으로(F11) 들어가 같은 일을 반복한다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤에 나오는 틀린 값들은 대부분 그 결과일 뿐이다.

```
기록표 (3부용)
틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

# 5부: 포인터 오용

2부에서 nullptr, vector 참조 무효화, string_view 댕글링, erase 뒤의 이터레이터, 이중 해제, 가상 소멸자, 구조체 버퍼 넘침을 다뤘습니다. 5부는 그 밖의 포인터 실수입니다.
5부의 핵심은 **같은 버그가 빌드 구성마다 다르게 보인다**는 것입니다. 각 랩을 **Debug → Release → ASan** 순서로 실행해 보고 무엇이 달라지는지 비교하세요. (구성은 도구 모음의 구성 목록에서 바꾸거나 `build.bat Release`처럼 빌드합니다.)

## 구성마다 다르게 보이는 이유

| 구성 | 메모리에 하는 일 | 그래서 포인터 버그는 |
|---|---|---|
| Debug | `/RTC1`이 지역 변수 자리를 `0xCC`로, 디버그 힙이 새 메모리를 `0xCD`, 해제한 메모리를 `0xDD`, 블록 앞뒤 경계를 `0xFD`로 채운다. `delete`할 때 힙 검사도 한다 | 쓰레기 값이 **알아볼 수 있는 쓰레기**(매직 넘버)가 된다. 힙을 망가뜨리면 그 자리에서 어설션 |
| Release | 아무것도 채우지 않는다. 최적화로 변수 위치도 바뀐다 | 해제된 메모리에 옛 값이 그대로 남아 **우연히 맞게** 동작하기도 하고, 한참 뒤 엉뚱한 곳에서 죽기도 한다 |
| ASan | 할당마다 앞뒤에 "레드존"을 두고, 해제한 메모리를 한동안 격리한다 | 잘못 읽고 쓰는 **바로 그 줄**에서 멈추고, 읽은 곳/해제한 곳/할당한 곳의 호출 스택까지 보여 준다. 다만 기본 설정으로는 지역 변수 주소 반환, 초기화 안 된 값, 메모리 누수(Windows에는 누수 검사기가 없음)는 못 잡는다 |

## 람다 캡처와 ASan (랩 42)

`[&]` 람다는 지역 변수의 **주소**를 들고 있습니다. 람다를 타이머나 콜백 목록에 맡기고 함수가 끝나면, 그 주소는 이미 끝난 함수의 스택입니다. 힙과 달리 스택은 "해제"라는 사건이 없고, 다음 함수 호출이 같은 자리를 바로 다시 씁니다.

| 구성 | 버그 상태로 실행한 결과 (이 저장소에서 확인) |
|---|---|
| Debug | Kael만 틀린다(45). 람다가 읽은 `bonus` 자리에 나중에 분노를 쓴 Doran의 `bonus`(45)가 들어 있다. Doran은 우연히 맞는다 |
| Release | 둘 다 틀리고 값이 Debug와 다르다. 최적화로 스택 배치가 바뀌기 때문 |
| ASan | 둘 다 쓰레기 값으로 틀리지만 **리포트가 없다** |

- ASan이 못 잡는 이유: 기본 ASan은 함수가 끝난 뒤의 스택 자리를 "죽은 메모리"로 표시하지 않습니다. 이런 버그(stack-use-after-return)를 잡으려면 스택 프레임을 따로 떼어 두는 옵션이 필요합니다. MSVC에서는 `/fsanitize-address-use-after-return`(프로젝트 속성 → C/C++ → 명령줄 → 추가 옵션)이고, 리포트는 `stack-buffer-underflow`라는 이름으로 나옵니다.
- **이 저장소에서는 그 옵션을 켜지 않았습니다.** MSVC 14.51에서 프로젝트 전체에 켜 보면 프로그램 시작 시 전역 `std::string` 초기화에서 오탐이 나서 랩까지 가지 못했고, 이 파일에만 켜면 다른 파일과 공유하는 표준 라이브러리 코드에서 오탐이 났습니다(Debug, Release 런타임 모두). 같은 버그를 담은 작은 단독 프로그램에서는 잘 잡혔습니다. 궁금하면 랩 42의 핵심만 떼어 새 콘솔 프로젝트로 시험해 보세요.
- 그래서 이 랩의 주 도구는 디버거입니다. 람다 안에 중단점을 걸면 지역 창에서 람다를 펼쳐 캡처한 것들을 볼 수 있고, 참조로 캡처한 변수의 주소가 **이미 끝난 함수의 스택**을 가리키는지 확인할 수 있습니다.

# 6부: 멈춤 - 무한루프와 데드락

크래시도 없고 틀린 결과도 나오지 않습니다. 프로그램이 그냥 **굳습니다**. 디버거는 알아서 멈춰 주지 않고, 중단점을 어디에 걸어야 할지도 모릅니다.
이때는 굳은 프로그램을 **그 순간 통째로 멈춰 세우고**(모두 중단), 각 스레드가 어디에 있는지 봅니다.

> **안전장치:** 6부 랩은 "랩 작업 스레드"에서 돌고, 메인 스레드가 2초 감시 타이머를 잽니다. 시간을 넘기면 `[FAIL] ... 응답 없음 (2000 ms 초과)`를 출력하고 끝납니다(`labs.h`의 `runWithWatchdog`).

# 7부: 성능 - 틀리지 않지만 느리다

결과는 모두 맞습니다. 그런데 **느립니다.** 디버거로 한 줄씩 따라가면 모든 줄이 멀쩡해 보입니다. 이때는 "어느 줄이 틀렸나"가 아니라 **"시간을 어디에 쓰나"**를 묻는 도구, **프로파일러**를 씁니다.

> **판정은 시간이 아니라 횟수로 합니다.** PC마다 속도가 달라서 "100 ms 이하" 같은 기준은 믿을 수 없기 때문입니다. 각 랩은 원소 이동, 복사, 할당 바이트, flush 같은 **일의 양**을 세어 판정하고, 시간은 참고로만 출력합니다. 그래서 7부는 Debug, Release, ASan **어느 구성으로 채점해도 결과가 같습니다.**
> **프로파일링은 Release로 하세요.** Debug는 최적화가 꺼져 있고 검사 코드가 많아서 엉뚱한 곳이 느려 보입니다. 이 저장소에서 잰 예로, 캐시를 거스르는 순회는 Release에서 수십 배 느렸지만 Debug에서는 2배도 안 됐습니다. 반대로 Debug에서만 크게 보이는 비용(반복자 검사, 인라인 안 된 작은 함수)도 있습니다.

## 프로파일러 사용법

| 도구 | 하는 법 | 무엇을 보나 |
|---|---|---|
| 성능 프로파일러 | 구성을 **Release**로 → 디버그 → 성능 프로파일러 (**Alt+F2**) → **CPU 사용량** 체크 → 시작 | 디버거 없이 실행해 함수별 CPU 시간을 모은다. 가장 정확 |
| 핫 경로 | 보고서의 "상위 함수"/"핫 경로", 불꽃 아이콘이 붙은 줄을 따라 펼친다 | 시간이 가장 많이 흐르는 호출 경로. 맨 아래가 실제로 일하는 함수 |
| 총 CPU / 자체 CPU | 보고서의 두 열 | 총(Total) = 그 함수와 그 함수가 부른 것 전부, 자체(Self) = 그 함수 몸통만. 자체가 큰 함수가 범인, 총이 큰 내 함수가 범인을 부른 곳 |
| 호출자/호출 수신자 | 함수를 더블클릭 | 그 함수를 누가 불렀고 그 함수가 누구를 불렀는지, 소스 줄별 시간 |
| 진단 도구 창 | F5로 실행하면 자동으로 열림 (**Ctrl+Alt+F2**) → CPU 사용량 탭 → **CPU 프로필 기록** | 디버깅하면서 중단점 두 개 사이 구간만 프로파일링. Debug에서도 쓸 수 있지만 위 주의 참고 |
| 크기를 두 배로 | 랩의 개수 상수를 두 배로 바꿔 실행 | 시간이나 횟수가 2배면 O(n), 4배면 O(n²). 어느 쪽인지가 첫 단서 |

## 따라 해 보기: 랩 48 (채팅 큐)

1. `48`로 실행합니다. `메시지 8000개 처리: ... ms, 원소 이동 31996000번`과 `[FAIL]`이 나옵니다. 메시지는 8000개인데 이동은 3천만 번입니다.
2. `pf01_chat_queue.cpp`의 `kMessages`를 16000으로 바꿔 다시 실행해 봅니다. 이동 횟수는 약 4배가 됩니다. → *O(n²)*. 확인했으면 8000으로 되돌립니다.
3. 구성을 **Release**로 바꾸고, 명령 인수가 `48`인지 확인한 뒤 **Alt+F2** → CPU 사용량 → 시작. 랩이 끝나면 보고서가 열립니다.
4. 핫 경로를 펼칩니다. `perf1::ChatQueue::drain` 아래에 `vector::erase`, 그 아래 `Message`의 이동 대입(또는 `memmove`)이 대부분의 시간을 차지합니다. (Release는 작은 함수를 인라인하므로 `drain` 자체의 "자체 CPU"가 크게 나올 수도 있습니다.) → *핫 경로 맨 아래 함수*
5. `drain`을 더블클릭하면 소스 줄별 시간이 보입니다. `queue_.erase(queue_.begin());` 줄이 거의 전부입니다. → *그 함수를 부른 줄*
6. vector의 맨 앞을 지우면 뒤의 원소가 전부 한 칸씩 당겨집니다. 남은 원소가 n개면 n번 이동하고, 이걸 n번 반복합니다.
7. 고친 뒤 다시 Alt+F2로 프로파일링해서 핫 경로가 어떻게 바뀌었는지 보고, Debug에서 `[PASS]`를 확인합니다.

# 채점

다 고쳤다고 생각되면 채점기로 확인하세요. 저장소 폴더에서 실행합니다.

```bash
grade.bat
```

- `grade.bat` = `grade.bat Debug`: Debug로 빌드한 뒤 랩 53개를 모두 채점합니다. `grade.bat Release`, `grade.bat ASan`도 됩니다.
- `grade.bat Debug 37`: 랩 37만 채점합니다.
- 이미 빌드했다면 `bin\Debug\BugHunt.exe --grade` (또는 `--grade 37`)로 바로 실행해도 됩니다.

```
   #  부  결과       시간  랩
   1  1부  CRASH       16 ms  친구 프로필
                              └ 액세스 위반 (0xC0000005)
  21  3부  PASS        31 ms  출석 보상
  43  6부  TIMEOUT   2020 ms  스킬 쿨다운
                              └ [FAIL] 쿨다운 계산  응답 없음 (2000 ms 초과)
...
총점: 23/53
결과 파일: grade-report.json
```

## 판정 방법

- 랩마다 `BugHunt.exe`를 **자식 프로세스로 따로** 띄웁니다(`--grade-child N`). 한 랩이 죽거나 멈춰도 다른 랩과 채점기는 영향을 받지 않습니다. 채점 중에는 어설션 창이나 "응답 없음" 창이 뜨지 않고 바로 종료됩니다.
- 판정은 자식 프로세스의 **종료 코드와 시간**으로만 합니다.

| 결과 | 조건 |
|---|---|
| PASS | 종료 코드 0 (모든 검사가 `[PASS]`). 숨은 케이스가 있으면 그것도 0 |
| FAIL | 종료 코드 10 (`[FAIL]`이 하나 이상) |
| TIMEOUT | 종료 코드 11 (6부 감시 타이머 2초 초과), 또는 채점기의 랩당 제한 15초 초과 |
| CRASH | 그 밖의 종료 코드. 액세스 위반 `0xC0000005`, 스택 오버플로 `0xC00000FD`, Debug 어설션 `0xC0000420`, 힙 손상 `0xC0000374`, `abort()` 3, ASan 오류 1 등 |

- **숨은 케이스:** 3~7부 랩은 평소 실행이 통과하면 **화면에 나오지 않는 다른 데이터로 한 번 더** 실행합니다(`--grade-child N --hidden`). 결과를 하드코딩해서 `[PASS]`를 만들거나, 보이는 데이터에서만 맞는 반쪽짜리 수정(예: 랩 43을 `t < cooldownSeconds`로만 고치기)은 여기서 걸립니다. 숨은 테스트는 각 랩 파일 맨 아래 `채점용 숨은 테스트` region에 있습니다. 소스라서 열어 볼 수는 있지만 풀이에는 필요 없고, 고치면 채점이 의미가 없어집니다. 1·2부는 크래시 자체가 증상이라 숨은 케이스가 없습니다.
- 채점은 **Debug 기준**으로 만들었습니다. 버그 상태 그대로 채점하면 Debug와 ASan은 0/53이지만, Release는 몇 랩이 우연히 PASS로 나옵니다(이 저장소에서 확인했을 때 랩 2, 8, 11, 16, 31, 37, 40. 범위 검사와 비교자 검사가 없고, 누수 측정은 Debug에서만 하고, 해제된 메모리에 옛 값이 남아 있기 때문. 랩 2, 40은 실행마다 달라질 수 있음). 7부는 횟수로 판정하므로 구성과 상관없이 FAIL입니다. 정답을 모두 적용하면 세 구성 모두 53/53입니다.
- 채점기 자체의 종료 코드는 만점이면 0, 아니면 1입니다.

## grade-report.json 형식 (BugHunt 네 판 공통)

채점 결과는 기계가 읽을 수 있는 `grade-report.json`으로도 저장됩니다(UTF-8, 채점기를 실행한 폴더, `.gitignore`에 포함). C#, 언리얼, 유니티판도 같은 형식을 씁니다.

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 53,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "CRASH", "ms": 16, "detail": "액세스 위반 (0xC0000005)" },
    { "id": 21, "title": "출석 보상", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| 필드 | 타입 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 어느 판의 결과인지. 이 저장소는 `"cpp"` |
| `version` | 정수 | 이 JSON 형식의 버전. 지금은 `1`. 필드의 뜻이 바뀌면 올린다 |
| `total` | 정수 | 채점한 랩 수(= `labs` 길이). 랩 하나만 채점하면 1 |
| `passed` | 정수 | `result`가 `"PASS"`인 랩 수 |
| `labs[].id` | 정수 | 랩 번호(메뉴 번호) |
| `labs[].title` | 문자열 | 랩 이름 |
| `labs[].part` | 정수 | 부 번호 |
| `labs[].result` | 문자열 | `"PASS"`, `"FAIL"`, `"TIMEOUT"`, `"CRASH"` 중 하나 |
| `labs[].ms` | 정수 | 걸린 시간(밀리초). 숨은 케이스 실행 시간 포함 |
| `labs[].detail` | 문자열 | 실패 이유 한 줄(첫 `[FAIL]` 줄, 크래시 종류와 단서 등). PASS면 빈 문자열. 숨은 케이스에서 실패하면 `"숨은 케이스: "`로 시작 |
