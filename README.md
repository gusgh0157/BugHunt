# BugHunt — C++ 버그 추적 실습 / C++ バグ追跡ラボ

한국어 또는 日本語를 펼쳐 읽으세요. / 韓国語または日本語を開いてお読みください。

<details>
<summary><b>한국어</b></summary>

버그가 **일부러 심어진** 작은 게임 코드 모음입니다.

- **1부: 호출 스택 입문 (랩 1~8)**: 프로그램이 죽은 순간 **호출 스택**을 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 심화 (랩 9~20)**: 메모리 오류, 미초기화, 레이스 등 증상이 덜 친절한 버그들. 데이터 중단점, ASan 같은 도구를 씁니다.
- **3부: 흐름 추적 (랩 21~32)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 디버거가 알아서 멈춰 주지 않으므로, 직접 중단점을 걸고 처음부터 한 줄씩 따라갑니다.
  - **연산자 실수 (랩 29~32)**: 후위 증가의 값, 매크로 인자의 두 번 평가, `&&` 자리의 `&`, `||` 자리의 `|`. 3부 끝에 붙는 랩입니다.
- **4부: 컨테이너 (랩 33~39)**: 표준 컨테이너와 알고리즘이 "규칙대로" 움직였는데 기대와 다른 경우. 연산 전후의 컨테이너를 펼쳐 비교합니다.
- **5부: C++ 언어 함정 (랩 40~48)**: `const`에 `std::move`, 부호 있는 정수 오버플로, 축소 변환, 부호 있는/없는 변환, 전역 초기화 순서, 헤더의 `static`, 예외 경로 누수, 소멸자에서 던지기, 범위 for. 컴파일러가 받아들이는 코드에 숨은 언어 규칙을 조사식과 경고로 찾습니다.
- **6부: 인터페이스와 상속 (랩 49~54)**: 재정의가 안 된 가상 함수, 슬라이싱, 생성자 안의 가상 호출, 기본 인자, 오버로드 숨김, `dynamic_cast`. "엉뚱한 함수가 불리는" 버그를 Step Into와 실제 형식 보기로 추적합니다.
- **7부: 파일 입출력 (랩 55~61)**: 작업 디렉터리, 버퍼와 flush, `eof()` 반복, `getline`, failbit, BOM, 반쯤 쓴 세이브. 스트림 상태와 디스크의 실제 바이트를 함께 봅니다.
- **8부: 직렬화 JSON/XML (랩 62~68)**: nlohmann/json과 pugixml을 쓰는 저장·불러오기 코드의 함정. `third_party/`에 고정 버전으로 들어 있습니다.
- **9부: 포인터 오용 (랩 69~80)**: 해제 후 사용, 초기화 안 된 포인터, `new[]`/`delete` 짝 틀림 같은 정의되지 않은 동작. 메모리 검사기와 ASan의 보고를 읽고 원인까지 거슬러 올라갑니다. 람다 캡처의 수명과 스택/힙 오버플로(랩 76~80)도 다룹니다.
- **10부: 비동기와 동시성 (랩 81~87)**: `std::async`와 `future`, `condition_variable`, `atomic`, 스레드 수명, 코루틴. 버그가 매번 똑같이 재현되도록 순서를 고정해 두었습니다. 스레드 목록, 모든 스레드의 호출 스택, 조건부 중단점으로 "어느 스레드가 언제"를 추적합니다.
- **11부: 멈춤 (랩 88~92)**: 크래시도 오답도 없이 프로그램이 **굳는** 무한루프와 데드락. 모두 중단(break all), 스레드 목록, 모든 스레드의 호출 스택으로 멈춘 곳을 찾습니다.
- **12부: 성능 (랩 93~98)**: 결과는 맞는데 **느린** 코드. 디버거 대신 **프로파일러**로 시간을 쓰는 곳을 찾습니다.
- **챌린지 (C-1~C-3, B-1~B-8)**: 다 끝낸 사람을 위한 힌트 없는 문제. 여러 단계를 거슬러 올라가는 깊은 추적과, 증상 한 줄만 주는 블라인드 문제입니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1·2부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 3~8부는 **직접 멈춘 곳에서부터 값을 확인하며**, 9부는 **검사기의 보고에서부터**, 10부는 **스레드 목록과 모든 스레드의 호출 스택에서부터**, 11부는 **굳은 순간 모두 중단으로 멈춰 세운 곳에서부터**, 12부는 **프로파일러의 핫 경로에서부터** 추적하세요. 다 고쳤으면 `grade.bat`(Windows) 또는 `./grade.sh`로 채점합니다.
>
> 각 부가 어떤 버그 종류를 다루고 무엇이 빠져 있는지는 아래 [다루는 버그 한눈에 보기](#다루는-버그-한눈에-보기)에 있습니다.

**표준 C++판입니다.** 랩 코드는 ISO C++20만 씁니다(컴파일러 확장, `_s` 함수, 컴파일러별 `#ifdef` 없음). MSVC, Clang, GCC 중 어느 것으로 빌드해도 **같은 랩이 같은 이유로 FAIL**하고, 고치면 PASS해야 합니다. 크래시 모양(어떤 신호, 어떤 메시지)은 컴파일러와 운영체제마다 달라도 채점 결과는 같습니다. 콘솔 설정, 자식 프로세스, 감시 타이머처럼 운영체제마다 다른 코드는 `BugHunt/src/platform/` 한곳에 Windows용과 POSIX(Linux, macOS)용으로 나눠 두었습니다.

## 준비

C++20을 지원하는 컴파일러와 CMake 3.21 이상이 필요합니다. 빌드 구성은 `CMakePresets.json`의 세 프리셋입니다.

| 프리셋 | 출력 | 용도 |
|---|---|---|
| `debug` | `bin/Debug/` | 기본. 최적화 없음, 디버그 정보 |
| `release` | `bin/Release/` | 최적화 빌드. 12부 프로파일링, "Debug에선 되는데 Release에선 안 돼요" 체험 |
| `asan` | `bin/ASan/` | Debug + AddressSanitizer |

**명령줄** (Windows는 `build.bat`, 그 밖은 `./build.sh`가 아래를 대신해 줍니다)

```bash
cmake --preset debug
cmake --build --preset debug
```

- Windows: Visual Studio의 "x64 Native Tools 명령 프롬프트"에서 실행하거나 `build.bat Debug`를 쓰세요. `build.bat`은 Visual Studio를 찾아 개발자 환경(MSVC, CMake, Ninja)을 불러옵니다.
- Linux, macOS: `./build.sh Debug`. 컴파일러를 고르려면 `CXX=clang++ ./build.sh Debug`처럼 지정합니다(처음 구성할 때만 적용되므로 바꾸려면 `build/` 폴더를 지우세요).

**IDE**

- **Visual Studio**: "폴더 열기"로 저장소 폴더를 열면 프리셋을 읽어 구성 목록에 Debug, Release, ASan이 생깁니다. 시작 항목을 `BugHunt.exe`로 고르고 실행합니다. 예전처럼 `BugHunt.sln`(또는 `.slnx`)을 열어도 됩니다(Windows 전용 선택 사항).
- **VS Code**: CMake Tools 확장과 디버거 확장(C/C++의 `cppdbg` 또는 CodeLLDB)을 설치하고, 프리셋을 고른 뒤 빌드하고 디버그합니다. 랩 번호는 `launch.json`의 `args`(예: `["1"]`)로 넘깁니다.
- **gdb / lldb**: `gdb --args bin/Debug/BugHunt 1` 또는 `lldb -- bin/Debug/BugHunt 1`로 띄우고 `run`.

**실행**: 메뉴에서 랩 번호를 입력하거나, 인자로 번호를 넘깁니다(`BugHunt 1`, `BugHunt C-1`). 1·2부는 **반드시 디버거를 붙여서** 실행하세요. 디버거 없이 실행하면 프로그램은 죽기만 하고 호출 스택을 볼 수 없습니다.

> 이 저장소에서 직접 빌드하고 채점해 본 컴파일러는 Windows의 **MSVC 14.51**과 **Clang 22**(Visual Studio에 들어 있는 것, MSVC 표준 라이브러리 사용)입니다. GCC, libstdc++, libc++, Linux/macOS에서는 아직 확인하지 못했습니다.

# 1부: 호출 스택 입문

## 호출 스택이 뭔가요?

함수가 함수를 부르면, 컴퓨터는 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.

```
printPlayer        ← 맨 위: 지금 실행 중인 함수 (여기서 죽었다)
showProfile        ← printPlayer를 부른 함수
openFriendList     ← showProfile을 부른 함수
cs01_profile
main               ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

## 호출 스택 보는 법

| 하고 싶은 것 | 방법 (도구별 키는 [디버거 대응표](#디버거-대응표)) |
|---|---|
| 호출 스택 보기 | 디버거가 멈추면 호출 스택 창(패널)을 연다. gdb·lldb는 `bt` |
| 지역 변수 보기 | 지역 변수 창(패널). gdb는 `info locals`, lldb는 `frame variable` |
| 다른 프레임으로 이동 | 호출 스택에서 줄을 고른다 → 코드 창이 그 함수의 "호출한 줄"로 이동하고, 지역 변수가 **그 함수의 변수**로 바뀜 |
| 표준 라이브러리, 시스템 함수 | 내 코드가 아닌 프레임. 도구에 따라 접어서 보여 준다(Visual Studio의 `[외부 코드]`) |

호출 스택의 한 줄은 도구마다 모양이 조금 다르지만 담긴 정보는 같습니다.

```
Visual Studio:  BugHunt.exe!lab1::showProfile(const std::string & name) 줄 40
gdb / lldb:     #1  lab1::showProfile (name="Dorna") at cs01_profile.cpp:40
                    └ 네임스페이스::함수 ┘ └ 매개변수 ┘    └ 소스 파일:줄 ┘
```

- **현재 줄**: 지금 멈춘 곳 (맨 위 프레임). Visual Studio는 노란 화살표, gdb는 `=>`
- **호출한 줄**: 다른 프레임을 골랐을 때 "여기서 위 함수를 불렀다"는 위치. Visual Studio는 초록 화살표
- 표준 라이브러리나 운영체제 프레임은 대부분 건너뛰고 **내 코드가 처음 나오는 줄**부터 보면 됩니다.

## 디버거가 멈추는 세 가지 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| 잘못된 메모리 접근 (Windows: "액세스 위반", Linux/macOS: `SIGSEGV`) | 잘못된 포인터 등. 그 줄에서 바로 멈춤 | 호출 스택 보기 |
| 처리되지 않은 예외 (`std::out_of_range` 등) | `throw`된 예외를 아무도 안 잡음. 결국 `std::terminate` → `abort()` | 디버거가 throw 지점이나 `abort`에서 멈춤 → 호출 스택에서 내 코드 찾기. 던지는 순간 멈추게 하려면 "예외가 던져질 때 멈춤"을 켠다 |
| `abort()` + `[CRASH] ...` 메시지 | BugHunt 검사기(메모리 검사, 정렬 검사)나 표준 라이브러리의 디버그 검사가 잘못을 발견함 | 콘솔 메시지를 끝까지 읽고 → 호출 스택에서 내 코드 찾기 |

<details>
<summary>도구별 참고: Visual Studio의 어설션 창</summary>

MSVC Debug 구성의 표준 라이브러리는 범위 밖 `operator[]`, 무효가 된 이터레이터 같은 잘못을 **Debug Assertion Failed!** 창으로 알립니다. **다시 시도(Retry)** → (중단점 메시지가 나오면 "중단") → 호출 스택을 보면 됩니다. GCC의 libstdc++는 `-D_GLIBCXX_ASSERTIONS`, Clang의 libc++는 하드닝 모드로 비슷한 검사를 켤 수 있고, 이 저장소의 CMake는 Debug에서 둘 다 켭니다. BugHunt의 랩은 이런 검사가 **있든 없든 같은 결과**가 나오도록 만들었습니다(1부의 범위 밖 접근은 `at()`을 쓰므로 어느 구성에서나 예외가 나고, 랩 13은 무효가 된 반복자를 직접 잡는 `bughunt::CheckedList`를 씁니다). 예외는 Debug와 Release의 이 차이를 보여 주려고 만든 랩 80입니다.
</details>

## 추적 4단계 (모든 랩 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 그 프레임의 지역 변수에서 이상한 값(nullptr, 0, 엄청 큰 수, 음수...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다. 호출 스택은 "잘못한 곳"으로 거슬러 올라가는 길입니다.

각 랩을 풀 때 아래 기록표를 채워 보세요.

```
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

## 따라 해 보기: 랩 1 (친구 프로필)

1. 인자 `1`로 **디버거를 붙여** 실행합니다.
2. 콘솔에 Kael, Mira 프로필이 나온 다음 디버거가 멈춥니다. Visual Studio는 **"읽기 액세스 위반... player이(가) nullptr였습니다"**, gdb·lldb는 `SIGSEGV`(또는 `EXC_BAD_ACCESS`) 비슷한 메시지를 보여 줍니다.
3. 호출 스택을 엽니다. 맨 위가 `lab1::printPlayer`입니다. → *멈춘 함수*
4. 지역 변수를 봅니다. `player`가 `0x0000000000000000`(nullptr)입니다. → *이상한 값*
5. 호출 스택에서 두 번째 줄 `lab1::showProfile`을 고릅니다. 지역 변수 `name`과 `player`를 봅니다. `player`는 `findPlayer(name)`의 결과였네요. `name`에는 어떤 값이 들어 있나요?

### 빌드 구성과 BugHunt 메모리 검사기

| 구성 | 용도 |
|---|---|
| Debug | 기본. 최적화가 없어 한 줄씩 따라가기 좋다 |
| Release | 최적화 빌드. 정의되지 않은 동작이 Debug와 **다른 모습**으로 나타나는 것을 체험할 때 |
| ASan | AddressSanitizer. 해제 후 사용, 범위 밖 접근, 이중 해제를 **그 줄에서** 잡고 읽은 곳/해제한 곳/할당한 곳의 호출 스택을 보여 준다 |

명령줄 빌드: `build.bat Debug` / `build.bat Release` / `build.bat ASan` (Linux, macOS는 `./build.sh`)

해제된 메모리를 읽거나 초기화하지 않은 값을 쓰는 것은 **정의되지 않은 동작**(undefined behavior)입니다. 표준은 결과를 정하지 않으므로, 아무 일 없이 맞는 값이 나올 수도 있고 컴파일러나 구성을 바꾸면 갑자기 틀릴 수도 있습니다. 그래서 채점 결과가 컴파일러에 따라 흔들리지 않도록, BugHunt는 표준이 허용하는 **전역 `operator new`/`delete` 교체**로 만든 작은 메모리 검사기(`src/support/heap_guard.cpp`)를 Debug와 Release에 넣었습니다. ASan 구성에서는 ASan이 같은 일을 더 정확하게 하므로 검사기를 끕니다.

| 검사기가 하는 일 | 그래서 |
|---|---|
| 새로 할당한 메모리를 `0xA5`로 채운다 | 초기화하지 않은 값을 읽으면 `0xA5A5A5A5`(-1515870811) 같은 **알아볼 수 있는 쓰레기**가 나온다 |
| 해제한 메모리를 `0xEE`로 덮고 한동안 다시 쓰지 않는다 | 해제 후 사용이 **우연히 맞는 값**을 읽지 못한다. `0xEEEEEEEE`(-286331154)가 보이면 해제된 메모리 |
| 블록 바로 뒤 16바이트를 `0xBD`로 채우고 해제할 때 확인한다 | 할당 크기를 넘어 쓰면 `[CRASH] 메모리 검사: ... 버퍼 오버런` |
| 이중 해제, `new[]`/`delete` 짝 틀림, `new`로 받지 않은 주소 해제 | `[CRASH] 메모리 검사: ...` 메시지 후 `abort()` |

이 값들은 BugHunt가 정한 것이라 어느 컴파일러에서나 같습니다. 진짜 프로그램에는 이런 검사기가 없다는 것을 기억하세요. 검사기 없이 같은 버그는 "실행할 때마다, 컴파일러마다 다르게" 보입니다.

<details>
<summary>도구별 참고: MSVC Debug의 <code>/RTC1</code>, CRT 디버그 힙, 매직 넘버</summary>

MSVC의 Debug 구성은 자체적으로 메모리를 채웁니다. Visual Studio에서 BugHunt를 디버깅하다 이 값들을 볼 수도 있습니다(검사기가 덮어쓰기 전, 스택 변수 등).

|---|---|

# 3부: 흐름 추적 (크래시 없음)

1·2부에서는 프로그램이 죽어 주었습니다. 디버거가 "여기야"라고 멈춰 주니 호출 스택을 거슬러 올라가기만 하면 됐죠.
실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **숫자 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 3부는 반드시 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되어 사용할 수 없음"(gdb: `<optimized out>`)으로 보입니다.

## 흐름 추적 4단계 (3부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `streak`는 2여야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다. 기대가 없으면 틀린 값을 봐도 지나친다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** 프로그램 맨 처음이 아니라, [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** 한 줄씩 실행(step over)하며 값을 확인한다. 달라진 줄이 함수 호출이면 그 함수 안으로(step into) 들어가 같은 일을 반복한다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤에 나오는 틀린 값들은 대부분 그 결과일 뿐이다.

```
기록표 (3부용)
틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

## 3부에서 쓰는 도구

도구별 키와 명령은 [디버거 대응표](#디버거-대응표)에 있습니다.

| 동작 | 언제 |
|---|---|
| 중단점 + 한 줄씩 실행(step over) | 기본. 값이 줄마다 어떻게 변하는지 볼 때 |
| 함수 안으로(step into) / 밖으로(step out) | 의심 가는 함수 호출이 있을 때. 밖으로 나오면 디버거가 방금 돌아온 값을 보여 준다(Visual Studio: 자동 창의 `함수명 반환`, gdb: `finish`의 `Value returned`) |
| 커서까지 실행 | 중단점 없이 "여기까지만 가 줘" (Visual Studio: Ctrl+F10, VS Code: Run to Cursor, gdb: `until 40`) |
| 조건부 중단점 (예: `tick == 148`, `c.name == "Selene"`) | 반복이 수백 번인데 그중 한 번만 이상할 때 |
| 적중 횟수 | "다섯 번째 호출에서만 멈춰" |
| 추적점 (logpoint, `dprintf`) | 멈추지 않고 **순서**와 값을 기록할 때. 결과는 디버거 출력에 찍힌다 |
| 조사식에 식 넣기 (`c.isVip()`, `&item`, `a.x - b.x`) | 조건문의 각 부분을 따로 계산해 볼 때, 두 객체가 같은지 주소로 비교할 때 |
| 특정 객체 따라가기 | 주소를 적어 두고 조사식에 `*(Item*)0x...`로 넣는다. Visual Studio는 "개체 ID 만들기"(`$1`)도 있다 |
| 실행 위치 옮기기 (다음 문 설정, `jump`) | 같은 코드를 다시 실행해 보거나 분기를 건너뛰어 가설을 시험할 때 (상태는 되돌아가지 않음에 주의) |

## 연산자 실수 (랩 29~32)

`x++`와 `++x`, `&`와 `&&`, `|`와 `||`는 한 글자 차이라 코드 리뷰에서 눈에 잘 띄지 않고, 컴파일도 경고 없이 됩니다.
결과는 크래시가 아니라 **값이 하나씩 어긋나는 것**이라 3부의 흐름 추적 도구로 잡습니다.
여기서는 특히 "식의 값"과 "변수에 남는 값"이 다른 순간을 보는 연습을 합니다.

- 조사식(watch)에 식을 통째로 넣어 보기: `2 & 1`, `2 && 1`, `guild.lastId++`는 넣지 마세요(조사식도 부작용을 실행합니다)
- 데이터 중단점(값이 바뀌면 멈추는 중단점, watchpoint)으로 한 줄에서 값이 몇 번 바뀌는지 세기
- 함수에서 나온 직후 반환값 보기 (step out 직후 디버거가 보여 주는 반환값. Visual Studio: 자동 창, gdb: `finish`)

> 컴파일러마다 결과가 달라지는 식(`f(i++, i++)`, `i++ + i++`)은 일부러 넣지 않았습니다. 판정이 컴파일러에 따라 달라지면 안 되기 때문입니다. 아래 "미포함"을 보세요.

# 5부: C++ 언어 함정

이 부의 버그는 모두 **컴파일러가 받아들이는 코드**입니다. `std::move`가 복사가 되고, 넘친 정수가 음수가 되고, 소수점이 잘리고, 음수가 아주 큰 양수가 되고, 전역 변수가 0이고, 헤더의 변수가 둘로 갈라지고, 예외가 메모리를 흘리고, 소멸자의 예외가 프로그램을 끄고, 범위 for가 새 원소를 못 봅니다.
문법은 맞지만 언어 규칙을 하나 잘못 알고 있으면 생기는 버그입니다. 그래서 고치는 법보다 **규칙 이름을 아는 것**이 중요합니다. 각 랩의 힌트 2가 그 규칙입니다.

이 부의 공통 도구는 **조사식에 식을 그대로 넣어 계산 단계를 나눠 보기**(`baseExp * multiplier`, `static_cast<std::size_t>(x)`, `&g_saveStats`)와 **경고를 단서로 읽기**입니다.
몇몇 랩은 컴파일러가 이미 경고를 냅니다(42 축소 변환, 47 던지는 소멸자). 경고 목록을 먼저 보는 습관이 가장 싼 디버깅입니다.

> 3부 랩 20(연산자 우선순위)과 3부 끝의 연산자 랩, 2부 랩 3(정수 나눗셈)·14(`unsigned` 언더플로)와 이어집니다. 이 부는 "형식과 수명의 규칙"에 집중합니다.

# 6부: 인터페이스와 상속

가상 함수는 "실제 객체의 형식에 맞는 함수가 불린다"는 약속입니다. 이 약속에는 예외가 여럿 있습니다.
시그니처가 한 글자라도 다르면 재정의가 아니고, 값으로 복사하면 파생 부분이 잘리고, 생성 중인 객체는 아직 파생 형식이 아니고, 기본 인자는 가상으로 고르지 않습니다.
모두 컴파일은 잘 되고, 결과는 "엉뚱한 함수가 불렸다"입니다.

이 부의 공통 도구는 **함수 안으로 들어가기(Step Into)로 실제로 어느 클래스의 함수에 들어가는지 보기**와 **조사식에서 객체의 실제 형식 보기**입니다.
디버거는 다형 객체를 실제 형식(예: `{Boss}`)으로 보여 주고, 가상 함수 표(vtable) 포인터도 펼쳐 볼 수 있습니다.

> 랩 16(가상 소멸자 누락)은 2부에 그대로 둡니다. 이 부는 "불리는 함수가 다르다"에 집중합니다.

## 6부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 함수 안으로 (Step Into) | 가상 호출 줄에서 한 단계 들어가기 | 어느 클래스의 함수가 불리는지 확인 (랩 49, 52) |
| 걸리지 않는 중단점 | 파생 클래스 함수에 중단점 → 안 멈추면 그게 단서 | 재정의가 안 됐거나 객체가 잘렸을 때 (랩 49, 50, 51) |
| 실제 형식 보기 | 조사식이나 지역 변수에서 객체를 펼쳐 형식 이름과 vtable 확인 | 슬라이싱, 생성자 안에서의 형식 (랩 50, 51) |
| 호출 스택에서 위로 | 죽은 곳에서 한 칸씩 올라가 값 비교 | `dynamic_cast` 결과가 nullptr일 때 (랩 54) |
| 컴파일러에게 묻기 | `override`, `explicit`, `= delete`를 붙여 다시 빌드 | 의도를 코드로 적어 실수를 컴파일 오류로 바꾸기 |

## 따라 해 보기: 랩 49 (백스탭)

2. **기대를 적습니다.** 오우거는 등을 보이고 있으니 백스탭은 20 × 3 = 60.

6. `Backstab::damage`에 `override`를 붙이고 빌드합니다. 컴파일러가 "재정의할 함수가 없다"는 오류를 냅니다. `const`를 붙여 고치고 다시 실행해 [PASS]를 확인합니다.

# 7부: 파일 입출력

파일 입출력 버그는 "파일은 멀쩡한데 프로그램이 다르게 읽는" 경우가 대부분입니다. 크래시도 없고 예외도 없습니다.
스트림은 실패해도 조용히 상태 비트만 켜고, 경로는 실행한 위치에 따라 다른 파일을 가리키고, 쓴 내용은 버퍼에 머물러 있습니다.
그래서 이 부에서는 변수 대신 **스트림의 상태**와 **디스크에 실제로 있는 바이트**를 함께 봅니다.

  중단점에서 멈춰 있는 동안에는 파일이 남아 있으니 탐색기나 편집기로 직접 열어 볼 수 있습니다.
- 판정은 운영체제와 컴파일러에 상관없이 같도록 만들었습니다. 그래서 OS마다 결과가 다른 주제(텍스트 모드 줄바꿈 변환 등)는 "미포함"에 이유와 함께 적었습니다.

# 8부: 직렬화 (JSON/XML)

세이브, 설정, 데이터 표는 거의 다 JSON이나 XML입니다. 라이브러리는 대부분 "친절하게" 동작합니다.

그 친절함이 버그를 숨깁니다. 이 부에서는 **라이브러리가 조용히 해 준 일**을 디버거로 드러냅니다.

- 쓰는 라이브러리: nlohmann/json (`json`, `ordered_json`), pugixml (`xml_document`, `xml_node`, `xml_attribute`)

- XML 보안(외부 엔티티/XXE, 엔티티 폭탄)은 랩으로 만들지 않고 해답 참고에만 적었습니다. pugixml은 DTD의 외부 엔티티를 처리하지 않습니다.

# 9부: 포인터 오용

1·2부에서 nullptr, vector 참조 무효화, string_view 댕글링, erase 뒤의 이터레이터, 이중 해제, 가상 소멸자, 구조체 버퍼 넘침을 다뤘습니다. 9부는 그 밖의 포인터 실수입니다.
9부의 버그는 모두 **정의되지 않은 동작**입니다. 수명이 끝난 메모리를 읽고, 초기화하지 않은 포인터를 따라가고, `new[]`로 만든 것을 `delete`로 지웁니다. 표준은 이때 무슨 일이 일어날지 정하지 않으므로, 진짜 프로그램에서는 컴파일러, 최적화, 운영체제, 심지어 실행할 때마다 증상이 달라집니다. "Release에서는 되는데요"는 버그가 없다는 뜻이 아닙니다.

BugHunt는 채점이 흔들리지 않도록 Debug와 Release에 **메모리 검사기**를 넣었습니다([빌드 구성과 BugHunt 메모리 검사기](#빌드-구성과-bughunt-메모리-검사기)). 그래서 9부는 어느 컴파일러, 어느 구성에서나 같은 랩이 같은 이유로 실패합니다. ASan 구성에서는 검사기 대신 ASan이 보고합니다. 두 가지를 모두 실행해 보고 보고 내용을 비교하세요.

| 보고하는 것 | 하는 일 | 그래서 포인터 버그는 |
|---|---|---|
| 메모리 검사기 (Debug, Release) | 새 메모리를 `0xA5`, 해제한 메모리를 `0xEE`, 블록 뒤를 `0xBD`로 채우고, `delete`할 때 짝과 경계를 확인한다 | 쓰레기 값이 **알아볼 수 있는 쓰레기**가 된다. 잘못된 해제는 그 자리에서 `[CRASH] 메모리 검사: ...`. 다만 잘못 **읽는** 순간에는 멈추지 않는다 |

## 람다 캡처와 ASan (랩 75)

`[&]` 람다는 지역 변수의 **주소**를 들고 있습니다. 람다를 타이머나 콜백 목록에 맡기고 함수가 끝나면, 그 주소는 이미 끝난 함수의 스택입니다. 힙과 달리 스택은 "해제"라는 사건이 없고, 다음 함수 호출이 같은 자리를 바로 다시 씁니다.

버그 상태로 실행해 보면 틀린 값이 컴파일러와 구성마다 다릅니다(이 저장소에서 확인한 Kael의 공격력의 예: MSVC Debug -124, MSVC·Clang Release 45, Clang Debug 85, ASan은 수억대 쓰레기 값. Debug의 값은 다시 빌드하면 바뀔 수 있습니다). 스택 자리가 언제 다시 쓰이는지는 최적화와 스택 배치에 달려 있기 때문입니다. Release의 45는 람다가 읽은 `bonus` 자리에 나중에 분노를 쓴 Doran의 `bonus`(45)가 들어 있어서 나온 값입니다. 어느 경우든 기대한 60은 나오지 않습니다.

- ASan이 기본으로 못 잡는 이유: 기본 ASan은 함수가 끝난 뒤의 스택 자리를 "죽은 메모리"로 표시하지 않습니다. 이런 버그(stack-use-after-return)를 잡으려면 스택 프레임을 따로 떼어 두는 기능을 켜야 합니다.
- **Clang, GCC**: 실행할 때 환경 변수 `ASAN_OPTIONS=detect_stack_use_after_return=1`을 주면 켜집니다(버전에 따라 기본으로 켜져 있기도 합니다). 이 저장소에서 Windows의 Clang 22 ASan 빌드로 시험했을 때 랩 75 람다 줄에서 `stack-use-after-return`이 정확히 보고되었습니다.
- **MSVC**: 컴파일 옵션 `/fsanitize-address-use-after-return`이 필요하고, 리포트는 `stack-buffer-underflow`라는 이름으로 나옵니다. 이 저장소에서는 켜지 않았습니다. MSVC 14.51에서 프로젝트 전체에 켜 보면 프로그램 시작 시 전역 `std::string` 초기화에서 오탐이 나서 랩까지 가지 못했고, 이 파일에만 켜면 다른 파일과 공유하는 표준 라이브러리 코드에서 오탐이 났습니다(Debug, Release 런타임 모두). 같은 버그를 담은 작은 단독 프로그램에서는 잘 잡혔습니다.
- 그래서 이 랩의 주 도구는 디버거입니다. 람다 안에 중단점을 걸면 람다를 펼쳐 캡처한 것들을 볼 수 있고, 참조로 캡처한 변수의 주소가 **이미 끝난 함수의 스택**을 가리키는지 확인할 수 있습니다.

6. ASan으로 빌드해 버그 상태를 다시 실행해 봅니다. 이번에는 **쓰는 순간** `heap-buffer-overflow`로 멈추고, 리포트의 첫 호출 스택이 바로 4번의 줄입니다.

# 10부: 비동기와 동시성

여러 스레드가 함께 도는 코드는 **"어느 스레드가, 언제"**가 버그의 절반입니다. 같은 줄이라도 다른 스레드가 어디까지 왔느냐에 따라 맞기도 틀리기도 합니다. 그래서 진짜 프로그램에서는 실행할 때마다 증상이 달라지고, 디버거로 멈추면 타이밍이 바뀌어 증상이 사라지기도 합니다.

> **이 부의 랩은 매번 똑같이 틀립니다.** 래치(`std::latch`), 신호(종, 게시판), 묶음 처리처럼 **순서를 고정하는 장치**를 넣어 버그가 나는 순서를 매번 재현하게 했습니다. 이 장치들은 게임 코드의 일부처럼 보이지만, 버그를 "가끔"에서 "매번"으로 바꾸려고 넣은 것입니다. 장치를 지워서 증상을 숨기지 말고, 원인을 고치세요. 굳을 수 있는 랩은 11부와 같은 2초 감시 타이머 아래에서 돕니다.

## ThreadSanitizer

ThreadSanitizer(TSan)는 두 스레드가 동기화 없이 같은 메모리에 접근하고 그중 하나가 쓰기일 때 그 줄에서 보고합니다. ASan처럼 컴파일 옵션으로 켭니다. ASan과 함께 켤 수는 없습니다.

```bash
cmake -S . -B build/tsan -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS=-fsanitize=thread -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread -DBUGHUNT_BIN_NAME=TSan
cmake --build build/tsan
./bin/TSan/BugHunt 17
```

- 랩 17(길드 금고)의 레이스는 `WARNING: ThreadSanitizer: data race`로 나옵니다. 랩 85는 데이터 레이스가 아닙니다(모든 접근이 `atomic`). TSan이 조용한데도 틀리는 버그가 있다는 것을 비교해 보세요.
- TSan이 보고하면 종료 코드가 바뀌어 채점에서는 CRASH로 나올 수 있습니다.

# 11부: 멈춤 - 무한루프와 데드락

크래시도 없고 틀린 결과도 나오지 않습니다. 프로그램이 그냥 **굳습니다**. 디버거는 알아서 멈춰 주지 않고, 중단점을 어디에 걸어야 할지도 모릅니다.
이때는 굳은 프로그램을 **그 순간 통째로 멈춰 세우고**(모두 중단), 각 스레드가 어디에 있는지 봅니다.

> **안전장치:** 11부 랩은 "랩 작업 스레드"(디버거에는 `lab-worker`로 보임)에서 돌고, 메인 스레드가 2초 감시 타이머를 잽니다. 시간을 넘기면 `[FAIL] ... 응답 없음 (2000 ms 초과)`를 출력하고 끝납니다(`labs.h`의 `runWithWatchdog`).
> **디버거를 붙여 실행하면 감시 타이머가 꺼집니다.** 콘솔에 안내가 나오니, 멈춘 상태를 마음껏 관찰하고 디버깅을 중지해서 끝내세요. (디버거 감지는 `src/platform`에 있습니다. Windows와 Linux, macOS를 지원합니다.)

# 12부: 성능 - 틀리지 않지만 느리다

결과는 모두 맞습니다. 그런데 **느립니다.** 디버거로 한 줄씩 따라가면 모든 줄이 멀쩡해 보입니다. 이때는 "어느 줄이 틀렸나"가 아니라 **"시간을 어디에 쓰나"**를 묻는 도구, **프로파일러**를 씁니다.

> **판정은 시간이 아니라 횟수로 합니다.** PC마다 속도가 달라서 "100 ms 이하" 같은 기준은 믿을 수 없기 때문입니다. 각 랩은 원소 이동, 복사, 할당 바이트, flush 같은 **일의 양**을 세어 판정하고, 시간은 참고로만 출력합니다. 그래서 12부는 Debug, Release, ASan **어느 구성으로 채점해도 결과가 같습니다.**
> **프로파일링은 Release로 하세요.** Debug는 최적화가 꺼져 있고 검사 코드가 많아서 엉뚱한 곳이 느려 보입니다. 이 저장소에서 잰 예로, 캐시를 거스르는 순회는 Release에서 수십 배 느렸지만 Debug에서는 2배도 안 됐습니다. 반대로 Debug에서만 크게 보이는 비용(반복자 검사, 인라인 안 된 작은 함수)도 있습니다.

## 프로파일러 사용법

CPU 샘플링 프로파일러는 프로그램을 디버거 없이 돌리면서 "지금 어느 함수를 실행 중인가"를 아주 자주 기록해, 함수별로 시간을 모읍니다. 도구마다 화면은 다르지만 보는 것은 같습니다.

| 도구 | 시작하는 법 |
|---|---|
| Visual Studio 성능 프로파일러 | 구성을 **Release**로 → 디버그 → 성능 프로파일러 (Alt+F2) → **CPU 사용량** → 시작 |
| Linux `perf` | `perf record -g ./bin/Release/BugHunt 93` → `perf report` |
| macOS Instruments | Instruments → **Time Profiler** → 대상에 `bin/Release/BugHunt`, 인자 `93` → 기록 |
| 그 밖 | Windows의 Intel VTune·AMD uProf, 크로스 플랫폼 `samply`, Valgrind의 `callgrind`(느리지만 정확한 호출 수) 등 |

| 보는 것 | 뜻 |
|---|---|
| 핫 경로 (hot path) | 시간이 가장 많이 흐르는 호출 경로. 맨 아래가 실제로 일하는 함수 (VS: "핫 경로", perf: `perf report`의 호출 그래프) |
| 총 / 자체 시간 (Total / Self, perf의 Children / Self) | 총 = 그 함수와 그 함수가 부른 것 전부, 자체 = 그 함수 몸통만. 자체가 큰 함수가 범인, 총이 큰 내 함수가 범인을 부른 곳 |
| 호출자 / 호출 수신자 | 그 함수를 누가 불렀고 그 함수가 누구를 불렀는지. 소스 줄별 시간(VS: 함수 더블클릭, perf: `perf annotate`) |
| 크기를 두 배로 | 랩의 개수 상수를 두 배로 바꿔 실행. 시간이나 횟수가 2배면 O(n), 4배면 O(n²). 어느 쪽인지가 첫 단서 |

> Visual Studio는 디버깅하면서 중단점 두 개 사이만 프로파일링하는 "진단 도구" 창도 있습니다. Debug에서도 쓸 수 있지만 위 주의대로 Debug의 시간은 믿기 어렵습니다.

> 12부 랩은 1초도 안 걸려 끝나서 프로파일러에 샘플이 적게 잡힐 수 있습니다. 그럴 때는 랩의 개수 상수를 몇 배로 늘려 실행하세요(채점은 원래 값으로 합니다).

```
기록표 (12부용)
크기를 2배로 했을 때 (시간 / 세는 값):   
핫 경로 맨 아래 함수 (자체 CPU가 큰 것):  
그 함수를 부른 내 코드의 줄:            
그 줄이 하는 일의 양이 커지는 이유:       
수정:                                 
수정 후 세는 값:                       
```

- 이미 빌드했다면 `bin/Debug/BugHunt --grade`(Windows는 `bin\Debug\BugHunt.exe --grade`)로 바로 실행해도 됩니다. `--grade 70`, `--grade C-1`, `--grade challenges`도 됩니다. IDE에서 빌드했다면 그 실행 파일에 `--grade`를 주면 됩니다.
- 출력 언어: `--lang ja` 또는 `--lang ko`를 붙입니다(예: `bin/Debug/BugHunt --lang ja --grade`). 붙이지 않으면 환경 변수 `BUGHUNT_LANG`(예: `BUGHUNT_LANG=ja ./grade.sh`, Windows는 `set BUGHUNT_LANG=ja` 뒤 `grade.bat`), 그다음 운영체제의 표시 언어를 따르고, 기본은 한국어입니다. 메뉴, 랩 제목과 증상, `[PASS]`/`[FAIL]` 줄의 설명, 채점기 메시지, 랩 코드가 따로 출력하는 진행 문구와 예외 메시지가 바뀝니다. 게임 안의 데이터(캐릭터·아이템 이름, 파일 내용 등)와 랩이 저장해 두고 비교하는 문구도 고른 언어를 따릅니다. `grade-report.json`은 키와 `result` 값이 언어와 상관없이 같고 `title`과 `detail`만 고른 언어로 나옵니다.
- 소스 코드에서는 화면에 나오는 한국어 문자열마다 그 자리에 일본어를 함께 적습니다. 예: `expect(i18n::L("최장 연속 출석", "最長連続出席"), 7, result.bestStreak)`. 한국어 문자열에 일본어 짝이 없으면 빌드가 실패합니다(빌드 끝에 `BugHunt --check-i18n BugHunt/src`가 실행됨).


## 판정 방법

- 랩마다 `BugHunt`를 **자식 프로세스로 따로** 띄웁니다(`--grade-child N`). 한 랩이 죽거나 멈춰도 다른 랩과 채점기는 영향을 받지 않습니다. 채점 중에는 어설션이나 오류 보고 대화상자가 뜨지 않고 바로 종료됩니다.
- 판정은 자식 프로세스의 **종료 코드와 시간**으로만 합니다.

| 결과 | 조건 |
|---|---|
| PASS | 종료 코드 0 (모든 검사가 `[PASS]`). 숨은 케이스가 있으면 그것도 0 |
| FAIL | 종료 코드 10 (`[FAIL]`이 하나 이상) |
| TIMEOUT | 종료 코드 11 (감시 타이머 2초 초과), 또는 채점기의 랩당 제한 15초 초과 |
| CRASH | 그 밖의 종료 코드나 시그널. 처리되지 않은 예외, `abort()`(BugHunt 메모리 검사기의 `[CRASH] 메모리 검사: ...` 포함), ASan 오류, 잘못된 주소 접근, 스택 오버플로 등. 아래 [크래시 코드](#크래시-코드) 표 참고 |

- **숨은 케이스:** 3~12부 랩과 챌린지는 평소 실행이 통과하면 **화면에 나오지 않는 다른 데이터로 한 번 더** 실행합니다(`--grade-child N --hidden`). 결과를 하드코딩해서 `[PASS]`를 만들거나, 보이는 데이터에서만 맞는 반쪽짜리 수정(예: 랩 88을 `t < cooldownSeconds`로만 고치기)은 여기서 걸립니다. 이때 결과는 FAIL이고, 설명은 `증상은 사라졌지만 원인이 남아 있음 (숨은 케이스)`으로 시작합니다. 챌린지는 모두 숨은 케이스가 있습니다. 숨은 테스트는 각 랩 파일 맨 아래 `채점용 숨은 테스트` region에 있습니다. 소스라서 열어 볼 수는 있지만 풀이에는 필요 없고, 고치면 채점이 의미가 없어집니다. 1·2부는 크래시 자체가 증상이라 숨은 케이스가 없습니다.
- 판정은 표준 C++에서 관찰할 수 있는 값(범위 검사 예외, 인스턴스 수, BugHunt 메모리 검사기 등)으로 하므로 구성이나 컴파일러가 달라도 결과가 같게 만들었습니다. 이 저장소에서 MSVC 14.51과 Clang 22(Windows)로 Debug, Release, ASan 여섯 가지를 모두 채점해 보니 **버그 상태는 모두 0/109, 정답을 모두 적용하면 모두 109/109**였습니다. 실패의 종류는 조금 다를 수 있습니다(예: Clang Release에서 랩 89는 TIMEOUT 대신 FAIL. 11부 랩 89 설명 참고).
- 채점기 자체의 종료 코드는 만점이면 0, 아니면 1입니다.

## grade-report.json 형식 (BugHunt 네 판 공통)

채점 결과는 기계가 읽을 수 있는 `grade-report.json`으로도 저장됩니다(UTF-8, 채점기를 실행한 폴더, `.gitignore`에 포함). C#, 언리얼, 유니티판도 같은 형식을 씁니다.

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 109,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "CRASH", "ms": 16, "detail": "액세스 위반 (0xC0000005)" },
    { "id": 21, "title": "출석 보상", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| 필드 | 타입 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 어느 판의 결과인지. 이 저장소는 `"cpp"` |
| `version` | 정수 | 이 JSON 형식의 버전. 지금은 `1`. 필드의 뜻이 바뀌면 올린다 |
| `total` | 정수 | 채점한 랩 수(= `labs` 길이). 랩 하나만 채점하면 1 |
| `passed` | 정수 | `result`가 `"PASS"`인 랩 수 |
| `labs[].id` | 정수 | 랩 번호(메뉴 번호). 챌린지는 정수를 유지하려고 깊은 추적 C-n = `100 + n`, 블라인드 B-n = `200 + n` (예: C-1 = 101, B-3 = 203). 네 판 공통 |
| `labs[].title` | 문자열 | 랩 이름. 챌린지는 `"챌린지 C-1"`처럼 번호만 (블라인드는 이름으로도 힌트를 주지 않는다) |
| `labs[].part` | 정수 | 부 번호. 챌린지는 `0`. 네 판 공통 |
| `labs[].result` | 문자열 | `"PASS"`, `"FAIL"`, `"TIMEOUT"`, `"CRASH"`, `"SKIP"` 중 하나. 이 저장소는 `"SKIP"`을 내지 않는다(엔진판에서 GPU가 필요한 랩에 쓴다) |
| `labs[].ms` | 정수 | 걸린 시간(밀리초). 숨은 케이스 실행 시간 포함 |
| `labs[].detail` | 문자열 | 실패 이유 한 줄(첫 `[FAIL]` 줄, 크래시 종류와 단서 등). PASS면 빈 문자열. 평소 데이터는 통과했는데 숨은 케이스에서 실패하면 `"증상은 사라졌지만 원인이 남아 있음 (숨은 케이스) "`로 시작 |

## 크래시 코드

채점표의 CRASH 설명이나 디버거가 멈춘 이유에 나오는 값입니다. Windows에서는 종료 코드(예외 코드)로, Linux·macOS에서는 시그널로 나옵니다. 디버거 키는 위 [디버거 대응표](#디버거-대응표)를 보세요.

| 뜻 | Windows | Linux / macOS |
|---|---|---|
| 잘못된 주소 접근 (nullptr, 해제된 메모리 등) | `0xC0000005` 액세스 위반 | `SIGSEGV` (macOS는 `SIGBUS`일 때도 있음) |
| 스택 오버플로 (끝나지 않는 재귀, 큰 지역 변수, 깊은 재귀 × 큰 프레임) | `0xC00000FD` | `SIGSEGV` |
| 정수를 0으로 나눔 (이 저장소의 랩에는 없음) | `0xC0000094` | `SIGFPE` |
| `abort()` (처리되지 않은 예외, 어설션, BugHunt 메모리 검사기) | 종료 코드 3 (어설션은 `0xC0000420`일 때도 있음) | `SIGABRT` |
| 런타임이 발견한 힙 손상 (보통 망가뜨린 곳보다 한참 뒤에 터짐) | `0xC0000374` | `SIGABRT` (glibc의 `free(): invalid pointer` 등) |
| ASan 오류 | 종료 코드 1 | 종료 코드 1 |

> BugHunt 메모리 검사기가 메모리를 채우는 값(새로 받은 메모리 `0xA5`, 해제된 메모리 `0xEE`, 블록 뒤 경계 `0xBD`)은 2부의 [빌드 구성과 BugHunt 메모리 검사기](#빌드-구성과-bughunt-메모리-검사기)에 있습니다. 컴파일러마다 다른 디버그 채움 값(MSVC의 `0xCC`, `0xDD` 등)도 그 절의 도구별 참고에 있습니다.

バグが **わざと仕込まれた** 小さなゲームコードの集まりです。

- **第1部: 呼び出し履歴入門 (ラボ1~8)**: プログラムが落ちた瞬間の **呼び出し履歴** をさかのぼって原因を探す練習。初心者はここから始めてください。
- **第2部: 応用 (ラボ9~20)**: メモリエラー、未初期化、データ競合など、症状があまり親切でないバグ。データ ブレークポイントや ASan のような道具を使います。

- **第4部: コンテナ (ラボ33~39)**: 標準コンテナとアルゴリズムが「規則どおり」に動いたのに期待と違う場合。操作の前後でコンテナを展開して比べます。
- **第5部: C++ 言語の落とし穴 (ラボ40~48)**: `const` への `std::move`、符号付き整数のオーバーフロー、縮小変換、符号付き/符号なしの変換、グローバル初期化順序、ヘッダーの `static`、例外の経路での漏れ、デストラクターから投げる、範囲 for。コンパイラーが受け入れるコードに潜む言語規則を、ウォッチと警告で見つけます。
- **第6部: インターフェースと継承 (ラボ49~54)**: オーバーライドされていない仮想関数、スライシング、コンストラクター内の仮想呼び出し、デフォルト引数、オーバーロードの隠蔽、`dynamic_cast`。「見当違いの関数が呼ばれる」バグを、ステップ イン (Step Into) と実際の型の表示で追跡します。
- **第7部: ファイル入出力 (ラボ55~61)**: 作業ディレクトリ、バッファーと flush、`eof()` のループ、`getline`、failbit、BOM、半分だけ書かれたセーブ。ストリームの状態とディスク上の実際のバイトを一緒に見ます。
- **第8部: シリアライズ JSON/XML (ラボ62~68)**: nlohmann/json と pugixml を使うセーブ・ロードのコードの落とし穴。`third_party/` に固定バージョンで入っています。
- **第9部: ポインターの誤用 (ラボ69~80)**: 解放後の使用 (use-after-free)、初期化されていないポインター、`new[]`/`delete` の組み合わせ違いのような未定義動作。メモリチェッカーと ASan の報告を読み、原因までさかのぼります。ラムダキャプチャの寿命とスタック/ヒープのあふれ(ラボ76~80)も扱います。
- **第10部: 非同期と並行性 (ラボ81~87)**: `std::async` と `future`、`condition_variable`、`atomic`、スレッドの寿命、コルーチン。バグが毎回同じように再現するよう、順序を固定してあります。スレッド一覧、すべてのスレッドの呼び出し履歴、条件付きブレークポイントで「どのスレッドがいつ」を追跡します。
- **第11部: フリーズ (ラボ88~92)**: クラッシュも間違った答えもなく、プログラムが **固まる** 無限ループとデッドロック。すべて中断 (break all)、スレッド一覧、すべてのスレッドの呼び出し履歴で止まった場所を探します。
- **第12部: パフォーマンス (ラボ93~98)**: 結果は正しいのに **遅い** コード。デバッガーの代わりに **プロファイラー** で時間を使っている場所を探します。
- **チャレンジ (C-1~C-3、B-1~B-8)**: すべて終えた人のためのヒントなしの問題。何段階もさかのぼる深い追跡と、症状を1行だけ与えるブラインド問題です。

> コードを目で流し読みして答えを探さないでください。第1・2部は **実行して落とし、デバッガーが止まった場所から**、第3~8部は **自分で止めた場所から値を確かめながら**、第9部は **チェッカーの報告から**、第10部は **スレッド一覧とすべてのスレッドの呼び出し履歴から**、第11部は **固まった瞬間にすべて中断で止めた場所から**、第12部は **プロファイラーのホット パスから** 追跡してください。すべて直したら `grade.bat`(Windows)または `./grade.sh` で採点します。
>
> 各部がどの種類のバグを扱い、何が抜けているかは、下の [扱うバグの一覧](#扱うバグの一覧) にあります。

**標準 C++ 版です。** ラボのコードは ISO C++20 だけを使います(コンパイラー拡張、`_s` 関数、コンパイラーごとの `#ifdef` はなし)。MSVC、Clang、GCC のどれでビルドしても **同じラボが同じ理由で FAIL** し、直せば PASS するはずです。クラッシュの形(どのシグナル、どのメッセージ)はコンパイラーと OS ごとに違っても、採点結果は同じです。コンソール設定、子プロセス、ウォッチドッグのように OS ごとに異なるコードは、`BugHunt/src/platform/` の1か所に Windows 用と POSIX(Linux、macOS)用に分けてあります。

## 準備

C++20 に対応したコンパイラーと CMake 3.21 以上が必要です。ビルド構成は `CMakePresets.json` の3つのプリセットです。

| プリセット | 出力 | 用途 |
|---|---|---|
| `debug` | `bin/Debug/` | 既定。最適化なし、デバッグ情報あり |
| `release` | `bin/Release/` | 最適化ビルド。第12部のプロファイリング、「Debug では動くのに Release では動きません」の体験 |
| `asan` | `bin/ASan/` | Debug + AddressSanitizer |

**コマンドライン** (Windows は `build.bat`、それ以外は `./build.sh` が下記を代わりに実行します)

```bash
cmake --preset debug
cmake --build --preset debug
```

- Windows: Visual Studio の「x64 Native Tools コマンド プロンプト」で実行するか、`build.bat Debug` を使ってください。`build.bat` は Visual Studio を探して開発者環境(MSVC、CMake、Ninja)を読み込みます。
- Linux、macOS: `./build.sh Debug`。コンパイラーを選ぶには `CXX=clang++ ./build.sh Debug` のように指定します(最初の構成時にだけ適用されるので、変えるには `build/` フォルダーを削除してください)。

**IDE**

- **Visual Studio**: 「フォルダーを開く」でリポジトリのフォルダーを開くと、プリセットが読み込まれて構成の一覧に Debug、Release、ASan が現れます。スタートアップ項目に `BugHunt.exe` を選んで実行します。以前のように `BugHunt.sln`(または `.slnx`)を開いてもかまいません(Windows 専用の選択肢)。
- **VS Code**: CMake Tools 拡張機能とデバッガー拡張機能(C/C++ の `cppdbg` または CodeLLDB)をインストールし、プリセットを選んでからビルドしてデバッグします。ラボ番号は `launch.json` の `args`(例: `["1"]`)で渡します。
- **gdb / lldb**: `gdb --args bin/Debug/BugHunt 1` または `lldb -- bin/Debug/BugHunt 1` で起動して `run`。

**実行**: メニューでラボ番号を入力するか、引数で番号を渡します(`BugHunt 1`、`BugHunt C-1`)。第1・2部は **必ずデバッガーをアタッチして** 実行してください。デバッガーなしで実行すると、プログラムは落ちるだけで呼び出し履歴を見ることができません。

> このリポジトリで実際にビルドして採点を確認したコンパイラーは、Windows の **MSVC 14.51** と **Clang 22**(Visual Studio に同梱のもの、MSVC 標準ライブラリを使用)です。GCC、libstdc++、libc++、Linux/macOS ではまだ確認していません。

# 第1部: 呼び出し履歴入門

## 呼び出し履歴とは?

関数が関数を呼ぶと、コンピューターは「誰が自分を呼んだか」を順番に積み上げておきます。その山が **呼び出し履歴(コールスタック、Call Stack)** です。

```
printPlayer        ← いちばん上: 今実行中の関数 (ここで落ちた)
showProfile        ← printPlayer を呼んだ関数
openFriendList     ← showProfile を呼んだ関数
cs01_profile
main               ← いちばん下: プログラムの始まり
```

**上から下へ読めば「誰が自分を呼んだか」**、**下から上へ読めば「プログラムがどうやってここまで来たか」** です。

## 呼び出し履歴の見方

| やりたいこと | 方法 (道具ごとのキーは [デバッガー対応表](#デバッガー対応表)) |
|---|---|
| 呼び出し履歴を見る | デバッガーが止まったら呼び出し履歴 ウィンドウ(パネル)を開く。gdb・lldb は `bt` |
| ローカル変数を見る | ローカル ウィンドウ(パネル)。gdb は `info locals`、lldb は `frame variable` |
| 別のフレームへ移動 | 呼び出し履歴で行を選ぶ → コードウィンドウがその関数の「呼び出した行」へ移り、ローカル変数が **その関数の変数** に切り替わる |
| 標準ライブラリ、システム関数 | 自分のコードではないフレーム。道具によっては折りたたんで表示される(Visual Studio の `[外部コード]`) |

呼び出し履歴の1行は道具ごとに見た目が少し違いますが、含まれる情報は同じです。

```
Visual Studio:  BugHunt.exe!lab1::showProfile(const std::string & name) 行 40
gdb / lldb:     #1  lab1::showProfile (name="Dorna") at cs01_profile.cpp:40
                    └ 名前空間::関数 ┘ └ 引数 ┘    └ ソースファイル:行 ┘
```

- **現在の行**: 今止まっている場所 (いちばん上のフレーム)。Visual Studio は黄色い矢印、gdb は `=>`
- **呼び出した行**: 別のフレームを選んだときの「ここで上の関数を呼んだ」という位置。Visual Studio は緑の矢印
- 標準ライブラリや OS のフレームはたいてい飛ばして、**自分のコードが最初に出てくる行** から見れば十分です。

## デバッガーが止まる3つのパターン

| パターン | 意味 | やること |
|---|---|---|
| 不正なメモリアクセス (Windows: 「アクセス違反」、Linux/macOS: `SIGSEGV`) | 不正なポインターなど。その行ですぐ止まる | 呼び出し履歴を見る |
| 処理されない例外 (`std::out_of_range` など) | `throw` された例外を誰も捕まえない。最終的に `std::terminate` → `abort()` | デバッガーが throw 地点か `abort` で止まる → 呼び出し履歴で自分のコードを探す。投げた瞬間に止めたいなら「例外が投げられたときに止める」をオンにする |
| `abort()` + `[CRASH] ...` メッセージ | BugHunt のチェッカー(メモリ検査、ソート検査)か標準ライブラリのデバッグチェックが誤りを見つけた | コンソールのメッセージを最後まで読み → 呼び出し履歴で自分のコードを探す |

<details>
<summary>道具別の参考: Visual Studio のアサーション ウィンドウ</summary>

MSVC の Debug 構成の標準ライブラリは、範囲外の `operator[]` や無効になったイテレーターのような誤りを **Debug Assertion Failed!** ウィンドウで知らせます。**再試行 (Retry)** → (ブレークポイントのメッセージが出たら「中断」) → 呼び出し履歴を見ればよいです。GCC の libstdc++ は `-D_GLIBCXX_ASSERTIONS`、Clang の libc++ はハードニングモードで似たチェックをオンにでき、このリポジトリの CMake は Debug で両方をオンにします。BugHunt のラボは、このようなチェックが **あってもなくても同じ結果** になるように作ってあります(第1部の範囲外アクセスは `at()` を使うので、どの構成でも例外になり、ラボ13は無効になったイテレーターを直接捕まえる `bughunt::CheckedList` を使います)。例外は、Debug と Release のこの違いを見せるために作ったラボ80です。
</details>

## 追跡の4ステップ (全ラボ共通)

1. **どこで止まった?** 呼び出し履歴で **自分のコードが出てくる最初の行** を探す。
2. **何がおかしい?** そのフレームのローカル変数から、おかしな値(nullptr、0、とても大きな数、負の数...)を探す。
3. **その値はどこから来た?** 1つ **下** のフレーム(= 自分を呼んだ関数)をダブルクリックして、その値を渡した場所を見る。出どころが分かるまで繰り返す。
4. **本当の原因は?** 止まった場所ではなく、**おかしな値が最初に作られた場所** を直す。

> 💡 ポイント: **落ちた場所 ≠ 間違えた場所** であることがほとんどです。呼び出し履歴は「間違えた場所」へさかのぼるための道です。

### ビルド構成と BugHunt メモリチェッカー

| 構成 | 用途 |
|---|---|
| Debug | 基本。最適化がないので1行ずつ追いやすい |
| Release | 最適化ビルド。未定義動作が Debug とは **違う形** で現れることを体験するとき |
| ASan | AddressSanitizer。解放後の使用、範囲外アクセス、二重解放を **その行で** 捕まえ、読んだ場所/解放した場所/確保した場所の呼び出し履歴を見せてくれる |

コマンドラインでのビルド: `build.bat Debug` / `build.bat Release` / `build.bat ASan` (Linux、macOS は `./build.sh`)

解放されたメモリを読んだり、初期化していない値を使ったりするのは **未定義動作**(undefined behavior)です。標準は結果を定めていないので、何事もなく正しい値が出ることもあれば、コンパイラーや構成を変えたとたんに間違うこともあります。そこで採点結果がコンパイラーによって揺れないように、BugHunt は標準が認める **グローバル `operator new`/`delete` の置き換え** で作った小さなメモリチェッカー(`src/support/heap_guard.cpp`)を Debug と Release に入れました。ASan 構成では ASan が同じことをより正確に行うので、メモリチェッカーはオフにします。

| メモリチェッカーがすること | その結果 |
|---|---|
| 新しく確保したメモリを `0xA5` で埋める | 初期化していない値を読むと `0xA5A5A5A5`(-1515870811)のような **見分けのつくゴミ** が出る |
| 解放したメモリを `0xEE` で上書きし、しばらく再利用しない | 解放後の使用で **たまたま正しい値** を読むことがない。`0xEEEEEEEE`(-286331154)が見えたら解放済みメモリ |
| ブロックの直後16バイトを `0xBD` で埋め、解放時に確認する | 確保したサイズを超えて書くと `[CRASH] メモリ検査: ... (バッファーオーバーラン)` |
| 二重解放、`new[]`/`delete` の組み合わせ間違い、`new` で得ていないアドレスの解放 | `[CRASH] メモリ検査: ...` のメッセージの後に `abort()` |

これらの値は BugHunt が決めたものなので、どのコンパイラーでも同じです。本物のプログラムにはこのようなメモリチェッカーがないことを覚えておいてください。メモリチェッカーがなければ、同じバグが「実行するたびに、コンパイラーごとに違って」見えます。

<details>
<summary>道具別の参考: MSVC Debug の <code>/RTC1</code>、CRT デバッグ ヒープ、マジックナンバー</summary>

MSVC の Debug 構成は独自にメモリを埋めます。Visual Studio で BugHunt をデバッグしていると、これらの値を見ることもあります(メモリチェッカーが上書きする前や、スタック変数など)。

| 値 | 意味 |
|---|---|
| `0xCCCCCCCC` (-858993460) | `/RTC1` が埋めた、初期化されていない **スタック** メモリ |
| `0xCDCDCDCD` | CRT デバッグ ヒープ: `new` で得たが、まだ何も書いていない **ヒープ** メモリ |
| `0xDDDDDDDD` | CRT デバッグ ヒープ: すでに解放されたヒープ メモリ |
| `0xFDFDFDFD` | CRT デバッグ ヒープ: ブロックの前後の境界(no man's land) |

`/RTC1` は MSVC 専用のランタイム チェックで(CMake の MSVC Debug の既定値)、GCC・Clang には同じものがありません。初期化されていない値は、GCC・Clang の `-ftrivial-auto-var-init=pattern`、MemorySanitizer(Clang、Linux)、Valgrind などの道具で見つけます。コード分析の警告(MSVC C26495「メンバーが初期化されていない」など)も手がかりになります。
</details>

# 第3部: フロー追跡 (クラッシュなし)

第1・2部ではプログラムが落ちてくれました。デバッガーが「ここだよ」と止まってくれるので、呼び出し履歴をさかのぼるだけで済みましたね。
実務のバグのほとんどはそうではありません。プログラムは最後まで問題なく動き、**数字が1つ間違っているだけ** です。このときは **自分で止めて、自分で追いかける** 必要があります。

> 第3部は必ず **Debug** 構成で行ってください。Release では最適化のために行が飛ばされたり、変数が「最適化されているため使用できません」(gdb: `<optimized out>`)と表示されたりします。

## フロー追跡の4ステップ (第3部共通)

1. **先に期待を書く。** 「この行が終わったら `streak` は2のはず」のように、追いかける前に各ステップの期待値を決める。期待がなければ、間違った値を見ても見過ごしてしまう。
2. **間違った結果に一番近い所から止める。** プログラムの一番最初ではなく、[FAIL] になった値を作る関数の入口にブレークポイントを置く。
3. **期待と最初に食い違う行を探す。** 1行ずつ実行(ステップ オーバー (step over))しながら値を確認する。食い違った行が関数呼び出しなら、その関数の中に(ステップ イン (step into))入って同じことを繰り返す。
4. **「最初に食い違った所」を直す。** その後に出てくる間違った値の多くは、その結果にすぎない。

```
記録表 (第3部用)
間違った結果:              
止めた位置:              
期待値 → 実際の値:         
最初にずれた行:          
本当の原因:              
修正:                   
```

## 第3部で使う道具

道具ごとのキーとコマンドは [デバッガー対応表](#デバッガー対応表) にあります。

| 操作 | いつ |
|---|---|
| ブレークポイント + 1行ずつ実行(step over) | 基本。値が行ごとにどう変わるかを見るとき |
| 関数の中へ(step into) / 外へ(ステップ アウト (step out)) | 怪しい関数呼び出しがあるとき。外に出ると、デバッガーが今戻ってきた値を見せてくれる(Visual Studio: 自動変数 ウィンドウの `関数名 の戻り値`、gdb: `finish` の `Value returned`) |
| カーソルまで実行 | ブレークポイントなしで「ここまで進めて」 (Visual Studio: Ctrl+F10、VS Code: Run to Cursor、gdb: `until 40`) |
| 条件付きブレークポイント (例: `tick == 148`、`c.name == "Selene"`) | 繰り返しが数百回あり、そのうち1回だけおかしいとき |
| ヒット カウント | 「5回目の呼び出しでだけ止まって」 |
| トレースポイント (logpoint、`dprintf`) | 止めずに **順序** と値を記録するとき。結果はデバッガーの出力に表示される |
| ウォッチに式を入れる (`c.isVip()`、`&item`、`a.x - b.x`) | 条件文の各部分を別々に計算してみるとき、2つのオブジェクトが同じかをアドレスで比べるとき |
| 特定のオブジェクトを追いかける | アドレスを書き留めておき、ウォッチに `*(Item*)0x...` と入れる。Visual Studio には「オブジェクト ID の作成」(`$1`)もある |
| 実行位置を移す (次のステートメントの設定、`jump`) | 同じコードをもう一度実行してみたり、分岐を飛ばして仮説を試したりするとき (状態は元に戻らないことに注意) |

## 演算子のミス (ラボ29~32)

`x++` と `++x`、`&` と `&&`、`|` と `||` は1文字違いなのでコードレビューで目に留まりにくく、警告なしでコンパイルされます。
結果はクラッシュではなく **値が1つずれる** ことなので、第3部のフロー追跡の道具で捕まえます。
ここでは特に「式の値」と「変数に残る値」が食い違う瞬間を見る練習をします。

- ウォッチ(watch)に式をまるごと入れてみる: `2 & 1`、`2 && 1`。`guild.lastId++` は入れないでください(ウォッチも副作用を実行します)
- データ ブレークポイント(値が変わると止まるブレークポイント、watchpoint)で、1行の中で値が何回変わるかを数える
- 関数から戻った直後に戻り値を見る (step out の直後にデバッガーが見せてくれる戻り値。Visual Studio: 自動変数 ウィンドウ、gdb: `finish`)

> コンパイラーによって結果が変わる式(`f(i++, i++)`、`i++ + i++`)はあえて入れていません。判定がコンパイラーによって変わってはいけないからです。下の「未収録」を見てください。

### 演算子ラボで追加で使う道具

| 道具 | やり方 | いつ |

| データ ブレークポイント (watchpoint) | 変数のアドレスに「値が変わったら中断」 (VS: デバッグ → 新しいブレークポイント → データ ブレークポイント、gdb/lldb: `watch`) | 1行の中で値が **何回** 変わるか、誰が変えるかを見るとき (ラボ30) |

### やってみよう: ラボ31 (闇の洞窟)

1. ラボ31を実行します。`[FAIL] ボラムは入れるか? (期待: true, 実際: false)`。ボラムは鍵2個、たいまつ1個です。
2. **期待を書きます。** 鍵 > 0 かつ たいまつ > 0 なら入場。ボラムは入場できるはずです。
3. `canEnterCave` の `return` 行にブレークポイントを置き、**条件付きブレークポイント** にします。条件: `a.name == "ボラム"`(`--lang ko` では `"보람"`) (または `a.keys == 2`)。
4. 実行します。ボラムで止まったら、ウォッチに `a.keys & a.torches` を入れます。値は0です。
5. ウォッチに `2 & 1`、`3 & 1`、`2 && 1` も入れて比べます。2(`10`)と1(`01`)には重なるビットがありません。
6. `&&` に直して(または `a.keys > 0 && a.torches > 0`)再実行し、[PASS] を確認します。
7. ラボ20(状態フラグ)では `&` が **正しい** 演算子で、優先順位が問題でした。今回は `&` 自体が間違いです。フラグ(ビットの集まり)には `&`、真偽には `&&`。

# 第5部: C++ 言語の落とし穴

この部のバグはすべて **コンパイラーが受け入れるコード** です。`std::move` がコピーになり、オーバーフローした整数が負の数になり、小数点以下が切り捨てられ、負の数がとても大きな正の数になり、グローバル変数が0で、ヘッダーの変数が二つに分かれ、例外がメモリを漏らし、デストラクターの例外がプログラムを終了させ、範囲 for が新しい要素を見ません。
文法は正しくても、言語の規則を一つ誤解していると起きるバグです。そのため、直し方よりも **規則の名前を知ること** が大切です。各ラボのヒント2がその規則です。

この部の共通の道具は、**ウォッチに式をそのまま入れて計算の段階を分けて見ること**(`baseExp * multiplier`、`static_cast<std::size_t>(x)`、`&g_saveStats`)と、**警告を手がかりとして読むこと** です。
いくつかのラボでは、コンパイラーがすでに警告を出しています(42 縮小変換、47 例外を投げるデストラクター)。警告一覧を先に見る習慣が、いちばん安上がりなデバッグです。

> 第3部のラボ20(演算子の優先順位)と第3部末尾の演算子ラボ、第2部のラボ3(整数の割り算)・14(`unsigned` のアンダーフロー)とつながっています。この部は「型と寿命の規則」に集中します。

# 第6部: インターフェースと継承

仮想関数は「実際のオブジェクトの型に合った関数が呼ばれる」という約束です。この約束には例外がいくつもあります。
シグネチャーが1文字でも違えばオーバーライドではなく、値でコピーすれば派生部分が切り落とされ、構築中のオブジェクトはまだ派生型ではなく、デフォルト引数は仮想的には選ばれません。
どれもコンパイルは問題なく通り、結果は「別の関数が呼ばれた」です。

この部の共通の道具は、**ステップイン (Step Into) で実際にどのクラスの関数に入るかを見ること** と、**ウォッチでオブジェクトの実際の型を見ること** です。
デバッガーはポリモーフィックなオブジェクトを実際の型(例: `{Boss}`)で表示し、仮想関数テーブル(vtable)のポインターも展開して見られます。

> ラボ16(仮想デストラクターの欠落)は第2部にそのまま置きます。この部は「呼ばれる関数が違う」に集中します。

## 第6部で使う道具

| 道具 | やり方 | いつ |
|---|---|---|
| ステップイン (Step Into) | 仮想呼び出しの行で1段入る | どのクラスの関数が呼ばれるか確認 (ラボ49, 52) |
| 止まらないブレークポイント | 派生クラスの関数にブレークポイント → 止まらなければそれが手がかり | オーバーライドされていない、またはオブジェクトが切られたとき (ラボ49, 50, 51) |
| 実際の型を見る | ウォッチやローカル ウィンドウでオブジェクトを展開し、型名とvtableを確認 | スライシング、コンストラクター内での型 (ラボ50, 51) |
| 呼び出し履歴を上がる | 落ちた場所から1段ずつ上がって値を比べる | `dynamic_cast` の結果が nullptr のとき (ラボ54) |
| コンパイラーに聞く | `override`、`explicit`、`= delete` を付けて再ビルド | 意図をコードに書いて、ミスをコンパイルエラーに変える |

# 第7部: ファイル入出力

ファイル入出力のバグの多くは「ファイルは無事なのに、プログラムの読み方が違う」ケースです。クラッシュも例外もありません。
ストリームは失敗しても黙って状態ビットを立てるだけで、パスは起動した場所によって別のファイルを指し、書いた内容はバッファーに留まっています。
そこでこの部では、変数の代わりに **ストリームの状態** と **ディスクに実際にあるバイト** を一緒に見ます。

- すべてのラボは `一時フォルダー/BugHunt/<ラボ名>/` の下にだけファイルを作り、終わったら削除します(`std::filesystem::temp_directory_path()`)。
  ブレークポイントで止まっている間はファイルが残っているので、エクスプローラーやエディターで直接開いてみられます。
- 判定はOSとコンパイラーに関係なく同じになるようにしました。そのため、OSによって結果が違うテーマ(テキストモードの改行変換など)は「未収録」に理由と一緒に書いています。

## 第7部で使う道具

| 道具 | やり方 | いつ |
|---|---|---|
| ストリーム状態のウォッチ | ウォッチに `in.good()`、`in.eof()`、`in.fail()`、`in.rdstate()` | 読み込みが「黙って」止まったとき。`fail` が立ったストリームはその後のすべての読み込みを無視する (ラボ57, 59) |

# 第9部: ポインターの誤用

第1部・第2部で nullptr、vector の参照の無効化、string_view のダングリング、erase 後のイテレーター、二重解放、仮想デストラクター、構造体のバッファーあふれを扱いました。第9部はそれ以外のポインターのミスです。
第9部のバグはすべて **未定義動作** です。寿命が終わったメモリを読み、初期化していないポインターをたどり、`new[]` で作ったものを `delete` で消します。規格はこのとき何が起きるかを定めていないので、実際のプログラムではコンパイラー、最適化、OS、さらには実行するたびに症状が変わります。「Release では動くんですが」はバグがないという意味ではありません。

BugHunt は採点がぶれないように Debug と Release に **メモリチェッカー** を入れました([ビルド構成と BugHunt メモリチェッカー](#ビルド構成と-bughunt-メモリチェッカー))。そのため第9部は、どのコンパイラー、どの構成でも同じラボが同じ理由で失敗します。ASan 構成ではチェッカーの代わりに ASan が報告します。両方を実行してみて、報告の内容を比べてください。

## ラムダのキャプチャと ASan (ラボ75)

`[&]` ラムダはローカル変数の **アドレス** を持っています。ラムダをタイマーやコールバックの一覧に預けて関数が終わると、そのアドレスはもう終わった関数のスタックです。ヒープと違ってスタックには「解放」という出来事がなく、次の関数呼び出しが同じ場所をすぐに再利用します。

バグの状態で実行してみると、間違った値はコンパイラーと構成ごとに違います(このリポジトリで確認した Kael の攻撃力の例: MSVC Debug -124、MSVC・Clang Release 45、Clang Debug 85、ASan は数億台のゴミ値。Debug の値はビルドし直すと変わることがあります)。スタックの場所がいつ再利用されるかは、最適化とスタックの配置しだいだからです。Release の 45 は、ラムダが読んだ `bonus` の場所に、後で怒りを使った Doran の `bonus`(45)が入っていたために出た値です。どの場合でも、期待した 60 は出ません。

- ASan が既定で捕まえられない理由: 既定の ASan は、関数が終わった後のスタックの場所を「死んだメモリ」として印を付けません。この種のバグ(stack-use-after-return)を捕まえるには、スタックフレームを別に切り離しておく機能を有効にする必要があります。
- **Clang, GCC**: 実行時に環境変数 `ASAN_OPTIONS=detect_stack_use_after_return=1` を与えると有効になります(バージョンによっては既定で有効なこともあります)。このリポジトリで Windows の Clang 22 ASan ビルドで試したところ、ラボ75のラムダの行で `stack-use-after-return` が正確に報告されました。
- **MSVC**: コンパイルオプション `/fsanitize-address-use-after-return` が必要で、レポートは `stack-buffer-underflow` という名前で出ます。このリポジトリでは有効にしていません。MSVC 14.51 でプロジェクト全体に有効にすると、プログラム開始時のグローバル `std::string` の初期化で誤検出が出てラボまでたどり着けず、このファイルだけに有効にすると、他のファイルと共有する標準ライブラリのコードで誤検出が出ました(Debug、Release ランタイムとも)。同じバグを含む小さな単独のプログラムではきちんと捕まりました。
- そのため、このラボの主な道具はデバッガーです。ラムダの中にブレークポイントを置くとラムダを展開してキャプチャしたものを見ることができ、参照でキャプチャした変数のアドレスが **もう終わった関数のスタック** を指しているかを確認できます。

## あふれ: スタックとヒープの境界 (ラボ76~80)

ポインターの誤用の最後のまとまりは **「決まった大きさを超えた」** です。スタックはスレッドごとに大きさが決まっていて(既定で Windows 1 MB、Linux 8 MB 程度)、ヒープのブロックや配列、構造体のメンバーもそれぞれ大きさを持っています。
あふれた瞬間にすぐ落ちる場合(スタックオーバーフロー)、しばらく後に解放するときに落ちる場合(ヒープ破損)、何も起きずに隣の値が変わる場合(構造体の中でのはみ出し)が、すべてこのまとまりにあります。
同じバグでも構成ごとに症状が違うので、第9部の他のラボと同じように **Debug、Release、ASan でそれぞれ実行して比べて** みてください。

# 第10部: 非同期と並行性

複数のスレッドが一緒に動くコードでは、**「どのスレッドが、いつ」** がバグの半分です。同じ行でも、他のスレッドがどこまで進んだかによって正しくもなり間違いにもなります。そのため実際のプログラムでは実行するたびに症状が変わり、デバッガーで止めるとタイミングが変わって症状が消えることもあります。

> **この部のラボは毎回同じように間違えます。** ラッチ(`std::latch`)、合図(鐘、掲示板)、まとめ処理のような **順序を固定する仕組み** を入れて、バグが起きる順序を毎回再現するようにしました。これらの仕組みはゲームのコードの一部のように見えますが、バグを「ときどき」から「毎回」に変えるために入れたものです。仕組みを消して症状を隠さず、原因を直してください。固まる可能性のあるラボは、第11部と同じ2秒のウォッチドッグの下で動きます。

## ThreadSanitizer

ThreadSanitizer(TSan)は、2つのスレッドが同期なしで同じメモリにアクセスし、そのうち1つが書き込みのときに、その行で報告します。ASan と同じくコンパイルオプションで有効にします。ASan と同時には有効にできません。

# 第11部: フリーズ - 無限ループとデッドロック

クラッシュもせず、間違った結果も出ません。プログラムがただ **固まります**。デバッガーは自分からは止まってくれず、どこにブレークポイントを置けばよいかもわかりません。
このときは、固まったプログラムを **その瞬間丸ごと止めて**(すべて中断)、各スレッドがどこにいるかを見ます。

> **安全装置:** 第11部のラボは「ラボ作業スレッド」(デバッガーでは `lab-worker` として見える)で動き、メインスレッドが2秒のウォッチドッグで時間を計ります。時間を超えると `[FAIL] ... 応答なし (2000 ms 超過)` を出力して終了します(`labs.h` の `runWithWatchdog`)。
> **デバッガーをアタッチして実行するとウォッチドッグは無効になります。** コンソールに案内が出るので、止まった状態を思う存分観察し、デバッグを停止して終了してください。(デバッガーの検出は `src/platform` にあります。Windows と Linux、macOS に対応しています。)

# 第12部: パフォーマンス - 間違ってはいないが遅い

結果はすべて正しいです。それなのに **遅いのです。** デバッガーで一行ずつ追っても、どの行もまともに見えます。このときは「どの行が間違っているか」ではなく **「時間をどこに使っているか」** を問う道具、**プロファイラー** を使います。

> **判定は時間ではなく回数で行います。** PC ごとに速度が違うので、「100 ms 以下」のような基準は当てにならないからです。各ラボは要素の移動、コピー、割り当てバイト数、flush のような **仕事の量** を数えて判定し、時間は参考として出力するだけです。そのため第12部は Debug、Release、ASan の **どの構成で採点しても結果が同じです。**
> **プロファイリングは Release で行ってください。** Debug は最適化がオフで検査コードも多いので、見当違いの場所が遅く見えます。このリポジトリで測った例では、キャッシュに逆らう走査は Release では数十倍遅くなりましたが、Debug では 2 倍にも届きませんでした。逆に Debug でだけ大きく見えるコスト(イテレーターの検査、インライン化されない小さな関数)もあります。

## プロファイラーの使い方

CPU サンプリング プロファイラーは、プログラムをデバッガーなしで動かしながら「今どの関数を実行中か」をごく頻繁に記録し、関数ごとに時間を集計します。ツールによって画面は違いますが、見るものは同じです。

| ツール | 始め方 |
|---|---|
| Visual Studio パフォーマンス プロファイラー | 構成を **Release** に → デバッグ → パフォーマンス プロファイラー (Alt+F2) → **CPU 使用率** → 開始 |
| Linux `perf` | `perf record -g ./bin/Release/BugHunt 93` → `perf report` |
| macOS Instruments | Instruments → **Time Profiler** → 対象に `bin/Release/BugHunt`、引数 `93` → 記録 |
| その他 | Windows の Intel VTune・AMD uProf、クロスプラットフォームの `samply`、Valgrind の `callgrind`(遅いが正確な呼び出し回数)など |

| 見るもの | 意味 |
|---|---|
| ホット パス (hot path) | 時間がいちばん多く流れる呼び出し経路。いちばん下が実際に仕事をしている関数 (VS: 「ホット パス」、perf: `perf report` のコールグラフ) |
| 合計 / 自己時間 (Total / Self、perf では Children / Self) | 合計 = その関数とその関数が呼んだものすべて、自己 = その関数の本体だけ。自己が大きい関数が犯人、合計が大きい自分の関数が犯人を呼んだ場所 |
| 呼び出し元 / 呼び出し先 | その関数を誰が呼び、その関数が誰を呼んだか。ソース行ごとの時間(VS: 関数をダブルクリック、perf: `perf annotate`) |
| サイズを 2 倍に | ラボの個数の定数を 2 倍に変えて実行。時間や回数が 2 倍なら O(n)、4 倍なら O(n²)。どちらかが最初の手がかり |

> Visual Studio には、デバッグしながら 2 つのブレークポイントの間だけをプロファイリングする「診断ツール」ウィンドウもあります。Debug でも使えますが、上の注意のとおり Debug の時間は信用しにくいです。

> 第12部のラボは 1 秒もかからずに終わるので、プロファイラーに取れるサンプルが少ないことがあります。そのときはラボの個数の定数を何倍かに増やして実行してください(採点は元の値で行います)。

```
記録表 (第12部用)
サイズを 2 倍にしたとき (時間 / 数える値):   
ホット パスのいちばん下の関数 (自己 CPU が大きいもの):  
その関数を呼んだ自分のコードの行:            
その行の仕事量が大きくなる理由:       
修正:                                 
修正後の数える値:                       
```

## やってみよう: ラボ93 (チャットキュー)

1. `93` で実行します。`メッセージ 8000件 処理: ... ms、要素の移動 31996000回` と `[FAIL]` が出ます。メッセージは 8000 件なのに、移動は 3 千万回です。
2. `pf01_chat_queue.cpp` の `kMessages` を 16000 に変えて、もう一度実行してみます。移動回数は約 4 倍になります。→ *O(n²)*。確認したら 8000 に戻します。
3. **Release** でビルドし、引数 `93` でプロファイラーを実行します。ラボが終わるとレポートが開きます。
4. ホット パスを展開します。`perf1::ChatQueue::drain` の下に `vector::erase`、その下の `Message` のムーブ代入(または `memmove`)が時間の大半を占めています。(Release は小さな関数をインライン化するので、`drain` 自体の「自己時間」が大きく出ることもあります。) → *ホット パスのいちばん下の関数*
5. `drain` のソース行ごとの時間を見ます。`queue_.erase(queue_.begin());` の行がほぼすべてです。→ *その関数を呼んだ行*
6. vector の先頭を消すと、後ろの要素がすべて 1 つずつ前に詰められます。残りの要素が n 個なら n 回移動し、これを n 回繰り返します。
7. 直したら再びプロファイリングしてホット パスがどう変わったかを見て、Debug で `[PASS]` を確認します。


## 判定方法

- ラボごとに `BugHunt` を **子プロセスとして別々に** 起動します(`--grade-child N`)。1 つのラボが落ちたり止まったりしても、他のラボや採点スクリプトは影響を受けません。採点中はアサーションやエラー報告のダイアログは表示されず、すぐに終了します。
- 判定は子プロセスの **終了コードと時間** だけで行います。

| 結果 | 条件 |
|---|---|
| PASS | 終了コード 0 (すべての検査が `[PASS]`)。隠しケースがあればそれも 0 |
| FAIL | 終了コード 10 (`[FAIL]` が 1 つ以上) |
| TIMEOUT | 終了コード 11 (ウォッチドッグの 2 秒超過)、または採点スクリプトのラボごとの制限 15 秒超過 |
| CRASH | それ以外の終了コードやシグナル。処理されない例外、`abort()`(BugHunt メモリチェッカーの `[CRASH] メモリ検査: ...` を含む)、ASan エラー、不正なアドレスへのアクセス、スタックオーバーフローなど。下の [クラッシュコード](#クラッシュコード) の表を参照 |

- **隠しケース:** 第3〜12部のラボとチャレンジは、通常の実行が合格すると **画面に出ない別のデータでもう一度** 実行します(`--grade-child N --hidden`)。結果をハードコードして `[PASS]` にしたり、見えているデータでだけ正しくなる中途半端な修正(例: ラボ 88 を `t < cooldownSeconds` だけに直す)は、ここで引っかかります。このとき結果は FAIL で、説明は `症状は消えたが原因が残っている (隠しケース)` で始まります。チャレンジにはすべて隠しケースがあります。隠しテストは各ラボファイルのいちばん下の `採点用の隠しテスト` region にあります。ソースなので開いて見ることはできますが、解くのには必要なく、書き換えると採点の意味がなくなります。第1・2部はクラッシュそのものが症状なので、隠しケースはありません。
- 判定は標準 C++ で観測できる値(範囲検査の例外、インスタンス数、BugHunt メモリチェッカーなど)で行うので、構成やコンパイラーが違っても結果が同じになるようにしてあります。このリポジトリで MSVC 14.51 と Clang 22(Windows)の Debug、Release、ASan の 6 通りすべてで採点したところ、**バグのある状態はすべて 0/109、解答をすべて適用するとすべて 109/109** でした。失敗の種類は少し異なることがあります(例: Clang Release ではラボ 89 が TIMEOUT ではなく FAIL。第11部のラボ 89 の説明を参照)。
- 採点スクリプト自体の終了コードは、満点なら 0、そうでなければ 1 です。

## grade-report.json の形式 (BugHunt 4 エディション共通)

採点結果は機械で読める `grade-report.json` としても保存されます(UTF-8、採点スクリプトを実行したフォルダー、`.gitignore` に含まれる)。C#、Unreal、Unity 版も同じ形式を使います。

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 109,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "友達のプロフィール", "part": 1, "result": "CRASH", "ms": 16, "detail": "アクセス違反 (0xC0000005)" },
    { "id": 21, "title": "出席報酬", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| フィールド | 型 | 意味 |
|---|---|---|
| `edition` | 文字列 | どのエディションの結果か。このリポジトリは `"cpp"` |
| `version` | 整数 | この JSON 形式のバージョン。現在は `1`。フィールドの意味が変わったら上げる |
| `total` | 整数 | 採点したラボの数(= `labs` の長さ)。ラボを 1 つだけ採点したら 1 |
| `passed` | 整数 | `result` が `"PASS"` のラボの数 |
| `labs[].id` | 整数 | ラボ番号(メニュー番号)。チャレンジは整数を保つため、深い追跡 C-n = `100 + n`、ブラインド B-n = `200 + n` (例: C-1 = 101、B-3 = 203)。4 エディション共通 |
| `labs[].title` | 文字列 | ラボ名。チャレンジは `"チャレンジ C-1"` のように番号だけ (ブラインドは名前でもヒントを与えない) |
| `labs[].part` | 整数 | 部の番号。チャレンジは `0`。4 エディション共通 |
| `labs[].result` | 文字列 | `"PASS"`、`"FAIL"`、`"TIMEOUT"`、`"CRASH"`、`"SKIP"` のいずれか。このリポジトリは `"SKIP"` を出さない(エンジン版で GPU が必要なラボに使う) |
| `labs[].ms` | 整数 | かかった時間(ミリ秒)。隠しケースの実行時間を含む |
| `labs[].detail` | 文字列 | 失敗理由 1 行(最初の `[FAIL]` 行、クラッシュの種類と手がかりなど)。PASS なら空文字列。通常のデータは合格したが隠しケースで失敗した場合は `"症状は消えたが原因が残っている (隠しケース) "` で始まる |

## クラッシュコード

採点表の CRASH の説明や、デバッガーが止まった理由に出てくる値です。Windows では終了コード(例外コード)として、Linux・macOS ではシグナルとして出ます。デバッガーのキーは上の [デバッガー対応表](#デバッガー対応表) を見てください。

| 意味 | Windows | Linux / macOS |
|---|---|---|
| 不正なアドレスへのアクセス (nullptr、解放されたメモリなど) | `0xC0000005` アクセス違反 | `SIGSEGV` (macOS は `SIGBUS` のこともある) |
| スタックオーバーフロー (終わらない再帰、大きなローカル変数、深い再帰 × 大きなフレーム) | `0xC00000FD` | `SIGSEGV` |
| 整数を 0 で除算 (このリポジトリのラボにはない) | `0xC0000094` | `SIGFPE` |
| `abort()` (処理されない例外、アサーション、BugHunt メモリチェッカー) | 終了コード 3 (アサーションは `0xC0000420` のこともある) | `SIGABRT` |
| ランタイムが見つけたヒープ破損 (たいてい壊した場所よりかなり後で落ちる) | `0xC0000374` | `SIGABRT` (glibc の `free(): invalid pointer` など) |
| ASan エラー | 終了コード 1 | 終了コード 1 |

> BugHunt メモリチェッカーがメモリを埋める値(新しく確保したメモリ `0xA5`、解放されたメモリ `0xEE`、ブロック後ろの境界 `0xBD`)は、第2部の [ビルド構成と BugHunt メモリチェッカー](#ビルド構成と-bughunt-メモリチェッカー) にあります。コンパイラーごとに異なるデバッグ用の埋め値(MSVC の `0xCC`、`0xDD` など)も、その節のツール別の参考にあります。
