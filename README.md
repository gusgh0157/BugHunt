# BugHunt — C++ 버그 추적 실습

버그가 **일부러 심어진** 작은 게임 코드 모음입니다.

- **1부: 호출 스택 입문 (랩 1~8)**: 프로그램이 죽은 순간 **호출 스택**을 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 심화 (랩 9~20)**: 메모리 오류, 미초기화, 레이스 등 증상이 덜 친절한 버그들. 데이터 중단점, ASan 같은 도구를 씁니다.
- **3부: 흐름 추적 (랩 21~28)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 디버거가 알아서 멈춰 주지 않으므로, 직접 중단점을 걸고 처음부터 한 줄씩 따라갑니다.
- **4부: 포인터 오용 (랩 29~34)**: 같은 포인터 버그가 Debug, Release, ASan에서 각각 어떻게 다르게 보이는지 비교하며 추적합니다.
- **5부: 멈춤 (랩 35~39)**: 크래시도 오답도 없이 프로그램이 **굳는** 무한루프와 데드락. 모두 중단, 스레드 창, 병렬 스택으로 멈춘 곳을 찾습니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1·2부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 3부는 **직접 멈춘 곳에서부터 값을 확인하며**, 4부는 **세 구성에서 실행해 증상을 비교하며**, 5부는 **굳은 순간 모두 중단으로 멈춰 세운 곳에서부터** 추적하세요. 다 고쳤으면 `grade.bat`으로 채점합니다.

# 1부: 호출 스택 입문

## 호출 스택이 뭔가요?

함수가 함수를 부르면, 컴퓨터는 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.

```
printPlayer        ← 맨 위: 지금 실행 중인 함수 (여기서 죽었다)
showProfile        ← printPlayer를 부른 함수
openFriendList     ← showProfile을 부른 함수
cs01_profile
main               ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

## 호출 스택 창 사용법

| 하고 싶은 것 | 방법 |
|---|---|
| 호출 스택 창 열기 | 디버깅 중 **Ctrl+Alt+C** (또는 메뉴 디버그 → 창 → 호출 스택) |
| 지역 변수 창 열기 | **Alt+4** (디버그 → 창 → 지역) |
| 다른 프레임으로 이동 | 호출 스택 창에서 줄을 **더블클릭** → 코드 창이 그 함수의 "호출한 줄"로 이동하고, 지역 창이 **그 함수의 변수**로 바뀜 |
| 숨겨진 STL/시스템 함수 보기 | 호출 스택 창 우클릭 → **외부 코드 표시** |

호출 스택 창의 한 줄은 이렇게 생겼습니다.

```
BugHunt.exe!lab1::showProfile(const std::string & name) 줄 40
└ 모듈 ┘  └ 네임스페이스::함수 ┘ └── 매개변수 ──┘     └ 소스 줄 ┘
```

- **노란 화살표**: 지금 멈춘 곳 (맨 위 프레임)
- **초록 화살표**: 다른 프레임을 더블클릭했을 때, "여기서 위 함수를 불렀다"는 위치
- **[외부 코드]**: STL, Windows 등 내 코드가 아닌 부분. 대부분 건너뛰고 **내 코드가 처음 나오는 줄**부터 보면 됩니다.

## 디버거가 멈추는 세 가지 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| "예외가 발생함: 읽기 액세스 위반" 같은 팝업 | 잘못된 포인터 등. 그 줄에서 바로 멈춤 | 호출 스택 창 열기 |
| **Debug Assertion Failed!** 창 | STL 등이 "이건 잘못됐어"라고 검사에 걸림 | **다시 시도(Retry)** 클릭 → (중단점 메시지가 나오면 "중단") → 호출 스택 창 열기 |
| "처리되지 않은 예외" / abort() | `throw`된 예외를 아무도 안 잡음 | 디버거가 throw 지점에서 멈춤 → 호출 스택 창 |

## 추적 4단계 (모든 랩 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 그 프레임의 지역 창에서 이상한 값(nullptr, 0, 엄청 큰 수, 음수...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다. 호출 스택은 "잘못한 곳"으로 거슬러 올라가는 길입니다.

각 랩을 풀 때 아래 기록표를 채워 보세요.

```
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

# 3부: 흐름 추적 (크래시 없음)

1·2부에서는 프로그램이 죽어 주었습니다. 디버거가 "여기야"라고 멈춰 주니 호출 스택을 거슬러 올라가기만 하면 됐죠.
실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **숫자 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 3부는 반드시 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되어 사용할 수 없음"으로 보입니다.

## 흐름 추적 4단계 (3부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `streak`는 2여야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다. 기대가 없으면 틀린 값을 봐도 지나친다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** 프로그램 맨 처음이 아니라, [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** F10으로 넘기며 값을 확인한다. 달라진 줄이 함수 호출이면 그 함수 안으로(F11) 들어가 같은 일을 반복한다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤에 나오는 틀린 값들은 대부분 그 결과일 뿐이다.

```
기록표 (3부용)
틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

## 3부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 중단점 + 한 줄씩 실행 | F9, F10 | 기본. 값이 줄마다 어떻게 변하는지 볼 때 |
| 함수 안으로 / 밖으로 | F11 / Shift+F11 | 의심 가는 함수 호출이 있을 때. 나오면 **자동 창**에 `함수명 반환` 값이 보임 |
| 커서까지 실행 | 원하는 줄에서 우클릭 → 커서까지 실행 (Ctrl+F10) | 중단점 없이 "여기까지만 가 줘" |
| 조건부 중단점 | 빨간 원 우클릭 → **조건** (예: `tick == 148`, `c.name == "Selene"`) | 반복이 수백 번인데 그중 한 번만 이상할 때 |

# 4부: 포인터 오용

2부에서 nullptr, vector 참조 무효화, string_view 댕글링, erase 뒤의 이터레이터, 이중 해제, 가상 소멸자, 구조체 버퍼 넘침을 다뤘습니다. 4부는 그 밖의 포인터 실수입니다.
4부의 핵심은 **같은 버그가 빌드 구성마다 다르게 보인다**는 것입니다. 각 랩을 **Debug → Release → ASan** 순서로 실행해 보고 무엇이 달라지는지 비교하세요. (구성은 도구 모음의 구성 목록에서 바꾸거나 `build.bat Release`처럼 빌드합니다.)

## 구성마다 다르게 보이는 이유

| 구성 | 메모리에 하는 일 | 그래서 포인터 버그는 |
|---|---|---|
| Debug | `/RTC1`이 지역 변수 자리를 `0xCC`로, 디버그 힙이 새 메모리를 `0xCD`, 해제한 메모리를 `0xDD`, 블록 앞뒤 경계를 `0xFD`로 채운다. `delete`할 때 힙 검사도 한다 | 쓰레기 값이 **알아볼 수 있는 쓰레기**(매직 넘버)가 된다. 힙을 망가뜨리면 그 자리에서 어설션 |
| Release | 아무것도 채우지 않는다. 최적화로 변수 위치도 바뀐다 | 해제된 메모리에 옛 값이 그대로 남아 **우연히 맞게** 동작하기도 하고, 한참 뒤 엉뚱한 곳에서 죽기도 한다 |
| ASan | 할당마다 앞뒤에 "레드존"을 두고, 해제한 메모리를 한동안 격리한다 | 잘못 읽고 쓰는 **바로 그 줄**에서 멈추고, 읽은 곳/해제한 곳/할당한 곳의 호출 스택까지 보여 준다. 다만 기본 설정으로는 지역 변수 주소 반환, 초기화 안 된 값, 메모리 누수(Windows에는 누수 검사기가 없음)는 못 잡는다 |

# 5부: 멈춤 - 무한루프와 데드락

크래시도 없고 틀린 결과도 나오지 않습니다. 프로그램이 그냥 **굳습니다**. 디버거는 알아서 멈춰 주지 않고, 중단점을 어디에 걸어야 할지도 모릅니다.
이때는 굳은 프로그램을 **그 순간 통째로 멈춰 세우고**(모두 중단), 각 스레드가 어디에 있는지 봅니다.

> **안전장치:** 5부 랩은 "랩 작업 스레드"에서 돌고, 메인 스레드가 2초 감시 타이머를 잽니다. 시간을 넘기면 `[FAIL] ... 응답 없음 (2000 ms 초과)`를 출력하고 끝납니다(`labs.h`의 `runWithWatchdog`).
> **F5(디버거 연결)로 실행하면 감시 타이머가 꺼집니다.** 콘솔에 안내가 나오니, 멈춘 상태를 마음껏 관찰하고 Shift+F5로 끝내세요.

## 멈춤을 추적하는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 모두 중단 | 디버그 → 모두 중단 (**Ctrl+Alt+Break**, 도구 모음의 ⏸) | 굳은 프로그램을 그 순간 그대로 멈춰 세울 때 |
| 스레드 창 | 디버그 → 창 → 스레드 (**Ctrl+Alt+H**), 줄을 더블클릭하면 그 스레드로 전환 | 모두 중단 직후 노란 화살표가 기다리기만 하는 메인 스레드에 있을 때, "랩 작업 스레드"로 바꾸기 |
| 병렬 스택 | 디버그 → 창 → 병렬 스택 (**Ctrl+Shift+D, S**) | 모든 스레드의 호출 스택을 한 그림으로. 데드락에서 누가 어디서 기다리는지 한눈에 |

4. 지역 창에서 `cooldownSeconds`, `t`, `ticks`를 봅니다. F5를 누르고 다시 Ctrl+Alt+Break 하면 `ticks`가 계속 커져 있습니다. → *무한루프*
5. **기대를 적습니다.** `t`는 0.1, 0.2, ...로 커지다가 15번째에 1.5가 되어 반복이 끝나야 합니다. Shift+F5로 멈추고, `++ticks;` 줄에 중단점을 건 뒤 **조건** `ticks == 15`를 넣고 F5. 멈추면 지역 창의 `t`는 정확히 1.5인가요? 조사식에 `t - cooldownSeconds`를 넣어 보세요.
6. (탈출 연습) 노란 화살표를 끌어 `return ticks;` 줄에 놓고 F5. 루프를 빠져나와 랩이 끝까지 진행됩니다. 다음 문 설정은 "이 루프만 빠져나오면 나머지는 맞는가?"를 확인하는 도구일 뿐, 코드는 그대로 틀려 있습니다.
7. 원인을 고치고 F5와 Ctrl+F5 모두에서 `[PASS]` 두 개를 확인합니다.

# 채점

다 고쳤다고 생각되면 채점기로 확인하세요. 저장소 폴더에서 실행합니다.

```bash
grade.bat
```

- `grade.bat` = `grade.bat Debug`: Debug로 빌드한 뒤 랩 39개를 모두 채점합니다. `grade.bat Release`, `grade.bat ASan`도 됩니다.
- `grade.bat Debug 30`: 랩 30만 채점합니다.
- 이미 빌드했다면 `bin\Debug\BugHunt.exe --grade` (또는 `--grade 30`)로 바로 실행해도 됩니다.

```
   #  부  결과       시간  랩
   1  1부  CRASH       16 ms  친구 프로필
                              └ 액세스 위반 (0xC0000005)
  21  3부  PASS        31 ms  출석 보상
  35  5부  TIMEOUT   2020 ms  스킬 쿨다운
                              └ [FAIL] 쿨다운 계산  응답 없음 (2000 ms 초과)
...
총점: 23/39
결과 파일: grade-report.json
```

## 판정 방법

- 랩마다 `BugHunt.exe`를 **자식 프로세스로 따로** 띄웁니다(`--grade-child N`). 한 랩이 죽거나 멈춰도 다른 랩과 채점기는 영향을 받지 않습니다. 채점 중에는 어설션 창이나 "응답 없음" 창이 뜨지 않고 바로 종료됩니다.
- 판정은 자식 프로세스의 **종료 코드와 시간**으로만 합니다.

| 결과 | 조건 |
|---|---|
| PASS | 종료 코드 0 (모든 검사가 `[PASS]`). 숨은 케이스가 있으면 그것도 0 |
| FAIL | 종료 코드 10 (`[FAIL]`이 하나 이상) |
| TIMEOUT | 종료 코드 11 (5부 감시 타이머 2초 초과), 또는 채점기의 랩당 제한 15초 초과 |
| CRASH | 그 밖의 종료 코드. 액세스 위반 `0xC0000005`, 스택 오버플로 `0xC00000FD`, Debug 어설션 `0xC0000420`, 힙 손상 `0xC0000374`, `abort()` 3, ASan 오류 1 등 |

- **숨은 케이스:** 3·4·5부 랩은 평소 실행이 통과하면 **화면에 나오지 않는 다른 데이터로 한 번 더** 실행합니다(`--grade-child N --hidden`). 결과를 하드코딩해서 `[PASS]`를 만들거나, 보이는 데이터에서만 맞는 반쪽짜리 수정(예: 랩 35를 `t < cooldownSeconds`로만 고치기)은 여기서 걸립니다. 숨은 테스트는 각 랩 파일 맨 아래 `채점용 숨은 테스트` region에 있습니다. 소스라서 열어 볼 수는 있지만 풀이에는 필요 없고, 고치면 채점이 의미가 없어집니다. 1·2부는 크래시 자체가 증상이라 숨은 케이스가 없습니다.
- 채점은 **Debug 기준**으로 만들었습니다. 버그 상태 그대로 채점하면 Debug와 ASan은 0/39이지만, Release는 몇 랩이 우연히 PASS로 나옵니다(이 저장소에서 확인했을 때 랩 8, 11, 16, 30, 33. 범위 검사가 없고, 누수 측정은 Debug에서만 하고, 해제된 메모리에 옛 값이 남아 있기 때문). 정답을 모두 적용하면 세 구성 모두 39/39입니다.
- 채점기 자체의 종료 코드는 만점이면 0, 아니면 1입니다.

## grade-report.json 형식 (BugHunt 네 판 공통)

채점 결과는 기계가 읽을 수 있는 `grade-report.json`으로도 저장됩니다(UTF-8, 채점기를 실행한 폴더, `.gitignore`에 포함). C#, 언리얼, 유니티판도 같은 형식을 씁니다.

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 39,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "CRASH", "ms": 16, "detail": "액세스 위반 (0xC0000005)" },
    { "id": 21, "title": "출석 보상", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| 필드 | 타입 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 어느 판의 결과인지. 이 저장소는 `"cpp"` |
| `version` | 정수 | 이 JSON 형식의 버전. 지금은 `1`. 필드의 뜻이 바뀌면 올린다 |
| `total` | 정수 | 채점한 랩 수(= `labs` 길이). 랩 하나만 채점하면 1 |
| `passed` | 정수 | `result`가 `"PASS"`인 랩 수 |
| `labs[].id` | 정수 | 랩 번호(메뉴 번호) |
| `labs[].title` | 문자열 | 랩 이름 |
| `labs[].part` | 정수 | 부 번호 |
| `labs[].result` | 문자열 | `"PASS"`, `"FAIL"`, `"TIMEOUT"`, `"CRASH"` 중 하나 |
| `labs[].ms` | 정수 | 걸린 시간(밀리초). 숨은 케이스 실행 시간 포함 |
| `labs[].detail` | 문자열 | 실패 이유 한 줄(첫 `[FAIL]` 줄, 크래시 종류와 단서 등). PASS면 빈 문자열. 숨은 케이스에서 실패하면 `"숨은 케이스: "`로 시작 |

## 알아두면 좋은 매직 넘버 (MSVC Debug)

| 값 | 의미 |
|---|---|
| `0x0000000000000000` | nullptr |
| `0xCCCCCCCC` (-858993460) | 초기화 안 된 **스택** 메모리 |
| `0xCDCDCDCD` | `new`로 받았지만 아직 아무것도 안 쓴 **힙** 메모리 |
| `0xDDDDDDDD` | 이미 `delete`된 힙 메모리 |
| `0xFDFDFDFD` | 디버그 힙 블록 앞뒤의 경계(no man's land). 여기를 읽거나 쓰면 범위 밖 접근 |
| `0xC0000005` | Access violation (잘못된 주소 접근) |
| `0xC0000094` | 정수를 0으로 나눔 |
| `0xC00000FD` | Stack overflow |
| `0xC0000374` | Heap corruption (힙이 망가짐. 보통 망가뜨린 곳보다 한참 뒤에 터진다) |
