# BugHunt — C++ 버그 추적 실습

버그가 **일부러 심어진** 작은 게임 코드 모음입니다.

- **1부: 호출 스택 입문 (랩 1~8)**: 프로그램이 죽은 순간 **호출 스택**을 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 심화 (랩 9~20)**: 메모리 오류, 미초기화, 레이스 등 증상이 덜 친절한 버그들. 데이터 중단점, ASan 같은 도구를 씁니다.
- **3부: 흐름 추적 (랩 21~28)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 디버거가 알아서 멈춰 주지 않으므로, 직접 중단점을 걸고 처음부터 한 줄씩 따라갑니다.
- **4부: 컨테이너 (랩 29~35)**: 표준 컨테이너와 알고리즘이 "규칙대로" 움직였는데 기대와 다른 경우. 연산 전후의 컨테이너를 펼쳐 비교합니다.
- **5부: 포인터 오용 (랩 36~42)**: 해제 후 사용, 초기화 안 된 포인터, `new[]`/`delete` 짝 틀림 같은 정의되지 않은 동작. 메모리 검사기와 ASan의 보고를 읽고 원인까지 거슬러 올라갑니다. 람다 캡처의 수명도 다룹니다.
- **비동기와 동시성 (랩 54~60, 번호는 임시)**: `std::async`와 `future`, `condition_variable`, `atomic`, 스레드 수명, 코루틴. 버그가 매번 똑같이 재현되도록 순서를 고정해 두었습니다. 스레드 목록, 모든 스레드의 호출 스택, 조건부 중단점으로 "어느 스레드가 언제"를 추적합니다.
- **6부: 멈춤 (랩 43~47)**: 크래시도 오답도 없이 프로그램이 **굳는** 무한루프와 데드락. 모두 중단(break all), 스레드 목록, 모든 스레드의 호출 스택으로 멈춘 곳을 찾습니다.
- **7부: 성능 (랩 48~53)**: 결과는 맞는데 **느린** 코드. 디버거 대신 **프로파일러**로 시간을 쓰는 곳을 찾습니다.
- **챌린지 (C-1~C-3, B-1~B-8)**: 다 끝낸 사람을 위한 힌트 없는 문제. 여러 단계를 거슬러 올라가는 깊은 추적과, 증상 한 줄만 주는 블라인드 문제입니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1·2부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 3·4부는 **직접 멈춘 곳에서부터 값을 확인하며**, 5부는 **검사기의 보고에서부터**, 6부는 **굳은 순간 모두 중단으로 멈춰 세운 곳에서부터**, 7부는 **프로파일러의 핫 경로에서부터** 추적하세요. 다 고쳤으면 `grade.bat`(Windows) 또는 `./grade.sh`로 채점합니다.
>
> 각 부가 어떤 버그 종류를 다루고 무엇이 빠져 있는지는 아래 [다루는 버그 한눈에 보기](#다루는-버그-한눈에-보기)에 있습니다.

**표준 C++판입니다.** 랩 코드는 ISO C++20만 씁니다(컴파일러 확장, `_s` 함수, 컴파일러별 `#ifdef` 없음). MSVC, Clang, GCC 중 어느 것으로 빌드해도 **같은 랩이 같은 이유로 FAIL**하고, 고치면 PASS해야 합니다. 크래시 모양(어떤 신호, 어떤 메시지)은 컴파일러와 운영체제마다 달라도 채점 결과는 같습니다. 콘솔 설정, 자식 프로세스, 감시 타이머처럼 운영체제마다 다른 코드는 `BugHunt/src/platform/` 한곳에 Windows용과 POSIX(Linux, macOS)용으로 나눠 두었습니다.

## 준비

C++20을 지원하는 컴파일러와 CMake 3.21 이상이 필요합니다. 빌드 구성은 `CMakePresets.json`의 세 프리셋입니다.

| 프리셋 | 출력 | 용도 |
|---|---|---|
| `debug` | `bin/Debug/` | 기본. 최적화 없음, 디버그 정보 |
| `release` | `bin/Release/` | 최적화 빌드. 7부 프로파일링, "Debug에선 되는데 Release에선 안 돼요" 체험 |
| `asan` | `bin/ASan/` | Debug + AddressSanitizer |

**명령줄** (Windows는 `build.bat`, 그 밖은 `./build.sh`가 아래를 대신해 줍니다)

```bash
cmake --preset debug
cmake --build --preset debug
```

- Windows: Visual Studio의 "x64 Native Tools 명령 프롬프트"에서 실행하거나 `build.bat Debug`를 쓰세요. `build.bat`은 Visual Studio를 찾아 개발자 환경(MSVC, CMake, Ninja)을 불러옵니다.
- Linux, macOS: `./build.sh Debug`. 컴파일러를 고르려면 `CXX=clang++ ./build.sh Debug`처럼 지정합니다(처음 구성할 때만 적용되므로 바꾸려면 `build/` 폴더를 지우세요).

**IDE**

- **Visual Studio**: "폴더 열기"로 저장소 폴더를 열면 프리셋을 읽어 구성 목록에 Debug, Release, ASan이 생깁니다. 시작 항목을 `BugHunt.exe`로 고르고 실행합니다. 예전처럼 `BugHunt.sln`(또는 `.slnx`)을 열어도 됩니다(Windows 전용 선택 사항).
- **VS Code**: CMake Tools 확장과 디버거 확장(C/C++의 `cppdbg` 또는 CodeLLDB)을 설치하고, 프리셋을 고른 뒤 빌드하고 디버그합니다. 랩 번호는 `launch.json`의 `args`(예: `["1"]`)로 넘깁니다.
- **gdb / lldb**: `gdb --args bin/Debug/BugHunt 1` 또는 `lldb -- bin/Debug/BugHunt 1`로 띄우고 `run`.

**실행**: 메뉴에서 랩 번호를 입력하거나, 인자로 번호를 넘깁니다(`BugHunt 1`, `BugHunt C-1`). 1·2부는 **반드시 디버거를 붙여서** 실행하세요. 디버거 없이 실행하면 프로그램은 죽기만 하고 호출 스택을 볼 수 없습니다.

> 이 저장소에서 직접 빌드하고 채점해 본 컴파일러는 Windows의 **MSVC 14.51**과 **Clang 22**(Visual Studio에 들어 있는 것, MSVC 표준 라이브러리 사용)입니다. GCC, libstdc++, libc++, Linux/macOS에서는 아직 확인하지 못했습니다.

# 1부: 호출 스택 입문

## 호출 스택이 뭔가요?

함수가 함수를 부르면, 컴퓨터는 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.

```
printPlayer        ← 맨 위: 지금 실행 중인 함수 (여기서 죽었다)
showProfile        ← printPlayer를 부른 함수
openFriendList     ← showProfile을 부른 함수
cs01_profile
main               ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

## 호출 스택 보는 법

| 하고 싶은 것 | 방법 (도구별 키는 [디버거 대응표](#디버거-대응표)) |
|---|---|
| 호출 스택 보기 | 디버거가 멈추면 호출 스택 창(패널)을 연다. gdb·lldb는 `bt` |
| 지역 변수 보기 | 지역 변수 창(패널). gdb는 `info locals`, lldb는 `frame variable` |
| 다른 프레임으로 이동 | 호출 스택에서 줄을 고른다 → 코드 창이 그 함수의 "호출한 줄"로 이동하고, 지역 변수가 **그 함수의 변수**로 바뀜 |
| 표준 라이브러리, 시스템 함수 | 내 코드가 아닌 프레임. 도구에 따라 접어서 보여 준다(Visual Studio의 `[외부 코드]`) |

호출 스택의 한 줄은 도구마다 모양이 조금 다르지만 담긴 정보는 같습니다.

```
Visual Studio:  BugHunt.exe!lab1::showProfile(const std::string & name) 줄 40
gdb / lldb:     #1  lab1::showProfile (name="Dorna") at cs01_profile.cpp:40
                    └ 네임스페이스::함수 ┘ └ 매개변수 ┘    └ 소스 파일:줄 ┘
```

- **현재 줄**: 지금 멈춘 곳 (맨 위 프레임). Visual Studio는 노란 화살표, gdb는 `=>`
- **호출한 줄**: 다른 프레임을 골랐을 때 "여기서 위 함수를 불렀다"는 위치. Visual Studio는 초록 화살표
- 표준 라이브러리나 운영체제 프레임은 대부분 건너뛰고 **내 코드가 처음 나오는 줄**부터 보면 됩니다.

## 디버거가 멈추는 세 가지 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| 잘못된 메모리 접근 (Windows: "액세스 위반", Linux/macOS: `SIGSEGV`) | 잘못된 포인터 등. 그 줄에서 바로 멈춤 | 호출 스택 보기 |
| 처리되지 않은 예외 (`std::out_of_range` 등) | `throw`된 예외를 아무도 안 잡음. 결국 `std::terminate` → `abort()` | 디버거가 throw 지점이나 `abort`에서 멈춤 → 호출 스택에서 내 코드 찾기. 던지는 순간 멈추게 하려면 "예외가 던져질 때 멈춤"을 켠다 |
| `abort()` + `[CRASH] ...` 메시지 | BugHunt 검사기(메모리 검사, 정렬 검사)나 표준 라이브러리의 디버그 검사가 잘못을 발견함 | 콘솔 메시지를 끝까지 읽고 → 호출 스택에서 내 코드 찾기 |

<details>
<summary>도구별 참고: Visual Studio의 어설션 창</summary>

MSVC Debug 구성의 표준 라이브러리는 범위 밖 `operator[]`, 무효가 된 이터레이터 같은 잘못을 **Debug Assertion Failed!** 창으로 알립니다. **다시 시도(Retry)** → (중단점 메시지가 나오면 "중단") → 호출 스택을 보면 됩니다. GCC의 libstdc++는 `-D_GLIBCXX_ASSERTIONS`, Clang의 libc++는 하드닝 모드로 비슷한 검사를 켤 수 있습니다. BugHunt의 랩은 이런 검사가 **있든 없든 같은 결과**가 나오도록 만들었습니다(1부의 범위 밖 접근은 `at()`을 쓰므로 어느 구성에서나 예외가 납니다).
</details>

## 추적 4단계 (모든 랩 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 그 프레임의 지역 변수에서 이상한 값(nullptr, 0, 엄청 큰 수, 음수...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다. 호출 스택은 "잘못한 곳"으로 거슬러 올라가는 길입니다.

각 랩을 풀 때 아래 기록표를 채워 보세요.

```
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

### 빌드 구성과 BugHunt 메모리 검사기

| 구성 | 용도 |
|---|---|
| Debug | 기본. 최적화가 없어 한 줄씩 따라가기 좋다 |
| Release | 최적화 빌드. 정의되지 않은 동작이 Debug와 **다른 모습**으로 나타나는 것을 체험할 때 |
| ASan | AddressSanitizer. 해제 후 사용, 범위 밖 접근, 이중 해제를 **그 줄에서** 잡고 읽은 곳/해제한 곳/할당한 곳의 호출 스택을 보여 준다 |

명령줄 빌드: `build.bat Debug` / `build.bat Release` / `build.bat ASan` (Linux, macOS는 `./build.sh`)

해제된 메모리를 읽거나 초기화하지 않은 값을 쓰는 것은 **정의되지 않은 동작**(undefined behavior)입니다. 표준은 결과를 정하지 않으므로, 아무 일 없이 맞는 값이 나올 수도 있고 컴파일러나 구성을 바꾸면 갑자기 틀릴 수도 있습니다. 그래서 채점 결과가 컴파일러에 따라 흔들리지 않도록, BugHunt는 표준이 허용하는 **전역 `operator new`/`delete` 교체**로 만든 작은 메모리 검사기(`src/support/heap_guard.cpp`)를 Debug와 Release에 넣었습니다. ASan 구성에서는 ASan이 같은 일을 더 정확하게 하므로 검사기를 끕니다.

| 검사기가 하는 일 | 그래서 |
|---|---|
| 새로 할당한 메모리를 `0xA5`로 채운다 | 초기화하지 않은 값을 읽으면 `0xA5A5A5A5`(-1515870811) 같은 **알아볼 수 있는 쓰레기**가 나온다 |
| 해제한 메모리를 `0xEE`로 덮고 한동안 다시 쓰지 않는다 | 해제 후 사용이 **우연히 맞는 값**을 읽지 못한다. `0xEEEEEEEE`(-286331154)가 보이면 해제된 메모리 |
| 블록 바로 뒤 16바이트를 `0xBD`로 채우고 해제할 때 확인한다 | 할당 크기를 넘어 쓰면 `[CRASH] 메모리 검사: ... 버퍼 오버런` |
| 이중 해제, `new[]`/`delete` 짝 틀림, `new`로 받지 않은 주소 해제 | `[CRASH] 메모리 검사: ...` 메시지 후 `abort()` |

이 값들은 BugHunt가 정한 것이라 어느 컴파일러에서나 같습니다. 진짜 프로그램에는 이런 검사기가 없다는 것을 기억하세요. 검사기 없이 같은 버그는 "실행할 때마다, 컴파일러마다 다르게" 보입니다.

<details>
<summary>도구별 참고: MSVC Debug의 <code>/RTC1</code>, CRT 디버그 힙, 매직 넘버</summary>

MSVC의 Debug 구성은 자체적으로 메모리를 채웁니다. Visual Studio에서 BugHunt를 디버깅하다 이 값들을 볼 수도 있습니다(검사기가 덮어쓰기 전, 스택 변수 등).

| 값 | 의미 |
|---|---|
| `0xCCCCCCCC` (-858993460) | `/RTC1`이 채운 초기화 안 된 **스택** 메모리 |
| `0xCDCDCDCD` | CRT 디버그 힙: `new`로 받았지만 아직 아무것도 안 쓴 **힙** 메모리 |
| `0xDDDDDDDD` | CRT 디버그 힙: 이미 해제된 힙 메모리 |
| `0xFDFDFDFD` | CRT 디버그 힙: 블록 앞뒤의 경계(no man's land) |

`/RTC1`은 MSVC 전용 런타임 검사이고(CMake의 MSVC Debug 기본값), GCC·Clang에는 같은 것이 없습니다. 초기화 안 된 값은 GCC·Clang의 `-ftrivial-auto-var-init=pattern`, MemorySanitizer(Clang, Linux), Valgrind 같은 도구로 찾습니다. 코드 분석 경고(MSVC C26495 "멤버를 초기화하지 않음" 등)도 단서가 됩니다.
</details>

# 3부: 흐름 추적 (크래시 없음)

1·2부에서는 프로그램이 죽어 주었습니다. 디버거가 "여기야"라고 멈춰 주니 호출 스택을 거슬러 올라가기만 하면 됐죠.
실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **숫자 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 3부는 반드시 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되어 사용할 수 없음"(gdb: `<optimized out>`)으로 보입니다.

## 흐름 추적 4단계 (3부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `streak`는 2여야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다. 기대가 없으면 틀린 값을 봐도 지나친다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** 프로그램 맨 처음이 아니라, [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** 한 줄씩 실행(step over)하며 값을 확인한다. 달라진 줄이 함수 호출이면 그 함수 안으로(step into) 들어가 같은 일을 반복한다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤에 나오는 틀린 값들은 대부분 그 결과일 뿐이다.

```
기록표 (3부용)
틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

## 3부에서 쓰는 도구

도구별 키와 명령은 [디버거 대응표](#디버거-대응표)에 있습니다.

| 동작 | 언제 |
|---|---|
| 중단점 + 한 줄씩 실행(step over) | 기본. 값이 줄마다 어떻게 변하는지 볼 때 |
| 함수 안으로(step into) / 밖으로(step out) | 의심 가는 함수 호출이 있을 때. 밖으로 나오면 디버거가 방금 돌아온 값을 보여 준다(Visual Studio: 자동 창의 `함수명 반환`, gdb: `finish`의 `Value returned`) |
| 커서까지 실행 | 중단점 없이 "여기까지만 가 줘" (Visual Studio: Ctrl+F10, VS Code: Run to Cursor, gdb: `until 40`) |
| 조건부 중단점 (예: `tick == 148`, `c.name == "Selene"`) | 반복이 수백 번인데 그중 한 번만 이상할 때 |
| 적중 횟수 | "다섯 번째 호출에서만 멈춰" |
| 추적점 (logpoint, `dprintf`) | 멈추지 않고 **순서**와 값을 기록할 때. 결과는 디버거 출력에 찍힌다 |
| 조사식에 식 넣기 (`c.isVip()`, `&item`, `a.x - b.x`) | 조건문의 각 부분을 따로 계산해 볼 때, 두 객체가 같은지 주소로 비교할 때 |
| 특정 객체 따라가기 | 주소를 적어 두고 조사식에 `*(Item*)0x...`로 넣는다. Visual Studio는 "개체 ID 만들기"(`$1`)도 있다 |
| 실행 위치 옮기기 (다음 문 설정, `jump`) | 같은 코드를 다시 실행해 보거나 분기를 건너뛰어 가설을 시험할 때 (상태는 되돌아가지 않음에 주의) |

   → 크래시가 없으니 호출 스택은 쓸모가 없습니다. 직접 멈춰야 합니다.
2. **기대를 적습니다.** 출석 기록은 `1111111011`. 루프를 돌 때 `streak`는 `1, 2, 3, 4, 5, 6, 7, 0, 1, 2`가 되어야 합니다.
3. `ft01_attendance.cpp`의 `calculateRewards`에서 `for (bool loggedIn : loginLog)` 줄에 **중단점**을 겁니다.
4. 다시 실행합니다. 그 줄에서 멈춥니다. 지역 변수를 봅니다.
5. **한 줄씩 실행**하며 `streak`와 `result.bestStreak`만 봅니다. (IDE는 값이 바뀐 줄을 다른 색으로 표시합니다. gdb는 `display streak`를 걸어 두면 멈출 때마다 보여 줍니다.)

# 4부: 컨테이너

1·2부에서 범위 밖 인덱스(랩 2, 9), 빈 컨테이너(랩 4), `map::at`(랩 6), vector 재할당(랩 10), `erase` 뒤의 이터레이터(랩 13)를 다뤘습니다. 4부는 그 밖의 표준 컨테이너와 알고리즘의 함정입니다.
대부분 **크래시가 없습니다.** 컨테이너가 "규칙대로" 움직였을 뿐인데 내가 기대한 것과 다를 때가 많습니다. 그래서 디버거의 **컨테이너 시각화**(지역 변수에서 펼치면 크기, 원소가 보임)로 **연산 전과 후**를 비교하는 것이 기본 도구입니다.

| 동작 | 하는 법 | 언제 |
|---|---|---|
| 컨테이너 펼쳐 보기 | 지역 변수/조사식에서 펼치기. Visual Studio는 `[Raw View]`, gdb는 `print /r`로 실제 멤버를 볼 수 있다 (gdb·lldb는 표준 라이브러리 pretty printer가 있어야 보기 좋게 나온다) | 크기, 순서, 원소가 연산 전후로 어떻게 바뀌었는지 |
| 조사식에서 함수 호출 | `bag.size()`, `board.bucket_count()`, `bag.count("Rope")` | 상태를 한 값으로 요약해서 비교할 때. (최적화로 인라인된 함수는 부를 수 없을 때가 있다) |
| 타입 보기 | 지역 변수의 타입 열, gdb `ptype wasOpen`, lldb `frame variable -T wasOpen` | `auto`가 실제로 무슨 타입이 되었는지 (랩 33) |
| 컴파일러 경고 | 빌드 출력 | `[[nodiscard]]` 반환값을 버렸을 때 (랩 32) |

# 5부: 포인터 오용

2부에서 nullptr, vector 참조 무효화, string_view 댕글링, erase 뒤의 이터레이터, 이중 해제, 가상 소멸자, 구조체 버퍼 넘침을 다뤘습니다. 5부는 그 밖의 포인터 실수입니다.
5부의 버그는 모두 **정의되지 않은 동작**입니다. 수명이 끝난 메모리를 읽고, 초기화하지 않은 포인터를 따라가고, `new[]`로 만든 것을 `delete`로 지웁니다. 표준은 이때 무슨 일이 일어날지 정하지 않으므로, 진짜 프로그램에서는 컴파일러, 최적화, 운영체제, 심지어 실행할 때마다 증상이 달라집니다. "Release에서는 되는데요"는 버그가 없다는 뜻이 아닙니다.

BugHunt는 채점이 흔들리지 않도록 Debug와 Release에 **메모리 검사기**를 넣었습니다([빌드 구성과 BugHunt 메모리 검사기](#빌드-구성과-bughunt-메모리-검사기)). 그래서 5부는 어느 컴파일러, 어느 구성에서나 같은 랩이 같은 이유로 실패합니다. ASan 구성에서는 검사기 대신 ASan이 보고합니다. 두 가지를 모두 실행해 보고 보고 내용을 비교하세요.

| 보고하는 것 | 하는 일 | 그래서 포인터 버그는 |
|---|---|---|
| 메모리 검사기 (Debug, Release) | 새 메모리를 `0xA5`, 해제한 메모리를 `0xEE`, 블록 뒤를 `0xBD`로 채우고, `delete`할 때 짝과 경계를 확인한다 | 쓰레기 값이 **알아볼 수 있는 쓰레기**가 된다. 잘못된 해제는 그 자리에서 `[CRASH] 메모리 검사: ...`. 다만 잘못 **읽는** 순간에는 멈추지 않는다 |
| ASan | 할당마다 앞뒤에 "레드존"을 두고, 해제한 메모리를 한동안 격리하고, 모든 읽기/쓰기를 검사한다 | 잘못 읽고 쓰는 **바로 그 줄**에서 멈추고, 읽은 곳/해제한 곳/할당한 곳의 호출 스택까지 보여 준다. 다만 기본 설정으로는 초기화 안 된 값, 스택 댕글링 일부, 메모리 누수(Windows에는 누수 검사기가 없음)는 못 잡는다 |

이 저장소에서 버그 상태로 실행해 본 결과입니다(Windows, MSVC 14.51과 Clang 22). Debug와 Release는 두 컴파일러 모두 같았습니다.

## 람다 캡처와 ASan (랩 42)

`[&]` 람다는 지역 변수의 **주소**를 들고 있습니다. 람다를 타이머나 콜백 목록에 맡기고 함수가 끝나면, 그 주소는 이미 끝난 함수의 스택입니다. 힙과 달리 스택은 "해제"라는 사건이 없고, 다음 함수 호출이 같은 자리를 바로 다시 씁니다.

버그 상태로 실행해 보면 틀린 값이 컴파일러와 구성마다 다릅니다(이 저장소에서 확인한 Kael의 공격력: MSVC Debug -124, MSVC·Clang Release 45, Clang Debug 85, ASan은 수억대 쓰레기 값). 스택 자리가 언제 다시 쓰이는지는 최적화와 스택 배치에 달려 있기 때문입니다. Release의 45는 람다가 읽은 `bonus` 자리에 나중에 분노를 쓴 Doran의 `bonus`(45)가 들어 있어서 나온 값입니다. 어느 경우든 기대한 60은 나오지 않습니다.

- ASan이 기본으로 못 잡는 이유: 기본 ASan은 함수가 끝난 뒤의 스택 자리를 "죽은 메모리"로 표시하지 않습니다. 이런 버그(stack-use-after-return)를 잡으려면 스택 프레임을 따로 떼어 두는 기능을 켜야 합니다.
- **Clang, GCC**: 실행할 때 환경 변수 `ASAN_OPTIONS=detect_stack_use_after_return=1`을 주면 켜집니다(버전에 따라 기본으로 켜져 있기도 합니다). 이 저장소에서 Windows의 Clang 22 ASan 빌드로 시험했을 때 랩 42 람다 줄에서 `stack-use-after-return`이 정확히 보고되었습니다.
- **MSVC**: 컴파일 옵션 `/fsanitize-address-use-after-return`이 필요하고, 리포트는 `stack-buffer-underflow`라는 이름으로 나옵니다. 이 저장소에서는 켜지 않았습니다. MSVC 14.51에서 프로젝트 전체에 켜 보면 프로그램 시작 시 전역 `std::string` 초기화에서 오탐이 나서 랩까지 가지 못했고, 이 파일에만 켜면 다른 파일과 공유하는 표준 라이브러리 코드에서 오탐이 났습니다(Debug, Release 런타임 모두). 같은 버그를 담은 작은 단독 프로그램에서는 잘 잡혔습니다.
- 그래서 이 랩의 주 도구는 디버거입니다. 람다 안에 중단점을 걸면 람다를 펼쳐 캡처한 것들을 볼 수 있고, 참조로 캡처한 변수의 주소가 **이미 끝난 함수의 스택**을 가리키는지 확인할 수 있습니다.

## ThreadSanitizer

ThreadSanitizer(TSan)는 두 스레드가 동기화 없이 같은 메모리에 접근하고 그중 하나가 쓰기일 때 그 줄에서 보고합니다. ASan처럼 컴파일 옵션으로 켭니다. ASan과 함께 켤 수는 없습니다.

```bash
cmake -S . -B build/tsan -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS=-fsanitize=thread -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread -DBUGHUNT_BIN_NAME=TSan
cmake --build build/tsan
./bin/TSan/BugHunt 17
```

- 랩 17(길드 금고)의 레이스는 `WARNING: ThreadSanitizer: data race`로 나옵니다. 랩 58은 데이터 레이스가 아닙니다(모든 접근이 `atomic`). TSan이 조용한데도 틀리는 버그가 있다는 것을 비교해 보세요.
- TSan이 보고하면 종료 코드가 바뀌어 채점에서는 CRASH로 나올 수 있습니다.

# 6부: 멈춤 - 무한루프와 데드락

크래시도 없고 틀린 결과도 나오지 않습니다. 프로그램이 그냥 **굳습니다**. 디버거는 알아서 멈춰 주지 않고, 중단점을 어디에 걸어야 할지도 모릅니다.
이때는 굳은 프로그램을 **그 순간 통째로 멈춰 세우고**(모두 중단), 각 스레드가 어디에 있는지 봅니다.

> **안전장치:** 6부 랩은 "랩 작업 스레드"(디버거에는 `lab-worker`로 보임)에서 돌고, 메인 스레드가 2초 감시 타이머를 잽니다. 시간을 넘기면 `[FAIL] ... 응답 없음 (2000 ms 초과)`를 출력하고 끝납니다(`labs.h`의 `runWithWatchdog`).
> **디버거를 붙여 실행하면 감시 타이머가 꺼집니다.** 콘솔에 안내가 나오니, 멈춘 상태를 마음껏 관찰하고 디버깅을 중지해서 끝내세요. (디버거 감지는 `src/platform`에 있습니다. Windows와 Linux, macOS를 지원합니다.)

# 7부: 성능 - 틀리지 않지만 느리다

결과는 모두 맞습니다. 그런데 **느립니다.** 디버거로 한 줄씩 따라가면 모든 줄이 멀쩡해 보입니다. 이때는 "어느 줄이 틀렸나"가 아니라 **"시간을 어디에 쓰나"**를 묻는 도구, **프로파일러**를 씁니다.

> **판정은 시간이 아니라 횟수로 합니다.** PC마다 속도가 달라서 "100 ms 이하" 같은 기준은 믿을 수 없기 때문입니다. 각 랩은 원소 이동, 복사, 할당 바이트, flush 같은 **일의 양**을 세어 판정하고, 시간은 참고로만 출력합니다. 그래서 7부는 Debug, Release, ASan **어느 구성으로 채점해도 결과가 같습니다.**
> **프로파일링은 Release로 하세요.** Debug는 최적화가 꺼져 있고 검사 코드가 많아서 엉뚱한 곳이 느려 보입니다. 이 저장소에서 잰 예로, 캐시를 거스르는 순회는 Release에서 수십 배 느렸지만 Debug에서는 2배도 안 됐습니다. 반대로 Debug에서만 크게 보이는 비용(반복자 검사, 인라인 안 된 작은 함수)도 있습니다.

## 프로파일러 사용법

CPU 샘플링 프로파일러는 프로그램을 디버거 없이 돌리면서 "지금 어느 함수를 실행 중인가"를 아주 자주 기록해, 함수별로 시간을 모읍니다. 도구마다 화면은 다르지만 보는 것은 같습니다.

| 도구 | 시작하는 법 |
|---|---|
| Visual Studio 성능 프로파일러 | 구성을 **Release**로 → 디버그 → 성능 프로파일러 (Alt+F2) → **CPU 사용량** → 시작 |
| Linux `perf` | `perf record -g ./bin/Release/BugHunt 48` → `perf report` |
| macOS Instruments | Instruments → **Time Profiler** → 대상에 `bin/Release/BugHunt`, 인자 `48` → 기록 |
| 그 밖 | Windows의 Intel VTune·AMD uProf, 크로스 플랫폼 `samply`, Valgrind의 `callgrind`(느리지만 정확한 호출 수) 등 |

| 보는 것 | 뜻 |
|---|---|
| 핫 경로 (hot path) | 시간이 가장 많이 흐르는 호출 경로. 맨 아래가 실제로 일하는 함수 (VS: "핫 경로", perf: `perf report`의 호출 그래프) |
| 총 / 자체 시간 (Total / Self, perf의 Children / Self) | 총 = 그 함수와 그 함수가 부른 것 전부, 자체 = 그 함수 몸통만. 자체가 큰 함수가 범인, 총이 큰 내 함수가 범인을 부른 곳 |
| 호출자 / 호출 수신자 | 그 함수를 누가 불렀고 그 함수가 누구를 불렀는지. 소스 줄별 시간(VS: 함수 더블클릭, perf: `perf annotate`) |
| 크기를 두 배로 | 랩의 개수 상수를 두 배로 바꿔 실행. 시간이나 횟수가 2배면 O(n), 4배면 O(n²). 어느 쪽인지가 첫 단서 |

> Visual Studio는 디버깅하면서 중단점 두 개 사이만 프로파일링하는 "진단 도구" 창도 있습니다. Debug에서도 쓸 수 있지만 위 주의대로 Debug의 시간은 믿기 어렵습니다.

> 7부 랩은 1초도 안 걸려 끝나서 프로파일러에 샘플이 적게 잡힐 수 있습니다. 그럴 때는 랩의 개수 상수를 몇 배로 늘려 실행하세요(채점은 원래 값으로 합니다).

```

그 함수를 부른 내 코드의 줄:            
그 줄이 하는 일의 양이 커지는 이유:

```

# 채점

다 고쳤다고 생각되면 채점기로 확인하세요. 저장소 폴더에서 실행합니다. Windows는 `grade.bat`, Linux·macOS는 `./grade.sh`이고 인자는 같습니다.

```bash
./grade.sh
```

- `grade.sh` = `grade.sh Debug`: Debug로 빌드한 뒤 랩 60개와 챌린지 11개를 모두 채점합니다. `Release`, `ASan`도 됩니다. 챌린지는 표 아래쪽 `챌린지` 구역에 따로 나오고, 총점 아래에 기본 랩과 챌린지 점수가 나뉘어 나옵니다.
- `grade.sh Debug 37`: 랩 37만 채점합니다. `grade.sh Debug C-1`처럼 챌린지 하나만 채점할 수도 있습니다.
- `grade.sh Debug labs`: 기본 랩 60개만, `grade.sh Debug challenges`: 챌린지 11개만 채점합니다.
- 이미 빌드했다면 `bin/Debug/BugHunt --grade`(Windows는 `bin\Debug\BugHunt.exe --grade`)로 바로 실행해도 됩니다. `--grade 37`, `--grade C-1`, `--grade challenges`도 됩니다. IDE에서 빌드했다면 그 실행 파일에 `--grade`를 주면 됩니다.

```
   #  부  결과       시간  랩
   1  1부  CRASH       16 ms  친구 프로필
                              └ 액세스 위반 (0xC0000005)
  21  3부  PASS        31 ms  출석 보상
  43  6부  TIMEOUT   2020 ms  스킬 쿨다운
                              └ [FAIL] 쿨다운 계산  응답 없음 (2000 ms 초과)
...
총점: 23/53
결과 파일: grade-report.json
```

## 판정 방법

- 랩마다 `BugHunt`를 **자식 프로세스로 따로** 띄웁니다(`--grade-child N`). 한 랩이 죽거나 멈춰도 다른 랩과 채점기는 영향을 받지 않습니다. 채점 중에는 어설션이나 오류 보고 대화상자가 뜨지 않고 바로 종료됩니다.
- 판정은 자식 프로세스의 **종료 코드와 시간**으로만 합니다.

| 결과 | 조건 |
|---|---|
| PASS | 종료 코드 0 (모든 검사가 `[PASS]`). 숨은 케이스가 있으면 그것도 0 |
| FAIL | 종료 코드 10 (`[FAIL]`이 하나 이상) |
| TIMEOUT | 종료 코드 11 (6부 감시 타이머 2초 초과), 또는 채점기의 랩당 제한 15초 초과 |
| CRASH | 그 밖의 종료 코드나 시그널. 처리되지 않은 예외, `abort()`(BugHunt 메모리 검사기의 `[CRASH] 메모리 검사: ...` 포함), ASan 오류, 잘못된 주소 접근, 스택 오버플로 등. 아래 [크래시 코드](#크래시-코드) 표 참고 |

- **숨은 케이스:** 3~7부 랩과 챌린지는 평소 실행이 통과하면 **화면에 나오지 않는 다른 데이터로 한 번 더** 실행합니다(`--grade-child N --hidden`). 결과를 하드코딩해서 `[PASS]`를 만들거나, 보이는 데이터에서만 맞는 반쪽짜리 수정(예: 랩 43을 `t < cooldownSeconds`로만 고치기)은 여기서 걸립니다. 이때 결과는 FAIL이고, 설명은 `증상은 사라졌지만 원인이 남아 있음 (숨은 케이스)`으로 시작합니다. 챌린지는 모두 숨은 케이스가 있습니다. 숨은 테스트는 각 랩 파일 맨 아래 `채점용 숨은 테스트` region에 있습니다. 소스라서 열어 볼 수는 있지만 풀이에는 필요 없고, 고치면 채점이 의미가 없어집니다. 1·2부는 크래시 자체가 증상이라 숨은 케이스가 없습니다.
- 판정은 표준 C++에서 관찰할 수 있는 값(범위 검사 예외, 인스턴스 수, BugHunt 메모리 검사기 등)으로 하므로 구성이나 컴파일러가 달라도 결과가 같게 만들었습니다. 이 저장소에서 MSVC 14.51과 Clang 22(Windows)로 Debug, Release, ASan 여섯 가지를 모두 채점해 보니 **버그 상태는 모두 0/71, 정답을 모두 적용하면 모두 71/71**였습니다. 실패의 종류는 조금 다를 수 있습니다(예: Clang Release에서 랩 44는 TIMEOUT 대신 FAIL. 6부 랩 44 설명 참고).
- 채점기 자체의 종료 코드는 만점이면 0, 아니면 1입니다.

## grade-report.json 형식 (BugHunt 네 판 공통)

채점 결과는 기계가 읽을 수 있는 `grade-report.json`으로도 저장됩니다(UTF-8, 채점기를 실행한 폴더, `.gitignore`에 포함). C#, 언리얼, 유니티판도 같은 형식을 씁니다.

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 53,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "CRASH", "ms": 16, "detail": "액세스 위반 (0xC0000005)" },
    { "id": 21, "title": "출석 보상", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| 필드 | 타입 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 어느 판의 결과인지. 이 저장소는 `"cpp"` |
| `version` | 정수 | 이 JSON 형식의 버전. 지금은 `1`. 필드의 뜻이 바뀌면 올린다 |
| `total` | 정수 | 채점한 랩 수(= `labs` 길이). 랩 하나만 채점하면 1 |
| `passed` | 정수 | `result`가 `"PASS"`인 랩 수 |
| `labs[].id` | 정수 | 랩 번호(메뉴 번호). 챌린지는 정수를 유지하려고 깊은 추적 C-n = `100 + n`, 블라인드 B-n = `200 + n` (예: C-1 = 101, B-3 = 203). 네 판 공통 |
| `labs[].title` | 문자열 | 랩 이름. 챌린지는 `"챌린지 C-1"`처럼 번호만 (블라인드는 이름으로도 힌트를 주지 않는다) |
| `labs[].part` | 정수 | 부 번호. 챌린지는 마지막 부 다음 번호(이 저장소는 `8`) |
| `labs[].result` | 문자열 | `"PASS"`, `"FAIL"`, `"TIMEOUT"`, `"CRASH"` 중 하나 |
| `labs[].ms` | 정수 | 걸린 시간(밀리초). 숨은 케이스 실행 시간 포함 |
| `labs[].detail` | 문자열 | 실패 이유 한 줄(첫 `[FAIL]` 줄, 크래시 종류와 단서 등). PASS면 빈 문자열. 평소 데이터는 통과했는데 숨은 케이스에서 실패하면 `"증상은 사라졌지만 원인이 남아 있음 (숨은 케이스) "`로 시작 |

## 크래시 코드

채점표의 CRASH 설명이나 디버거가 멈춘 이유에 나오는 값입니다. Windows에서는 종료 코드(예외 코드)로, Linux·macOS에서는 시그널로 나옵니다. 디버거 키는 위 [디버거 대응표](#디버거-대응표)를 보세요.

| 뜻 | Windows | Linux / macOS |
|---|---|---|
| 잘못된 주소 접근 (nullptr, 해제된 메모리 등) | `0xC0000005` 액세스 위반 | `SIGSEGV` (macOS는 `SIGBUS`일 때도 있음) |
| 스택 오버플로 (끝나지 않는 재귀) | `0xC00000FD` | `SIGSEGV` |
| 정수를 0으로 나눔 | `0xC0000094` | `SIGFPE` |
| `abort()` (처리되지 않은 예외, 어설션, BugHunt 메모리 검사기) | 종료 코드 3 (어설션은 `0xC0000420`일 때도 있음) | `SIGABRT` |
| 런타임이 발견한 힙 손상 (보통 망가뜨린 곳보다 한참 뒤에 터짐) | `0xC0000374` | `SIGABRT` (glibc의 `free(): invalid pointer` 등) |
| ASan 오류 | 종료 코드 1 | 종료 코드 1 |

> BugHunt 메모리 검사기가 메모리를 채우는 값(새로 받은 메모리 `0xA5`, 해제된 메모리 `0xEE`, 블록 뒤 경계 `0xBD`)은 2부의 [빌드 구성과 BugHunt 메모리 검사기](#빌드-구성과-bughunt-메모리-검사기)에 있습니다. 컴파일러마다 다른 디버그 채움 값(MSVC의 `0xCC`, `0xDD` 등)도 그 절의 도구별 참고에 있습니다.
