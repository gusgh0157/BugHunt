# BugHunt — C++ バグ追跡の実習

バグが **わざと仕込まれた** 小さなゲームコードの集まりです。

- **第1部: 呼び出し履歴入門 (ラボ1~8)**: プログラムが落ちた瞬間の **呼び出し履歴** をさかのぼって原因を探す練習。初心者はここから始めてください。
- **第2部: 応用 (ラボ9~20)**: メモリエラー、未初期化、データ競合など、症状があまり親切でないバグ。データ ブレークポイントや ASan のような道具を使います。
- **第3部: フロー追跡 (ラボ21~32)**: プログラムは **問題なく終わるのに結果が間違っている** バグ。デバッガーが勝手に止まってくれないので、自分でブレークポイントを置いて最初から1行ずつ追います。
  - **演算子のミス (ラボ29~32)**: 後置インクリメントの値、マクロ引数の二重評価、`&&` の代わりの `&`、`||` の代わりの `|`。第3部の最後に付くラボです。
- **第4部: コンテナ (ラボ33~39)**: 標準コンテナとアルゴリズムが「規則どおり」に動いたのに期待と違う場合。操作の前後でコンテナを展開して比べます。
- **第5部: C++ 言語の落とし穴 (ラボ40~48)**: `const` への `std::move`、符号付き整数のオーバーフロー、縮小変換、符号付き/符号なしの変換、グローバル初期化順序、ヘッダーの `static`、例外の経路での漏れ、デストラクターから投げる、範囲 for。コンパイラーが受け入れるコードに潜む言語規則を、ウォッチと警告で見つけます。
- **第6部: インターフェースと継承 (ラボ49~54)**: オーバーライドされていない仮想関数、スライシング、コンストラクター内の仮想呼び出し、デフォルト引数、オーバーロードの隠蔽、`dynamic_cast`。「見当違いの関数が呼ばれる」バグを、ステップ イン (Step Into) と実際の型の表示で追跡します。
- **第7部: ファイル入出力 (ラボ55~61)**: 作業ディレクトリ、バッファーと flush、`eof()` のループ、`getline`、failbit、BOM、半分だけ書かれたセーブ。ストリームの状態とディスク上の実際のバイトを一緒に見ます。
- **第8部: シリアライズ JSON/XML (ラボ62~68)**: nlohmann/json と pugixml を使うセーブ・ロードのコードの落とし穴。`third_party/` に固定バージョンで入っています。
- **第9部: ポインターの誤用 (ラボ69~80)**: 解放後の使用 (use-after-free)、初期化されていないポインター、`new[]`/`delete` の組み合わせ違いのような未定義動作。メモリチェッカーと ASan の報告を読み、原因までさかのぼります。ラムダキャプチャの寿命とスタック/ヒープのあふれ(ラボ76~80)も扱います。
- **第10部: 非同期と並行性 (ラボ81~87)**: `std::async` と `future`、`condition_variable`、`atomic`、スレッドの寿命、コルーチン。バグが毎回同じように再現するよう、順序を固定してあります。スレッド一覧、すべてのスレッドの呼び出し履歴、条件付きブレークポイントで「どのスレッドがいつ」を追跡します。
- **第11部: フリーズ (ラボ88~92)**: クラッシュも間違った答えもなく、プログラムが **固まる** 無限ループとデッドロック。すべて中断 (break all)、スレッド一覧、すべてのスレッドの呼び出し履歴で止まった場所を探します。
- **第12部: パフォーマンス (ラボ93~98)**: 結果は正しいのに **遅い** コード。デバッガーの代わりに **プロファイラー** で時間を使っている場所を探します。
- **チャレンジ (C-1~C-3、B-1~B-8)**: すべて終えた人のためのヒントなしの問題。何段階もさかのぼる深い追跡と、症状を1行だけ与えるブラインド問題です。

> コードを目で流し読みして答えを探さないでください。第1・2部は **実行して落とし、デバッガーが止まった場所から**、第3~8部は **自分で止めた場所から値を確かめながら**、第9部は **チェッカーの報告から**、第10部は **スレッド一覧とすべてのスレッドの呼び出し履歴から**、第11部は **固まった瞬間にすべて中断で止めた場所から**、第12部は **プロファイラーのホット パスから** 追跡してください。すべて直したら `grade.bat`(Windows)または `./grade.sh` で採点します。
>
> 各部がどの種類のバグを扱い、何が抜けているかは、下の [扱うバグの一覧](#扱うバグの一覧) にあります。

**標準 C++ 版です。** ラボのコードは ISO C++20 だけを使います(コンパイラー拡張、`_s` 関数、コンパイラーごとの `#ifdef` はなし)。MSVC、Clang、GCC のどれでビルドしても **同じラボが同じ理由で FAIL** し、直せば PASS するはずです。クラッシュの形(どのシグナル、どのメッセージ)はコンパイラーと OS ごとに違っても、採点結果は同じです。コンソール設定、子プロセス、ウォッチドッグのように OS ごとに異なるコードは、`BugHunt/src/platform/` の1か所に Windows 用と POSIX(Linux、macOS)用に分けてあります。

## 準備

C++20 に対応したコンパイラーと CMake 3.21 以上が必要です。ビルド構成は `CMakePresets.json` の3つのプリセットです。

| プリセット | 出力 | 用途 |
|---|---|---|
| `debug` | `bin/Debug/` | 既定。最適化なし、デバッグ情報あり |
| `release` | `bin/Release/` | 最適化ビルド。第12部のプロファイリング、「Debug では動くのに Release では動きません」の体験 |
| `asan` | `bin/ASan/` | Debug + AddressSanitizer |

**コマンドライン** (Windows は `build.bat`、それ以外は `./build.sh` が下記を代わりに実行します)

```bash
cmake --preset debug
cmake --build --preset debug
```

- Windows: Visual Studio の「x64 Native Tools コマンド プロンプト」で実行するか、`build.bat Debug` を使ってください。`build.bat` は Visual Studio を探して開発者環境(MSVC、CMake、Ninja)を読み込みます。
- Linux、macOS: `./build.sh Debug`。コンパイラーを選ぶには `CXX=clang++ ./build.sh Debug` のように指定します(最初の構成時にだけ適用されるので、変えるには `build/` フォルダーを削除してください)。

**IDE**

- **Visual Studio**: 「フォルダーを開く」でリポジトリのフォルダーを開くと、プリセットが読み込まれて構成の一覧に Debug、Release、ASan が現れます。スタートアップ項目に `BugHunt.exe` を選んで実行します。以前のように `BugHunt.sln`(または `.slnx`)を開いてもかまいません(Windows 専用の選択肢)。
- **VS Code**: CMake Tools 拡張機能とデバッガー拡張機能(C/C++ の `cppdbg` または CodeLLDB)をインストールし、プリセットを選んでからビルドしてデバッグします。ラボ番号は `launch.json` の `args`(例: `["1"]`)で渡します。
- **gdb / lldb**: `gdb --args bin/Debug/BugHunt 1` または `lldb -- bin/Debug/BugHunt 1` で起動して `run`。

**実行**: メニューでラボ番号を入力するか、引数で番号を渡します(`BugHunt 1`、`BugHunt C-1`)。第1・2部は **必ずデバッガーをアタッチして** 実行してください。デバッガーなしで実行すると、プログラムは落ちるだけで呼び出し履歴を見ることができません。

> このリポジトリで実際にビルドして採点を確認したコンパイラーは、Windows の **MSVC 14.51** と **Clang 22**(Visual Studio に同梱のもの、MSVC 標準ライブラリを使用)です。GCC、libstdc++、libc++、Linux/macOS ではまだ確認していません。

# 第1部: 呼び出し履歴入門

## 呼び出し履歴とは?

関数が関数を呼ぶと、コンピューターは「誰が自分を呼んだか」を順番に積み上げておきます。その山が **呼び出し履歴(コールスタック、Call Stack)** です。

```
printPlayer        ← いちばん上: 今実行中の関数 (ここで落ちた)
showProfile        ← printPlayer を呼んだ関数
openFriendList     ← showProfile を呼んだ関数
cs01_profile
main               ← いちばん下: プログラムの始まり
```

**上から下へ読めば「誰が自分を呼んだか」**、**下から上へ読めば「プログラムがどうやってここまで来たか」** です。

## 呼び出し履歴の見方

| やりたいこと | 方法 (道具ごとのキーは [デバッガー対応表](#デバッガー対応表)) |
|---|---|
| 呼び出し履歴を見る | デバッガーが止まったら呼び出し履歴 ウィンドウ(パネル)を開く。gdb・lldb は `bt` |
| ローカル変数を見る | ローカル ウィンドウ(パネル)。gdb は `info locals`、lldb は `frame variable` |
| 別のフレームへ移動 | 呼び出し履歴で行を選ぶ → コードウィンドウがその関数の「呼び出した行」へ移り、ローカル変数が **その関数の変数** に切り替わる |
| 標準ライブラリ、システム関数 | 自分のコードではないフレーム。道具によっては折りたたんで表示される(Visual Studio の `[外部コード]`) |

呼び出し履歴の1行は道具ごとに見た目が少し違いますが、含まれる情報は同じです。

```
Visual Studio:  BugHunt.exe!lab1::showProfile(const std::string & name) 行 40
gdb / lldb:     #1  lab1::showProfile (name="Dorna") at cs01_profile.cpp:40
                    └ 名前空間::関数 ┘ └ 引数 ┘    └ ソースファイル:行 ┘
```

- **現在の行**: 今止まっている場所 (いちばん上のフレーム)。Visual Studio は黄色い矢印、gdb は `=>`
- **呼び出した行**: 別のフレームを選んだときの「ここで上の関数を呼んだ」という位置。Visual Studio は緑の矢印
- 標準ライブラリや OS のフレームはたいてい飛ばして、**自分のコードが最初に出てくる行** から見れば十分です。

## デバッガーが止まる3つのパターン

| パターン | 意味 | やること |
|---|---|---|
| 不正なメモリアクセス (Windows: 「アクセス違反」、Linux/macOS: `SIGSEGV`) | 不正なポインターなど。その行ですぐ止まる | 呼び出し履歴を見る |
| 処理されない例外 (`std::out_of_range` など) | `throw` された例外を誰も捕まえない。最終的に `std::terminate` → `abort()` | デバッガーが throw 地点か `abort` で止まる → 呼び出し履歴で自分のコードを探す。投げた瞬間に止めたいなら「例外が投げられたときに止める」をオンにする |
| `abort()` + `[CRASH] ...` メッセージ | BugHunt のチェッカー(メモリチェック、ソートのチェック)か標準ライブラリのデバッグチェックが誤りを見つけた | コンソールのメッセージを最後まで読み → 呼び出し履歴で自分のコードを探す |

<details>
<summary>道具別の参考: Visual Studio のアサーション ウィンドウ</summary>

MSVC の Debug 構成の標準ライブラリは、範囲外の `operator[]` や無効になったイテレーターのような誤りを **Debug Assertion Failed!** ウィンドウで知らせます。**再試行 (Retry)** → (ブレークポイントのメッセージが出たら「中断」) → 呼び出し履歴を見ればよいです。GCC の libstdc++ は `-D_GLIBCXX_ASSERTIONS`、Clang の libc++ はハードニングモードで似たチェックをオンにできます。BugHunt のラボは、このようなチェックが **あってもなくても同じ結果** になるように作ってあります(第1部の範囲外アクセスは `at()` を使うので、どの構成でも例外になります)。
</details>

## 追跡の4ステップ (全ラボ共通)

1. **どこで止まった?** 呼び出し履歴で **自分のコードが出てくる最初の行** を探す。
2. **何がおかしい?** そのフレームのローカル変数から、おかしな値(nullptr、0、とても大きな数、負の数...)を探す。
3. **その値はどこから来た?** 1つ **下** のフレーム(= 自分を呼んだ関数)をダブルクリックして、その値を渡した場所を見る。出どころが分かるまで繰り返す。
4. **本当の原因は?** 止まった場所ではなく、**おかしな値が最初に作られた場所** を直す。

> 💡 ポイント: **落ちた場所 ≠ 間違えた場所** であることがほとんどです。呼び出し履歴は「間違えた場所」へさかのぼるための道です。

各ラボを解くときに、下の記録表を埋めてみてください。

```
止まった関数:              
おかしな値:              
その値が来たフレーム:       
本当の原因:              
修正:                   
```

## やってみよう: ラボ1 (フレンドプロフィール)

### ビルド構成と BugHunt メモリチェッカー

| 構成 | 用途 |
|---|---|
| Debug | 基本。最適化がないので1行ずつ追いやすい |
| Release | 最適化ビルド。未定義動作が Debug とは **違う形** で現れることを体験するとき |
| ASan | AddressSanitizer。解放後の使用、範囲外アクセス、二重解放を **その行で** 捕まえ、読んだ場所/解放した場所/確保した場所の呼び出し履歴を見せてくれる |

コマンドラインでのビルド: `build.bat Debug` / `build.bat Release` / `build.bat ASan` (Linux、macOS は `./build.sh`)

解放されたメモリを読んだり、初期化していない値を使ったりするのは **未定義動作**(undefined behavior)です。標準は結果を定めていないので、何事もなく正しい値が出ることもあれば、コンパイラーや構成を変えたとたんに間違うこともあります。そこで採点結果がコンパイラーによって揺れないように、BugHunt は標準が認める **グローバル `operator new`/`delete` の置き換え** で作った小さなメモリチェッカー(`src/support/heap_guard.cpp`)を Debug と Release に入れました。ASan 構成では ASan が同じことをより正確に行うので、メモリチェッカーはオフにします。

| メモリチェッカーがすること | その結果 |
|---|---|
| 新しく確保したメモリを `0xA5` で埋める | 初期化していない値を読むと `0xA5A5A5A5`(-1515870811)のような **見分けのつくゴミ** が出る |
| 解放したメモリを `0xEE` で上書きし、しばらく再利用しない | 解放後の使用で **たまたま正しい値** を読むことがない。`0xEEEEEEEE`(-286331154)が見えたら解放済みメモリ |
| ブロックの直後16バイトを `0xBD` で埋め、解放時に確認する | 確保したサイズを超えて書くと `[CRASH] メモリチェック: ... バッファオーバーラン` |
| 二重解放、`new[]`/`delete` の組み合わせ間違い、`new` で得ていないアドレスの解放 | `[CRASH] メモリチェック: ...` のメッセージの後に `abort()` |

これらの値は BugHunt が決めたものなので、どのコンパイラーでも同じです。本物のプログラムにはこのようなメモリチェッカーがないことを覚えておいてください。メモリチェッカーがなければ、同じバグが「実行するたびに、コンパイラーごとに違って」見えます。

<details>
<summary>道具別の参考: MSVC Debug の <code>/RTC1</code>、CRT デバッグ ヒープ、マジックナンバー</summary>

MSVC の Debug 構成は独自にメモリを埋めます。Visual Studio で BugHunt をデバッグしていると、これらの値を見ることもあります(メモリチェッカーが上書きする前や、スタック変数など)。

| 値 | 意味 |
|---|---|
| `0xCCCCCCCC` (-858993460) | `/RTC1` が埋めた、初期化されていない **スタック** メモリ |
| `0xCDCDCDCD` | CRT デバッグ ヒープ: `new` で得たが、まだ何も書いていない **ヒープ** メモリ |
| `0xDDDDDDDD` | CRT デバッグ ヒープ: すでに解放されたヒープ メモリ |
| `0xFDFDFDFD` | CRT デバッグ ヒープ: ブロックの前後の境界(no man's land) |

`/RTC1` は MSVC 専用のランタイム チェックで(CMake の MSVC Debug の既定値)、GCC・Clang には同じものがありません。初期化されていない値は、GCC・Clang の `-ftrivial-auto-var-init=pattern`、MemorySanitizer(Clang、Linux)、Valgrind などの道具で見つけます。コード分析の警告(MSVC C26495「メンバーが初期化されていない」など)も手がかりになります。
</details>

# 第3部: フロー追跡 (クラッシュなし)

第1・2部ではプログラムが落ちてくれました。デバッガーが「ここだよ」と止まってくれるので、呼び出し履歴をさかのぼるだけで済みましたね。
実務のバグのほとんどはそうではありません。プログラムは最後まで問題なく動き、**数字が1つ間違っているだけ** です。このときは **自分で止めて、自分で追いかける** 必要があります。

> 第3部は必ず **Debug** 構成で行ってください。Release では最適化のために行が飛ばされたり、変数が「最適化されているため使用できません」(gdb: `<optimized out>`)と表示されたりします。

## フロー追跡の4ステップ (第3部共通)

1. **先に期待を書く。** 「この行が終わったら `streak` は2のはず」のように、追いかける前に各ステップの期待値を決める。期待がなければ、間違った値を見ても見過ごしてしまう。
2. **間違った結果に一番近い所から止める。** プログラムの一番最初ではなく、[FAIL] になった値を作る関数の入口にブレークポイントを置く。
3. **期待と最初に食い違う行を探す。** 1行ずつ実行(ステップ オーバー (step over))しながら値を確認する。食い違った行が関数呼び出しなら、その関数の中に(ステップ イン (step into))入って同じことを繰り返す。
4. **「最初に食い違った所」を直す。** その後に出てくる間違った値の多くは、その結果にすぎない。

```
記録表 (第3部用)
間違った結果:              
止めた位置:              
期待値 → 実際の値:         
最初にずれた行:          
本当の原因:              
修正:                   
```

## 第3部で使う道具

道具ごとのキーとコマンドは [デバッガー対応表](#デバッガー対応表) にあります。

| 操作 | いつ |
|---|---|
| ブレークポイント + 1行ずつ実行(step over) | 基本。値が行ごとにどう変わるかを見るとき |
| 関数の中へ(step into) / 外へ(ステップ アウト (step out)) | 怪しい関数呼び出しがあるとき。外に出ると、デバッガーが今戻ってきた値を見せてくれる(Visual Studio: 自動変数 ウィンドウの `関数名 の戻り値`、gdb: `finish` の `Value returned`) |
| カーソルまで実行 | ブレークポイントなしで「ここまで進めて」 (Visual Studio: Ctrl+F10、VS Code: Run to Cursor、gdb: `until 40`) |

## 演算子のミス (ラボ29~32)

`x++` と `++x`、`&` と `&&`、`|` と `||` は1文字違いなのでコードレビューで目に留まりにくく、警告なしでコンパイルされます。
結果はクラッシュではなく **値が1つずれる** ことなので、第3部のフロー追跡の道具で捕まえます。
ここでは特に「式の値」と「変数に残る値」が食い違う瞬間を見る練習をします。

# 第5部: C++ 言語の落とし穴

この部のバグはすべて **コンパイラーが受け入れるコード** です。`std::move` がコピーになり、オーバーフローした整数が負の数になり、小数点以下が切り捨てられ、負の数がとても大きな正の数になり、グローバル変数が0で、ヘッダーの変数が二つに分かれ、例外がメモリを漏らし、デストラクターの例外がプログラムを終了させ、範囲 for が新しい要素を見ません。

# 第6部: インターフェースと継承

仮想関数は「実際のオブジェクトの型に合った関数が呼ばれる」という約束です。この約束には例外がいくつもあります。
シグネチャーが1文字でも違えばオーバーライドではなく、値でコピーすれば派生部分が切り落とされ、構築中のオブジェクトはまだ派生型ではなく、デフォルト引数は仮想的には選ばれません。
どれもコンパイルは問題なく通り、結果は「別の関数が呼ばれた」です。

この部の共通の道具は、**ステップイン (Step Into) で実際にどのクラスの関数に入るかを見ること** と、**ウォッチでオブジェクトの実際の型を見ること** です。
デバッガーはポリモーフィックなオブジェクトを実際の型(例: `{Boss}`)で表示し、仮想関数テーブル(vtable)のポインターも展開して見られます。

> ラボ16(仮想デストラクターの欠落)は第2部にそのまま置きます。この部は「呼ばれる関数が違う」に集中します。

## 第6部で使う道具

| 道具 | やり方 | いつ |
|---|---|---|
| ステップイン (Step Into) | 仮想呼び出しの行で1段入る | どのクラスの関数が呼ばれるか確認 (ラボ49, 52) |
| 止まらないブレークポイント | 派生クラスの関数にブレークポイント → 止まらなければそれが手がかり | オーバーライドされていない、またはオブジェクトが切られたとき (ラボ49, 50, 51) |
| 実際の型を見る | ウォッチやローカル ウィンドウでオブジェクトを展開し、型名とvtableを確認 | スライシング、コンストラクター内での型 (ラボ50, 51) |
| 呼び出し履歴を上がる | 落ちた場所から1段ずつ上がって値を比べる | `dynamic_cast` の結果が nullptr のとき (ラボ54) |
| コンパイラーに聞く | `override`、`explicit`、`= delete` を付けて再ビルド | 意図をコードに書いて、ミスをコンパイルエラーに変える |

# 第7部: ファイル入出力

ファイル入出力のバグの多くは「ファイルは無事なのに、プログラムの読み方が違う」ケースです。クラッシュも例外もありません。
ストリームは失敗しても黙って状態ビットを立てるだけで、パスは起動した場所によって別のファイルを指し、書いた内容はバッファーに留まっています。
そこでこの部では、変数の代わりに **ストリームの状態** と **ディスクに実際にあるバイト** を一緒に見ます。

- すべてのラボは `一時フォルダー/BugHunt/<ラボ名>/` の下にだけファイルを作り、終わったら削除します(`std::filesystem::temp_directory_path()`)。
  ブレークポイントで止まっている間はファイルが残っているので、エクスプローラーやエディターで直接開いてみられます。
- 判定はOSとコンパイラーに関係なく同じになるようにしました。そのため、OSによって結果が違うテーマ(テキストモードの改行変換など)は「未収録」に理由と一緒に書いています。

## 第7部で使う道具

| 道具 | やり方 | いつ |
|---|---|---|
| ストリーム状態のウォッチ | ウォッチに `in.good()`、`in.eof()`、`in.fail()`、`in.rdstate()` | 読み込みが「黙って」止まったとき。`fail` が立ったストリームはその後のすべての読み込みを無視する (ラボ57, 59) |

# 第8部: シリアライズ (JSON/XML)

セーブ、設定、データ表のほとんどはJSONかXMLです。ライブラリの多くは「親切に」動きます。

# 第9部: ポインターの誤用

第1部・第2部で nullptr、vector の参照の無効化、string_view のダングリング、erase 後のイテレーター、二重解放、仮想デストラクター、構造体のバッファーあふれを扱いました。第9部はそれ以外のポインターのミスです。
第9部のバグはすべて **未定義動作** です。寿命が終わったメモリを読み、初期化していないポインターをたどり、`new[]` で作ったものを `delete` で消します。規格はこのとき何が起きるかを定めていないので、実際のプログラムではコンパイラー、最適化、OS、さらには実行するたびに症状が変わります。「Release では動くんですが」はバグがないという意味ではありません。

BugHunt は採点がぶれないように Debug と Release に **メモリチェッカー** を入れました([ビルド構成と BugHunt メモリチェッカー](#ビルド構成と-bughunt-メモリチェッカー))。そのため第9部は、どのコンパイラー、どの構成でも同じラボが同じ理由で失敗します。ASan 構成ではチェッカーの代わりに ASan が報告します。両方を実行してみて、報告の内容を比べてください。

| 報告するもの | すること | だからポインターのバグは |
|---|---|---|
| メモリチェッカー (Debug, Release) | 新しいメモリを `0xA5`、解放したメモリを `0xEE`、ブロックの後ろを `0xBD` で埋め、`delete` のときに対応と境界を確認する | ゴミ値が **見分けられるゴミ** になる。誤った解放はその場で `[CRASH] メモリチェック: ...`。ただし誤って **読む** 瞬間には止まらない |
| ASan | 割り当てごとに前後に「レッドゾーン」を置き、解放したメモリをしばらく隔離し、すべての読み書きを検査する | 誤って読み書きした **まさにその行** で止まり、読んだ場所/解放した場所/割り当てた場所の呼び出し履歴まで見せてくれる。ただし既定の設定では、初期化されていない値、スタックのダングリングの一部、メモリリーク(Windows にはリーク検出器がない)は捕まえられない |

## ラムダのキャプチャと ASan (ラボ75)

`[&]` ラムダはローカル変数の **アドレス** を持っています。ラムダをタイマーやコールバックの一覧に預けて関数が終わると、そのアドレスはもう終わった関数のスタックです。ヒープと違ってスタックには「解放」という出来事がなく、次の関数呼び出しが同じ場所をすぐに再利用します。

バグの状態で実行してみると、間違った値はコンパイラーと構成ごとに違います(このリポジトリで確認した Kael の攻撃力: MSVC Debug -124、MSVC・Clang Release 45、Clang Debug 85、ASan は数億台のゴミ値)。スタックの場所がいつ再利用されるかは、最適化とスタックの配置しだいだからです。Release の 45 は、ラムダが読んだ `bonus` の場所に、後で怒りを使った Doran の `bonus`(45)が入っていたために出た値です。どの場合でも、期待した 60 は出ません。

- ASan が既定で捕まえられない理由: 既定の ASan は、関数が終わった後のスタックの場所を「死んだメモリ」として印を付けません。この種のバグ(stack-use-after-return)を捕まえるには、スタックフレームを別に切り離しておく機能を有効にする必要があります。
- **Clang, GCC**: 実行時に環境変数 `ASAN_OPTIONS=detect_stack_use_after_return=1` を与えると有効になります(バージョンによっては既定で有効なこともあります)。このリポジトリで Windows の Clang 22 ASan ビルドで試したところ、ラボ75のラムダの行で `stack-use-after-return` が正確に報告されました。
- **MSVC**: コンパイルオプション `/fsanitize-address-use-after-return` が必要で、レポートは `stack-buffer-underflow` という名前で出ます。このリポジトリでは有効にしていません。MSVC 14.51 でプロジェクト全体に有効にすると、プログラム開始時のグローバル `std::string` の初期化で誤検出が出てラボまでたどり着けず、このファイルだけに有効にすると、他のファイルと共有する標準ライブラリのコードで誤検出が出ました(Debug、Release ランタイムとも)。同じバグを含む小さな単独のプログラムではきちんと捕まりました。
- そのため、このラボの主な道具はデバッガーです。ラムダの中にブレークポイントを置くとラムダを展開してキャプチャしたものを見ることができ、参照でキャプチャした変数のアドレスが **もう終わった関数のスタック** を指しているかを確認できます。

## あふれ: スタックとヒープの境界 (ラボ76~80)

ポインターの誤用の最後のまとまりは **「決まった大きさを超えた」** です。スタックはスレッドごとに大きさが決まっていて(既定で Windows 1 MB、Linux 8 MB 程度)、ヒープのブロックや配列、構造体のメンバーもそれぞれ大きさを持っています。
あふれた瞬間にすぐ落ちる場合(スタックオーバーフロー)、しばらく後に解放するときに落ちる場合(ヒープ破損)、何も起きずに隣の値が変わる場合(構造体の中でのはみ出し)が、すべてこのまとまりにあります。
同じバグでも構成ごとに症状が違うので、第9部の他のラボと同じように **Debug、Release、ASan でそれぞれ実行して比べて** みてください。

# 第10部: 非同期と並行性

複数のスレッドが一緒に動くコードでは、**「どのスレッドが、いつ」** がバグの半分です。同じ行でも、他のスレッドがどこまで進んだかによって正しくもなり間違いにもなります。そのため実際のプログラムでは実行するたびに症状が変わり、デバッガーで止めるとタイミングが変わって症状が消えることもあります。

> **この部のラボは毎回同じように間違えます。** ラッチ(`std::latch`)、合図(鐘、掲示板)、まとめ処理のような **順序を固定する仕組み** を入れて、バグが起きる順序を毎回再現するようにしました。これらの仕組みはゲームのコードの一部のように見えますが、バグを「ときどき」から「毎回」に変えるために入れたものです。仕組みを消して症状を隠さず、原因を直してください。固まる可能性のあるラボは、第11部と同じ2秒のウォッチドッグの下で動きます。

## ThreadSanitizer

ThreadSanitizer(TSan)は、2つのスレッドが同期なしで同じメモリにアクセスし、そのうち1つが書き込みのときに、その行で報告します。ASan と同じくコンパイルオプションで有効にします。ASan と同時には有効にできません。

```bash
cmake -S . -B build/tsan -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS=-fsanitize=thread -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread -DBUGHUNT_BIN_NAME=TSan
cmake --build build/tsan
./bin/TSan/BugHunt 17
```

- ラボ17(ギルドの金庫)の競合は `WARNING: ThreadSanitizer: data race` として出ます。ラボ85はデータ競合ではありません(すべてのアクセスが `atomic`)。TSan が黙っているのに間違うバグがあることを比べてみてください。
- TSan が報告すると終了コードが変わり、採点では CRASH になることがあります。

<summary>ツール別の参考: TSan を使える環境</summary>

TSan は Linux と macOS の GCC・Clang で使います。MSVC と Windows の Clang にはありません。Windows では WSL でビルドするか、上の記録表とスレッド一覧で追跡してください。このリポジトリでは Windows しか試せなかったため、TSan の結果は確認できていません。

# 第11部: フリーズ - 無限ループとデッドロック

クラッシュもせず、間違った結果も出ません。プログラムがただ **固まります**。デバッガーは自分からは止まってくれず、どこにブレークポイントを置けばよいかもわかりません。
このときは、固まったプログラムを **その瞬間丸ごと止めて**(すべて中断)、各スレッドがどこにいるかを見ます。

> **安全装置:** 第11部のラボは「ラボ作業スレッド」(デバッガーでは `lab-worker` として見える)で動き、メインスレッドが2秒のウォッチドッグで時間を計ります。時間を超えると `[FAIL] ... 応答なし (2000 ms 超過)` を出力して終了します(`labs.h` の `runWithWatchdog`)。
> **デバッガーをアタッチして実行するとウォッチドッグは無効になります。** コンソールに案内が出るので、止まった状態を思う存分観察し、デバッグを停止して終了してください。(デバッガーの検出は `src/platform` にあります。Windows と Linux、macOS に対応しています。)

## フリーズを追跡する道具

ツールごとのキーとコマンドは [デバッガー対応表](#デバッガー対応表) にあります。

| 操作 | いつ |
|---|---|
| すべて中断 (break all) | 固まったプログラムをその瞬間のまま止めるとき |
| スレッド一覧と切り替え | すべて中断の直後、現在の行が待っているだけのメインスレッドにあるとき、`lab-worker` に切り替える |
| すべてのスレッドの呼び出し履歴 (Visual Studio: 並列スタック、gdb: `thread apply all bt`) | デッドロックで誰がどこで待っているかをひと目で |
| もう一度すべて中断 | 1~2秒さらに実行してから再びすべて中断。値が変わり続けるなら無限ループ、同じ場所のままならデッドロック |
| 実行位置を移す (次のステートメントの設定、`jump`) | 無限ループから抜け出して「その後のコードは正しいか?」を試すとき。値は元に戻らないので、実験用であって修正ではない |
| 値を変える | ループ変数を変えて「この値なら終わるか?」を試すとき |

| 原因を探す場所 | ループの条件と、ループ変数の変わり方 | 各スレッドが **持っているロック** と **待っているロック** |

# 第12部: パフォーマンス - 間違ってはいないが遅い

結果はすべて正しいです。それなのに **遅いのです。** デバッガーで一行ずつ追っても、どの行もまともに見えます。このときは「どの行が間違っているか」ではなく **「時間をどこに使っているか」** を問う道具、**プロファイラー** を使います。

> **判定は時間ではなく回数で行います。** PC ごとに速度が違うので、「100 ms 以下」のような基準は当てにならないからです。各ラボは要素の移動、コピー、割り当てバイト数、flush のような **仕事の量** を数えて判定し、時間は参考として出力するだけです。そのため第12部は Debug、Release、ASan の **どの構成で採点しても結果が同じです。**
> **プロファイリングは Release で行ってください。** Debug は最適化がオフで検査コードも多いので、見当違いの場所が遅く見えます。このリポジトリで測った例では、キャッシュに逆らう走査は Release では数十倍遅くなりましたが、Debug では 2 倍にも届きませんでした。逆に Debug でだけ大きく見えるコスト(イテレーターの検査、インライン化されない小さな関数)もあります。

## プロファイラーの使い方

CPU サンプリング プロファイラーは、プログラムをデバッガーなしで動かしながら「今どの関数を実行中か」をごく頻繁に記録し、関数ごとに時間を集計します。ツールによって画面は違いますが、見るものは同じです。

| ツール | 始め方 |
|---|---|
| Visual Studio パフォーマンス プロファイラー | 構成を **Release** に → デバッグ → パフォーマンス プロファイラー (Alt+F2) → **CPU 使用率** → 開始 |
| Linux `perf` | `perf record -g ./bin/Release/BugHunt 48` → `perf report` |
| macOS Instruments | Instruments → **Time Profiler** → 対象に `bin/Release/BugHunt`、引数 `48` → 記録 |
| その他 | Windows の Intel VTune・AMD uProf、クロスプラットフォームの `samply`、Valgrind の `callgrind`(遅いが正確な呼び出し回数)など |

| 見るもの | 意味 |
|---|---|
| ホット パス (hot path) | 時間がいちばん多く流れる呼び出し経路。いちばん下が実際に仕事をしている関数 (VS: 「ホット パス」、perf: `perf report` のコールグラフ) |
| 合計 / 自己時間 (Total / Self、perf では Children / Self) | 合計 = その関数とその関数が呼んだものすべて、自己 = その関数の本体だけ。自己が大きい関数が犯人、合計が大きい自分の関数が犯人を呼んだ場所 |
| 呼び出し元 / 呼び出し先 | その関数を誰が呼び、その関数が誰を呼んだか。ソース行ごとの時間(VS: 関数をダブルクリック、perf: `perf annotate`) |
| サイズを 2 倍に | ラボの個数の定数を 2 倍に変えて実行。時間や回数が 2 倍なら O(n)、4 倍なら O(n²)。どちらかが最初の手がかり |

> Visual Studio には、デバッグしながら 2 つのブレークポイントの間だけをプロファイリングする「診断ツール」ウィンドウもあります。Debug でも使えますが、上の注意のとおり Debug の時間は信用しにくいです。

> 第12部のラボは 1 秒もかからずに終わるので、プロファイラーに取れるサンプルが少ないことがあります。そのときはラボの個数の定数を何倍かに増やして実行してください(採点は元の値で行います)。

```

サイズを 2 倍にしたとき (時間 / 数える値):   
ホット パスのいちばん下の関数 (自己 CPU が大きいもの):  
その関数を呼んだ自分のコードの行:            
その行の仕事量が大きくなる理由:       
修正:                                 
修正後の数える値:                       
```

## 判定方法

- ラボごとに `BugHunt` を **子プロセスとして別々に** 起動します(`--grade-child N`)。1 つのラボが落ちたり止まったりしても、他のラボや採点スクリプトは影響を受けません。採点中はアサーションやエラー報告のダイアログは表示されず、すぐに終了します。
- 判定は子プロセスの **終了コードと時間** だけで行います。

| 結果 | 条件 |
|---|---|
| PASS | 終了コード 0 (すべての検査が `[PASS]`)。隠しケースがあればそれも 0 |
| FAIL | 終了コード 10 (`[FAIL]` が 1 つ以上) |
| TIMEOUT | 終了コード 11 (ウォッチドッグの 2 秒超過)、または採点スクリプトのラボごとの制限 15 秒超過 |
| CRASH | それ以外の終了コードやシグナル。処理されない例外、`abort()`(BugHunt メモリチェッカーの `[CRASH] メモリチェック: ...` を含む)、ASan エラー、不正なアドレスへのアクセス、スタックオーバーフローなど。下の [クラッシュコード](#クラッシュコード) の表を参照 |

- **隠しケース:** 第3〜12部のラボとチャレンジは、通常の実行が合格すると **画面に出ない別のデータでもう一度** 実行します(`--grade-child N --hidden`)。結果をハードコードして `[PASS]` にしたり、見えているデータでだけ正しくなる中途半端な修正(例: ラボ 88 を `t < cooldownSeconds` だけに直す)は、ここで引っかかります。このとき結果は FAIL で、説明は `症状は消えたが原因が残っている (隠しケース)` で始まります。チャレンジにはすべて隠しケースがあります。隠しテストは各ラボファイルのいちばん下の `採点用の隠しテスト` region にあります。ソースなので開いて見ることはできますが、解くのには必要なく、書き換えると採点の意味がなくなります。第1・2部はクラッシュそのものが症状なので、隠しケースはありません。
- 判定は標準 C++ で観測できる値(範囲検査の例外、インスタンス数、BugHunt メモリチェッカーなど)で行うので、構成やコンパイラーが違っても結果が同じになるようにしてあります。このリポジトリで MSVC 14.51 と Clang 22(Windows)の Debug、Release、ASan の 6 通りすべてで採点したところ、**バグのある状態はすべて 0/109、解答をすべて適用するとすべて 109/109** でした。失敗の種類は少し異なることがあります(例: Clang Release ではラボ 89 が TIMEOUT ではなく FAIL。第11部のラボ 89 の説明を参照)。
- 採点スクリプト自体の終了コードは、満点なら 0、そうでなければ 1 です。

## grade-report.json の形式 (BugHunt 4 エディション共通)

採点結果は機械で読める `grade-report.json` としても保存されます(UTF-8、採点スクリプトを実行したフォルダー、`.gitignore` に含まれる)。C#、Unreal、Unity 版も同じ形式を使います。

```json
{
  "edition": "cpp",
  "version": 1,
  "total": 109,
  "passed": 23,
  "labs": [
    { "id": 1, "title": "フレンドプロフィール", "part": 1, "result": "CRASH", "ms": 16, "detail": "アクセス違反 (0xC0000005)" },
    { "id": 21, "title": "ログインボーナス", "part": 3, "result": "PASS", "ms": 31, "detail": "" }
  ]
}
```

| フィールド | 型 | 意味 |
|---|---|---|
| `edition` | 文字列 | どのエディションの結果か。このリポジトリは `"cpp"` |
| `version` | 整数 | この JSON 形式のバージョン。現在は `1`。フィールドの意味が変わったら上げる |
| `total` | 整数 | 採点したラボの数(= `labs` の長さ)。ラボを 1 つだけ採点したら 1 |
| `passed` | 整数 | `result` が `"PASS"` のラボの数 |
| `labs[].id` | 整数 | ラボ番号(メニュー番号)。チャレンジは整数を保つため、深い追跡 C-n = `100 + n`、ブラインド B-n = `200 + n` (例: C-1 = 101、B-3 = 203)。4 エディション共通 |
| `labs[].title` | 文字列 | ラボ名。チャレンジは `"チャレンジ C-1"` のように番号だけ (ブラインドは名前でもヒントを与えない) |
| `labs[].part` | 整数 | 部の番号。チャレンジは最後の部の次の番号(このリポジトリは `13`) |
| `labs[].result` | 文字列 | `"PASS"`、`"FAIL"`、`"TIMEOUT"`、`"CRASH"` のいずれか |
| `labs[].ms` | 整数 | かかった時間(ミリ秒)。隠しケースの実行時間を含む |
| `labs[].detail` | 文字列 | 失敗理由 1 行(最初の `[FAIL]` 行、クラッシュの種類と手がかりなど)。PASS なら空文字列。通常のデータは合格したが隠しケースで失敗した場合は `"症状は消えたが原因が残っている (隠しケース) "` で始まる |

## クラッシュコード

採点表の CRASH の説明や、デバッガーが止まった理由に出てくる値です。Windows では終了コード(例外コード)として、Linux・macOS ではシグナルとして出ます。デバッガーのキーは上の [デバッガー対応表](#デバッガー対応表) を見てください。

| 意味 | Windows | Linux / macOS |
|---|---|---|
| 不正なアドレスへのアクセス (nullptr、解放されたメモリなど) | `0xC0000005` アクセス違反 | `SIGSEGV` (macOS は `SIGBUS` のこともある) |
| スタックオーバーフロー (終わらない再帰、大きなローカル変数、深い再帰 × 大きなフレーム) | `0xC00000FD` | `SIGSEGV` |
| 整数を 0 で除算 | `0xC0000094` | `SIGFPE` |
| `abort()` (処理されない例外、アサーション、BugHunt メモリチェッカー) | 終了コード 3 (アサーションは `0xC0000420` のこともある) | `SIGABRT` |
| ランタイムが見つけたヒープ破損 (たいてい壊した場所よりかなり後で落ちる) | `0xC0000374` | `SIGABRT` (glibc の `free(): invalid pointer` など) |
| ASan エラー | 終了コード 1 | 終了コード 1 |

> BugHunt メモリチェッカーがメモリを埋める値(新しく確保したメモリ `0xA5`、解放されたメモリ `0xEE`、ブロック後ろの境界 `0xBD`)は、第2部の [ビルド構成と BugHunt メモリチェッカー](#ビルド構成と-bughunt-メモリチェッカー) にあります。コンパイラーごとに異なるデバッグ用の埋め値(MSVC の `0xCC`、`0xDD` など)も、その節のツール別の参考にあります。
