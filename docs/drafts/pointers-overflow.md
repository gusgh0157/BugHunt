# 초안: 스택/힙 오버플로 (포인터 오용 부 끝에 붙일 랩 5개)

> README/SOLUTIONS/커버리지 표에 합칠 **초안**입니다. 랩 번호 94~98은 실행 파일의 **임시 번호**(머지 뒤 번호)이고, 최종 위치는 **5부 포인터 오용의 끝**(랩 42 다음)입니다.
> 파일: `BugHunt/src/overflow/of01_minimap.cpp` ~ `of05_skill_tree.cpp`
> 소스의 머리 주석과 힌트는 한국어·일본어 병기(`// [JA]`)로 썼습니다.

## README: 5부에 덧붙일 소개

### 넘침: 스택과 힙의 경계

포인터 오용의 마지막 묶음은 **"정해진 크기를 넘었다"** 입니다. 스택은 스레드마다 크기가 정해져 있고(기본 Windows 1 MB, Linux 8 MB 정도), 힙 블록과 배열과 구조체 멤버도 각자 크기가 있습니다.
넘치는 순간 바로 죽는 경우(스택 오버플로), 한참 뒤 해제할 때 죽는 경우(힙 손상), 아무 일도 없이 옆 값이 바뀌는 경우(구조체 안의 넘침)가 모두 이 묶음에 있습니다.
같은 버그라도 구성마다 증상이 다르므로, 5부의 다른 랩처럼 **Debug, Release, ASan에서 각각 실행해 비교**해 보세요.

## 이 묶음에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 호출 스택의 깊이 보기 | 스택 오버플로로 멈춘 뒤 호출 스택의 줄 수와 맨 위 함수 | 재귀가 아닌 넘침(94)과 깊이 × 프레임 크기의 넘침(95) 구별 |
| 프레임 사이 주소 차이 | 호출 스택에서 두 프레임을 골라 같은 지역 변수의 주소(`&layout`) 빼기 | 한 번의 호출이 쓰는 스택 크기 (95) |
| 조사식의 `sizeof` | `sizeof(dist)`, `sizeof(dst)` | 배열 크기가 예상과 다를 때 (94, 97) |
| 데이터 중단점 | 블록 바로 뒤 주소(`&frames_[ticks_]`)나 옆 멤버(`hero.gold`)에 걸기 | 크래시나 틀린 값이 난 곳과 원인이 떨어져 있을 때 (96, 98) |
| 메모리 창 | 버퍼를 바이트로 보기 | 널 문자 누락, 앞사람 이름이 남은 버퍼 (97) |

## 따라 해 보기: 랩 96 (리플레이 녹화)

1. 랩 96을 Debug로 실행합니다. `[CRASH] 메모리 검사: 할당한 크기를 넘어서 썼다 (버퍼 오버런). 블록 바로 뒤 경계가 바뀌어 있다`.
2. 디버거로 다시 실행해 멈춘 곳의 호출 스택을 봅니다. 맨 아래에서 올라가면 `recordMatch` → `~ReplayRecorder` → `delete[]`. **죽은 곳은 해제**입니다. 기록하는 `recordAll`은 이미 끝났습니다. → *증상이 드러난 곳*
3. "블록 바로 뒤"는 `frames_ + ticks_`입니다. `recordAll` 첫 줄에 중단점을 걸고, 조사식에 `&frames_[ticks_]`를 넣어 그 주소에 **데이터 중단점**(8바이트, 값이 바뀔 때)을 겁니다.
4. 계속 실행하면 `frames_[t] = Frame{ ... }` 줄에서 멈춥니다. 조사식 `t`는 600, `ticks_`도 600. → *처음 어긋난 줄*
5. 반복 조건이 `t <= ticks_`입니다. 원소 600개의 마지막 인덱스는 599입니다. `t < ticks_`로 고치고 [PASS]를 확인합니다.
6. ASan으로 빌드해 버그 상태를 다시 실행해 봅니다. 이번에는 **쓰는 순간** `heap-buffer-overflow`로 멈추고, 리포트의 첫 호출 스택이 바로 4번의 줄입니다.

98은 요청대로 "Debug는 잡고 Release는 조용히 덮는다"를 보여 주는 랩이라 구성마다 증상이 다릅니다. 판정은 FAIL 또는 CRASH로 어느 구성에서도 0점입니다. 나머지 넷은 구성 안에서 MSVC와 clang++의 판정이 같습니다. 검증: MSVC 14.51, clang++ 22(Windows, MSVC STL). GCC와 Linux(스택 8 MB)는 확인하지 않았지만, 94(16 MB)와 95(160 × 96 KB ≈ 15 MB)는 8 MB 스택도 넘도록 크기를 잡았습니다.

스택 오버플로 랩과 채점기: 두 랩 모두 감시 타이머를 쓰지 않는 보통 랩이고, 채점기는 자식 프로세스의 종료 코드(0xC00000FD, ASan은 종료 코드 1)로 CRASH를 판정합니다. 크래시까지 100 ms 안쪽이라 시간 제한과 부딪히지 않습니다. 95는 버퍼를 96 KB로 잡아, ASan의 `detect_stack_use_after_return`이 켜져 있어도(가짜 스택은 64 KB 이하 프레임만 옮김) 진짜 스택에서 넘치게 했습니다.

## SOLUTIONS 기록표

## Lab 94 — 16 MB 지역 배열로 스택 오버플로
```
틀린 결과:     CRASH, 스택 오버플로 (0xC00000FD / ASan stack-overflow)
멈춘 위치:     countReachable의 첫 줄(또는 스택을 미리 건드리는 도우미 함수). 호출 스택은 lab → countReachable 두어 줄뿐
진짜 원인:     int dist[2048][2048] = 16 MB 지역 변수. 함수에 들어가자마자 스택(Windows 1 MB)을 넘는다. 지도 크기와 상관없다
```
**수정:** `std::vector<std::vector<int>> dist(map.height, std::vector<int>(map.width, -1));` (또는 1차원 `std::vector<int>`에 `y * width + x`)
**교훈:** 스택 오버플로가 늘 재귀인 것은 아니다. 호출 스택이 짧은데 스택 오버플로라면 큰 지역 변수를 의심한다. 크기가 실행 중에 정해지거나 수십 KB를 넘는 데이터는 힙(`vector`)에. `static` 배열로 바꾸면 죽지는 않지만 16 MB를 늘 붙잡고 여러 스레드에서 쓸 수 없다.

## Lab 95 — 프레임마다 96 KB 버퍼 × 재귀 160겹
```
틀린 결과:     CRASH, 스택 오버플로. "방 8번 생성"까지 출력되고 죽음 (방 5개 시험 던전은 통과)
멈춘 위치:     buildRooms가 열 겹 남짓 쌓인 호출 스택. 이웃한 두 프레임의 &layout 차이 ≈ 98,000바이트
진짜 원인:     재귀는 160겹에서 끝나지만, 한 겹이 96 KB라 160겹이면 15 MB. 버퍼가 재귀 호출 뒤에도 쓰여 줄일 수 없다
```
**수정:** `std::vector<char> layout(kLayoutBytes);` (프레임에는 vector 하나만 남는다). 또는 보물 상자를 재귀 전에 세고 버퍼를 일찍 끝내거나, 재귀를 반복문으로.
**교훈:** 스택 사용량은 "프레임 크기 × 깊이"다. 깊이가 데이터(방 수, 트리 높이)에 따라 정해지는 재귀는 스택 한도를 생각해야 한다. 프레임 크기는 구성마다 다르다(Debug는 검사용 공간, ASan은 변수 사이 경계). 그래서 프레임이 작고 깊이가 경계에 걸린 재귀는 Debug에서만, 또는 ASan에서만 죽기도 한다. 직접 보려면 `kLayoutBytes`를 8 KB로 줄이고 방 수를 늘려 Debug와 Release에서 죽는 방 번호를 비교해 보라.

## Lab 96 — `new Frame[n]` 뒤 `<=`로 한 칸 더 쓰기, 해제할 때 드러남
```
틀린 결과:     CRASH, [CRASH] 메모리 검사: 할당한 크기를 넘어서 썼다 (ASan: heap-buffer-overflow)
멈춘 위치:     ~ReplayRecorder의 delete[]. 데이터 중단점(&frames_[ticks_])을 걸면 recordAll의 frames_[t] = ... 에서 t == 600
진짜 원인:     for (t = 0; t <= ticks_; ++t)가 원소 600개 배열의 frames_[600]에 쓴다
```
**수정:** `for (int t = 0; t < ticks_; ++t)`
**교훈:** 힙 넘침은 쓰는 순간이 아니라 그 자리를 다른 누가 볼 때(해제, 다음 할당, 옆 블록 사용) 드러난다. 크래시 위치와 원인이 멀면 **데이터 중단점**으로 "그 바이트를 누가 바꾸는지"를 묻는다. ASan은 쓰는 순간 잡는다. 랩 39(포인터 산술의 단위, 읽기)와 달리 이 랩은 반복 경계의 한 칸 쓰기다.

## Lab 97 — `memcpy`에 `sizeof(포인터)`
```
틀린 결과:     첫 번째 이름 "Nighting" (기대 "Nightingale"), 두 번째 이름 "Moonshadingale" 같은 이어 붙음
멈춘 위치:     writeName, 조사식 sizeof(dst) == 8, std::strlen(src) == 11. 메모리 창에서 packet.name 9바이트째부터 앞사람 이름
진짜 원인:     매개변수 char* dst는 배열이 아니라 포인터라 sizeof가 8. 앞 8바이트만 복사되고 널 문자가 없다
```
**수정:**
```cpp
void writeName(char* dst, std::size_t cap, const char* src)
{
    const std::size_t n = std::min(std::strlen(src), cap - 1);
    std::memcpy(dst, src, n);
    dst[n] = '\0';
}
// 호출: writeName(packet.name, sizeof(packet.name), name);
```
**교훈:** 배열은 함수 매개변수가 되는 순간 포인터로 바뀐다(배열 붕괴). 크기는 같이 넘기거나 `char (&dst)[N]` 템플릿으로 받는다. C 문자열 복사는 "길이 + 널 문자 1"과 "버퍼 크기 - 1로 자르기"를 둘 다 챙겨야 한다. clang은 `-Wsizeof-pointer-memaccess`로 이미 경고한다. 패킷 밖에서는 `std::string`.

## Lab 98 — 1부터 세는 스킬 번호로 `std::array` 인덱스, 옆 멤버 `gold`를 덮음
```
틀린 결과:     Debug: CRASH, "array subscript out of range" / Release: 2번 스킬 레벨 0, 골드 801 (기대 800)
멈춘 위치:     Debug: learnSkill의 hero.skillLevels[skillId] 줄 (어설션) / Release: hero.gold 데이터 중단점이 같은 줄에서 멈춤
진짜 원인:     화면 번호 1~4를 그대로 인덱스로 씀. skillLevels[4]는 배열 바로 뒤의 gold
```
**수정:** `hero.skillLevels[skillId - 1] += 1;`
**교훈:** `operator[]`는 범위를 검사하지 않는다. Debug 구성의 표준 라이브러리 검사는 보험일 뿐이고(Release CRT로 빌드한 ASan에도 없음), 같은 객체 안의 넘침은 ASan도 대개 못 잡는다. 확신이 없는 인덱스에는 `at()`. "어디서 바뀌었는지 모르는 값"에는 데이터 중단점(랩 18).

새 줄:

| 종류 | 다루는 랩 | 미포함 |
|---|---|---|
| 스택/힙 오버플로 | 94 큰 지역 배열로 스택 오버플로, 95 프레임 크기 × 재귀 깊이, 96 힙 off-by-one 쓰기(해제할 때 드러남), 97 `memcpy`에 `sizeof(포인터)`·널 문자 자리, 98 `operator[]` 범위 밖 쓰기로 옆 멤버 덮기 | 지역 배열 넘침으로 반환 주소 덮기(스택 버퍼 오버런), `alloca`·가변 길이 배열(VLA), 스레드마다 다른 스택 크기, 할당 크기 계산의 정수 오버플로(`new T[a * b]`), `sprintf`/`strcat` 계열 |

기존 줄 수정 (번호는 재배치 뒤 번호로):
- **포인터와 수명**: 다루는 랩에 `96 힙 off-by-one`, `97 sizeof(포인터)`를 더한다(18 "구조체 안 버퍼 넘침", 39와 나란히).
- **멈춤**: 바꾸지 않는다. 94, 95는 끝나는 코드가 스택 한도에 걸린 것이라 "멈춤"(끝나지 않는 재귀 5, 19)과 구별한다. 대신 README의 [크래시 코드] 표 "스택 오버플로 (끝나지 않는 재귀)" 줄을 "스택 오버플로 (끝나지 않는 재귀, 큰 지역 변수, 깊은 재귀 × 큰 프레임)"으로 고친다.
- **정의되지 않은 동작**: 다루는 랩에 `96~98 범위 밖 쓰기`를 더한다.

## 미포함 사유

- **지역 배열 넘침으로 반환 주소 덮기(스택 버퍼 오버런)**: 결과가 컴파일러의 스택 배치와 보호 기능(MSVC `/GS` 쿠키 → 0xC0000409, GCC/Clang stack protector는 배포판 기본값에 따라 켜짐/꺼짐, ASan은 stack-buffer-overflow)에 따라 CRASH·FAIL·통과가 갈린다. 판정을 고정할 수 없다.
- **`alloca`·가변 길이 배열(VLA)**: 표준 C++이 아니다(VLA는 GCC/Clang 확장, MSVC는 지원하지 않음).
- **스레드마다 다른 스택 크기**: 기본 스레드 스택 크기는 OS와 라이브러리마다 다르고(Windows 1 MB, glibc 8 MB, macOS 보조 스레드 512 KB), 표준으로 정할 수 없다.
- **할당 크기 계산의 정수 오버플로**: 정의되지 않은 동작이거나(부호 있는 곱셈) `bad_array_new_length` 예외로 바뀌는 등 경로가 여러 갈래이고, 실제로 넘치려면 수 GB 할당이 필요해 랩으로 재현하기 어렵다.
- **`sprintf`/`strcat` 계열**: MSVC가 사용 중단 경고(C4996)를 내고 대안이 `_s` 함수라, "표준 C++만, `_s` 함수 금지" 규칙과 맞지 않는다. 97(`memcpy`)이 같은 원리를 다룬다.

# 일본어판 (README.ja.md / SOLUTIONS.ja.md로 옮길 부분)

### あふれ: スタックとヒープの境界

ポインターの誤用の最後のまとまりは **「決まった大きさを超えた」** です。スタックはスレッドごとに大きさが決まっていて(既定で Windows 1 MB、Linux 8 MB 程度)、ヒープのブロックや配列、構造体のメンバーもそれぞれ大きさを持っています。
あふれた瞬間にすぐ落ちる場合(スタックオーバーフロー)、しばらく後に解放するときに落ちる場合(ヒープ破損)、何も起きずに隣の値が変わる場合(構造体の中でのはみ出し)が、すべてこのまとまりにあります。
同じバグでも構成ごとに症状が違うので、第5部の他のラボと同じように **Debug、Release、ASan でそれぞれ実行して比べて** みてください。

| 道具 | やり方 | いつ |
|---|---|---|
| 呼び出し履歴の深さを見る | スタックオーバーフローで止まった後、呼び出し履歴の行数といちばん上の関数 | 再帰ではないあふれ(94)と、深さ × フレームの大きさによるあふれ(95)の区別 |
| フレーム間のアドレスの差 | 呼び出し履歴で二つのフレームを選び、同じローカル変数のアドレス(`&layout`)を引く | 一回の呼び出しが使うスタックの大きさ (95) |
| ウォッチの `sizeof` | `sizeof(dist)`、`sizeof(dst)` | 配列の大きさが予想と違うとき (94, 97) |
| データ ブレークポイント | ブロックの直後のアドレス(`&frames_[ticks_]`)や隣のメンバー(`hero.gold`)に置く | クラッシュやおかしな値の場所と原因が離れているとき (96, 98) |
| メモリ ウィンドウ | バッファーをバイト単位で見る | ヌル文字の抜け、前の人の名前が残ったバッファー (97) |

| # (仮) | 名前 | 症状 | 新しく学ぶこと | 難易度 |
|---|---|---|---|---|
| 94 | ミニマップ | 小さいマップなのにミニマップを開くとすぐ落ちます | 再帰のない **スタックオーバーフロー**(16 MB のローカル配列)、呼び出し履歴が短い | ★ |
| 95 | ダンジョン生成器 | 部屋の多いダンジョンを作ると落ちます | **フレームの大きさ × 再帰の深さ**、フレーム間のアドレスの差 | ★★ |
| 96 | リプレイ録画 | 録画を終えて録画機を閉じるときに落ちます | ヒープの **off-by-one 書き込み** が **後で** 解放するときに表に出る、データ ブレークポイント | ★★ |

| 98 | スキルツリー | スキルを覚えたらゴールドがおかしく変わります | `operator[]` の範囲外書き込みが **隣のメンバーを上書き**、Debug のチェックと `at()` | ★ |

## やってみよう: ラボ96(リプレイ録画)

1. ラボ96を Debug で実行します。`[CRASH] メモリチェック: 確保した大きさを超えて書き込んだ(バッファーオーバーラン)`。
2. デバッガーでもう一度実行し、止まった場所の呼び出し履歴を見ます。`recordMatch` → `~ReplayRecorder` → `delete[]`。**落ちた場所は解放** です。記録する `recordAll` はもう終わっています。→ *症状が表に出た場所*
3. 「ブロックの直後」は `frames_ + ticks_` です。`recordAll` の最初の行にブレークポイントを置き、ウォッチに `&frames_[ticks_]` を入れて、そのアドレスに **データ ブレークポイント**(8バイト、値が変わったとき)を置きます。
4. 実行を続けると `frames_[t] = Frame{ ... }` の行で止まります。ウォッチの `t` は600、`ticks_` も600。→ *最初にずれた行*
5. ループの条件が `t <= ticks_` です。要素600個の最後のインデックスは599です。`t < ticks_` に直して [PASS] を確認します。
6. ASan でビルドしてバグの状態をもう一度実行してみます。今度は **書き込んだ瞬間に** `heap-buffer-overflow` で止まり、レポートの最初の呼び出し履歴がまさに手順4の行です。

## 構成ごとの症状(採点結果はすべて0点)

94・95 はどの構成でも CRASH(スタックオーバーフロー 0xC00000FD、ASan は `stack-overflow`)、96 は Debug/Release で解放時に `[CRASH] メモリチェック`、ASan で書き込み時に `heap-buffer-overflow`、97 はどの構成でも FAIL(`Nighting`)です。98 は Debug(と Debug CRT を使う MSVC の ASan)で `array subscript out of range` のアサーションにより CRASH、Release(と Release CRT を使う clang++ の ASan)では黙って FAIL(2番スキルのレベル0、ゴールド801)になります。

## 解答の記録表

### Lab 94 — 16 MB のローカル配列でスタックオーバーフロー
```
間違った結果:   CRASH、スタックオーバーフロー(0xC00000FD / ASan stack-overflow)
止めた位置:     countReachable の最初の行(またはスタックを事前に触る補助関数)。呼び出し履歴は lab → countReachable の数行だけ
本当の原因:     int dist[2048][2048] = 16 MB のローカル変数。関数に入った直後にスタック(Windows 1 MB)を超える。マップの大きさとは関係ない
```
**修正:** `std::vector<std::vector<int>> dist(map.height, std::vector<int>(map.width, -1));`
**教訓:** スタックオーバーフローがいつも再帰とは限りません。呼び出し履歴が短いのにスタックオーバーフローなら、大きなローカル変数を疑います。

### Lab 95 — フレームごとに 96 KB のバッファー × 再帰160段
```
間違った結果:   CRASH、スタックオーバーフロー。「部屋8番を生成」まで出力されて落ちる(部屋5個の試験ダンジョンは通る)
止めた位置:     buildRooms が十段ほど積まれた呼び出し履歴。隣り合う二つのフレームの &layout の差 ≈ 98,000バイト
本当の原因:     再帰は160段で終わるが、1段が 96 KB なので160段で 15 MB。バッファーは再帰呼び出しの後でも使われるので小さくできない
```
**修正:** `std::vector<char> layout(kLayoutBytes);`(または再帰の前に宝箱を数える、再帰をループにする)
**教訓:** スタックの使用量は「フレームの大きさ × 深さ」です。フレームの大きさは構成ごとに違うので、境界ぎりぎりの再帰は Debug でだけ、あるいは ASan でだけ落ちることもあります。

### Lab 96 — `new Frame[n]` の後で `<=` により1つ余分に書く、解放時に表に出る
```
間違った結果:   CRASH、[CRASH] メモリチェック: 確保した大きさを超えて書き込んだ(ASan: heap-buffer-overflow)
止めた位置:     ~ReplayRecorder の delete[]。データ ブレークポイント(&frames_[ticks_])を置くと recordAll の frames_[t] = ... で t == 600
本当の原因:     for (t = 0; t <= ticks_; ++t) が要素600個の配列の frames_[600] に書き込む
```
**修正:** `for (int t = 0; t < ticks_; ++t)`
**教訓:** ヒープのあふれは書いた瞬間ではなく、その場所を誰かが見るとき(解放、次の割り当て)に表に出ます。クラッシュの位置と原因が離れていたら、データ ブレークポイントで「そのバイトを誰が変えるか」を尋ねます。

### Lab 97 — `memcpy` に `sizeof(ポインター)`
```
間違った結果:   1番目の名前 "Nighting"(期待 "Nightingale")、2番目は前の人の名前がくっつく
止めた位置:     writeName、ウォッチ sizeof(dst) == 8、std::strlen(src) == 11。メモリ ウィンドウで packet.name の9バイト目から前の人の名前
本当の原因:     引数 char* dst は配列ではなくポインターなので sizeof は8。先頭8バイトだけコピーされ、ヌル文字がない
```
**修正:** バッファーの大きさ `cap` も渡し、`n = std::min(std::strlen(src), cap - 1)` だけコピーして `dst[n] = '\0'`。呼び出しは `writeName(packet.name, sizeof(packet.name), name)`。
**教訓:** 配列は関数の引数になった瞬間にポインターに変わります(配列の減衰)。C 文字列のコピーは「長さ + ヌル文字1」と「バッファーの大きさ - 1 で切り詰め」の両方が必要です。

### Lab 98 — 1から数えるスキル番号で `std::array` のインデックス、隣のメンバー `gold` を上書き
```
間違った結果:   Debug: CRASH、"array subscript out of range" / Release: 2番スキルのレベル0、ゴールド801(期待800)
止めた位置:     Debug: learnSkill の hero.skillLevels[skillId] の行(アサーション) / Release: hero.gold のデータ ブレークポイントが同じ行で止まる
本当の原因:     画面の番号1~4をそのままインデックスに使った。skillLevels[4] は配列の直後の gold
```
**修正:** `hero.skillLevels[skillId - 1] += 1;`
**教訓:** `operator[]` は範囲をチェックしません。Debug 構成の標準ライブラリのチェックは保険にすぎず、同じオブジェクトの中のはみ出しは ASan もたいてい捕まえられません。確信のないインデックスには `at()`。

## 対応表の行

| 種類 | 扱うラボ | 未収録 |
|---|---|---|
| スタック/ヒープのあふれ | 94 大きなローカル配列でスタックオーバーフロー、95 フレームの大きさ × 再帰の深さ、96 ヒープの off-by-one 書き込み(解放時に表に出る)、97 `memcpy` に `sizeof(ポインター)`・ヌル文字の分、98 `operator[]` の範囲外書き込みで隣のメンバーを上書き | ローカル配列のあふれで戻りアドレスを上書き(スタックバッファーオーバーラン)、`alloca`・可変長配列(VLA)、スレッドごとに違うスタックの大きさ、割り当てサイズ計算の整数オーバーフロー、`sprintf`/`strcat` 系 |

未収録の理由: スタックバッファーオーバーランは、コンパイラーのスタック配置と保護機能(MSVC `/GS`、stack protector、ASan)によって CRASH・FAIL・通過に分かれ、判定を固定できません。`alloca` と VLA は標準 C++ ではありません。スレッドの既定のスタックの大きさは OS ごとに違います。`sprintf` 系は MSVC が非推奨の警告を出し、代わりが `_s` 関数なので、このリポジトリの規則と合いません。
