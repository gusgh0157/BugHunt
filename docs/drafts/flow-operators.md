## README: 부 소개에 넣을 문단 (3부 끝)

### 연산자 실수 (랩 54~57)

`x++`와 `++x`, `&`와 `&&`, `|`와 `||`는 한 글자 차이라 코드 리뷰에서 눈에 잘 띄지 않고, 컴파일도 경고 없이 됩니다.
결과는 크래시가 아니라 **값이 하나씩 어긋나는 것**이라 3부의 흐름 추적 도구로 잡습니다.
여기서는 특히 "식의 값"과 "변수에 남는 값"이 다른 순간을 보는 연습을 합니다.

- 조사식(watch)에 식을 통째로 넣어 보기: `2 & 1`, `2 && 1`, `guild.lastId++`는 넣지 마세요(조사식도 부작용을 실행합니다)
- 데이터 중단점(값이 바뀌면 멈추는 중단점, watchpoint)으로 한 줄에서 값이 몇 번 바뀌는지 세기
- 함수에서 나온 직후 반환값 보기 (자동/지역 창의 "반환값" 줄)

> 컴파일러마다 결과가 달라지는 식(`f(i++, i++)`, `i++ + i++`)은 일부러 넣지 않았습니다. 판정이 컴파일러에 따라 달라지면 안 되기 때문입니다. 아래 "미포함"을 보세요.

## SOLUTIONS 기록표

## Lab 54 — 후위 증가의 값은 올리기 전 값
```
틀린 결과:     새봄이 1007번 (도윤과 같은 번호). lastId는 1010으로 맞지만 실제로 준 번호는 1007~1009
멈춘 위치:     issueId의 return 줄, 첫 join
기대값 → 실제값: lastId 1007 → 새 번호 1008 기대 / 실제 반환 1007
진짜 원인:     return guild.lastId++; 는 올리기 전 값(마지막으로 이미 준 번호)을 돌려준다
```
**수정:** `return ++guild.lastId;`
**교훈:** `x++`는 "x를 올린다" + "식의 값은 옛 x"라는 두 가지 일을 한다. 변수의 뜻("마지막으로 준 번호" vs "다음에 줄 번호")을 먼저 정하고 전위/후위를 고른다. `if (hits++ == 3)`도 같은 실수로, 네 번째 타격에서야 참이 된다.

## Lab 55 — 매크로가 부작용 있는 인자를 두 번 평가
```
틀린 결과:     화면 콤보 2 4 6 0 2 4 (기대 1 2 3 0 1 2), 최고 콤보 6
멈춘 위치:     c.current 데이터 중단점 → 공격 한 번에 두 번 멈춤
처음 어긋난 줄: c.best = BUGHUNT_MAX(c.best, ++c.current);
진짜 원인:     ((a) > (b) ? (a) : (b))로 펼쳐져 조건에서 한 번, 고른 쪽에서 또 한 번 ++c.current
```
**수정:**
```cpp
++c.current;
c.best = std::max(c.best, c.current);
```
**교훈:** 매크로는 함수가 아니라 글자 치환이다. 인자에 `++`, `--`, 함수 호출을 넣지 않는다. 가능하면 `std::max`나 `inline`/`constexpr` 함수를 쓴다. (`?:`는 조건을 먼저 계산하고 고른 쪽만 계산하도록 순서가 정해져 있어서, 이 결과는 어느 컴파일러에서나 같다.)

## Lab 56 — `&&` 자리에 비트 AND `&`
```
틀린 결과:     보람(열쇠 2, 횃불 1) 입장 불가, 들어간 인원 1
멈춘 위치:     canEnterCave, 조건 a.name == "보람"
기대값 → 실제값: a.keys & a.torches → 기대 참 / 실제 0 (2 = 10, 1 = 01)
진짜 원인:     정수 두 개를 &로 묶어 공통 비트가 없으면 0(거짓)
```
**수정:** `return a.keys > 0 && a.torches > 0;`
**교훈:** `&`는 정수의 비트끼리, `&&`는 참/거짓끼리 계산한다. 둘 다 1일 때만 우연히 같은 답이 나와서 처음 테스트(1, 1)를 통과한다. 개수를 참/거짓으로 쓸 때는 `> 0`으로 뜻을 적어 준다.

## Lab 57 — `||` 자리에 `|` → 단락 평가가 사라짐
```
틀린 결과:     연 문 4 (기대 5), 남은 따개 0 (기대 1)
멈춘 위치:     useLockpick의 --t.lockpicks 줄, 호출 스택에서 openDoor의 door 확인
처음 어긋난 곳: "감옥" 문 (열쇠가 있는데 따개가 줄어듦)
진짜 원인:     hasKey(...) | useLockpick(...) 는 앞이 true여도 뒤를 호출한다
```
**수정:** `return hasKey(t, door) || useLockpick(t);`
**교훈:** `||`/`&&`만 단락 평가를 한다. 뒤쪽 피연산자에 부작용(소모, 저장, 로그)이 있으면 `|`/`&`는 그 부작용을 항상 일으킨다. 랩 27과 짝: 27은 단락 평가 때문에 **필요한 호출이 빠졌고**, 57은 단락 평가가 없어서 **불필요한 호출이 일어났다**. `p == nullptr | p->hp <= 0`처럼 앞의 검사가 뒤를 지켜 주는 식에서는 `|`가 null 역참조 크래시가 된다.

## 미포함 사유

- `f(i++, i++)`, `i++ + i++`: C++17 이후에도 함수 인자끼리의 평가 순서는 정해지지 않았고(`f`), 같은 변수의 순서 없는 수정은 정의되지 않은 동작이다(`+`). MSVC와 clang이 다른 값을 내므로 [PASS]/[FAIL] 판정을 고정할 수 없다. 해설로만 다룬다.
- `a[i] = i++`: C++17부터 오른쪽이 먼저 계산되도록 정해졌지만, 예전 표준 기준으로 쓰인 자료와 결과가 달라 혼란만 주고 랩 54와 배우는 내용이 겹친다.
- `while (--n)` vs `while (n--)`: 랩 54의 전위/후위 차이와 같은 원리라 랩을 따로 두지 않았다. `n`이 0으로 들어오면 `--n` 쪽은 음수로 내려가 멈춤(6부)이 된다는 점만 랩 54 해설에 덧붙일 수 있다.
- `p == nullptr | p->hp <= 0`: null 역참조 크래시라 "크래시 없음"인 3부에 맞지 않아 랩 57의 교훈에 문장으로만 넣었다.

## 演算子のミス (ラボ54~57)

`x++` と `++x`、`&` と `&&`、`|` と `||` は1文字違いなのでコードレビューで目に留まりにくく、警告なしでコンパイルされます。
結果はクラッシュではなく **値が1つずれる** ことなので、第3部のフロー追跡の道具で捕まえます。
ここでは特に「式の値」と「変数に残る値」が食い違う瞬間を見る練習をします。

- ウォッチに式をまるごと入れてみる: `2 & 1`、`2 && 1`(`guild.lastId++` は入れないでください。ウォッチも副作用を実行します)
- データ ブレークポイント(値が変わると止まるブレークポイント、ウォッチポイント)で、1行の中で値が何回変わるかを数える
- 関数から戻った直後に戻り値を見る(自動変数/ローカル ウィンドウの「戻り値」の行)

> コンパイラーによって結果が変わる式(`f(i++, i++)`、`i++ + i++`)はあえて入れていません。判定がコンパイラーによって変わってはいけないからです。

## やってみよう: ラボ56(闇の洞窟)

## 解答の記録表

### Lab 54 — 後置インクリメントの値は増やす前の値
```
間違った結果:   セボムが1007番(ドユンと同じ番号)。lastIdは1010で合っているが、実際に渡した番号は1007~1009
止めた位置:     issueId の return 行、最初の join
期待値 → 実際:  lastId 1007 → 新しい番号1008を期待 / 実際の戻り値1007
本当の原因:     return guild.lastId++; は増やす前の値(最後にすでに渡した番号)を返す
```
**修正:** `return ++guild.lastId;`
**教訓:** `x++` は「xを増やす」と「式の値は古いx」の2つのことをします。変数の意味(「最後に渡した番号」か「次に渡す番号」か)を先に決めてから前置/後置を選びます。`if (hits++ == 3)` も同じミスで、4回目の攻撃でやっと真になります。

### Lab 55 — マクロが副作用のある引数を2回評価する
```
間違った結果:   画面のコンボ 2 4 6 0 2 4(期待 1 2 3 0 1 2)、最高コンボ6
止めた位置:     c.current のデータ ブレークポイント → 攻撃1回で2回止まる
最初にずれた行: c.best = BUGHUNT_MAX(c.best, ++c.current);
本当の原因:     ((a) > (b) ? (a) : (b)) に展開され、条件で1回、選ばれた側でもう1回 ++c.current
```
**修正:** `++c.current;` の後に `c.best = std::max(c.best, c.current);`
**教訓:** マクロは関数ではなく文字の置き換えです。引数に `++`、`--`、関数呼び出しを入れないでください。できれば `std::max` や `inline`/`constexpr` 関数を使います。

### Lab 56 — `&&` の代わりにビットAND `&`
```
間違った結果:   ボラム(鍵2、たいまつ1)入場不可、入場人数1
止めた位置:     canEnterCave、条件 a.keys == 2
期待値 → 実際:  a.keys & a.torches → 真を期待 / 実際は0(2 = 10、1 = 01)
本当の原因:     整数2つを & で結ぶと、共通のビットがなければ0(偽)になる
```
**修正:** `return a.keys > 0 && a.torches > 0;`
**教訓:** `&` は整数のビット同士、`&&` は真偽同士を計算します。両方1のときだけ偶然同じ答えになるので、最初のテスト(1, 1)は通ってしまいます。

### Lab 57 — `||` の代わりに `|` → 短絡評価がなくなる
```
間違った結果:   開いた扉4(期待5)、残りのロックピック0(期待1)
止めた位置:     useLockpick の --t.lockpicks 行、呼び出し履歴で openDoor の door を確認
最初にずれた所: 「牢屋」の扉(鍵があるのにロックピックが減る)
本当の原因:     hasKey(...) | useLockpick(...) は左が true でも右を呼ぶ
```
**修正:** `return hasKey(t, door) || useLockpick(t);`
**教訓:** 短絡評価をするのは `||`/`&&` だけです。ラボ27と対になります: 27は短絡評価のせいで **必要な呼び出しが抜け**、57は短絡評価がないせいで **不要な呼び出しが起きました**。`p == nullptr | p->hp <= 0` のように左の検査が右を守っている式では、`|` はnull参照のクラッシュになります。
