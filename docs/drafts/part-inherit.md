# N부: 인터페이스와 상속

가상 함수는 "실제 객체의 형식에 맞는 함수가 불린다"는 약속입니다. 이 약속에는 예외가 여럿 있습니다.
시그니처가 한 글자라도 다르면 재정의가 아니고, 값으로 복사하면 파생 부분이 잘리고, 생성 중인 객체는 아직 파생 형식이 아니고, 기본 인자는 가상으로 고르지 않습니다.
모두 컴파일은 잘 되고, 결과는 "엉뚱한 함수가 불렸다"입니다.

이 부의 공통 도구는 **함수 안으로 들어가기(Step Into)로 실제로 어느 클래스의 함수에 들어가는지 보기**와 **조사식에서 객체의 실제 형식 보기**입니다.
디버거는 다형 객체를 실제 형식(예: `{Boss}`)으로 보여 주고, 가상 함수 표(vtable) 포인터도 펼쳐 볼 수 있습니다.

> 랩 16(가상 소멸자 누락)은 2부에 그대로 둡니다. 이 부는 "불리는 함수가 다르다"에 집중합니다.

## N부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 함수 안으로 (Step Into) | 가상 호출 줄에서 한 단계 들어가기 | 어느 클래스의 함수가 불리는지 확인 (랩 72, 75) |
| 걸리지 않는 중단점 | 파생 클래스 함수에 중단점 → 안 멈추면 그게 단서 | 재정의가 안 됐거나 객체가 잘렸을 때 (랩 72, 73, 74) |
| 실제 형식 보기 | 조사식/지역 창에서 객체를 펼쳐 형식 이름과 vtable 확인 | 슬라이싱, 생성자 안에서의 형식 (랩 73, 74) |
| 호출 스택에서 위로 | 죽은 곳에서 한 칸씩 올라가 값 비교 | `dynamic_cast` 결과가 nullptr일 때 (랩 77) |
| 컴파일러에게 묻기 | `override`, `explicit`, `= delete`를 붙여 다시 빌드 | 의도를 코드로 적어 실수를 컴파일 오류로 바꾸기 |

## 따라 해 보기: 랩 72 (백스탭)

1. 랩 72를 실행합니다. `[FAIL] 등 뒤 백스탭 피해 (기대: 60, 실제: 20)`.
2. **기대를 적습니다.** 오우거는 등을 보이고 있으니 백스탭은 20 × 3 = 60.
3. `Backstab::damage` 안에 중단점을 겁니다. 실행해 보면 **멈추지 않습니다.** 걸리지 않는 중단점도 단서입니다(랩 27).
4. `useSkill`의 `skill.damage(target)` 줄에 중단점을 걸고, 두 번째로 멈췄을 때(백스탭) 함수 안으로 들어갑니다. `Skill::damage`로 들어갑니다.
5. 두 선언을 나란히 놓고 봅니다. `virtual int damage(const Target&) const` vs `virtual int damage(const Target& t)`. 끝의 `const`가 없습니다.
6. `Backstab::damage`에 `override`를 붙이고 빌드합니다. 컴파일러가 "재정의할 함수가 없다"는 오류를 냅니다. `const`를 붙여 고치고 다시 실행해 [PASS]를 확인합니다.

## SOLUTIONS 기록표

## Lab 72 — `const`가 빠져 재정의가 아니라 숨김
```
틀린 결과:     등 뒤 백스탭 20 (기대 60)
멈춘 위치:     Backstab::damage 중단점은 걸리지 않음 → useSkill에서 Step Into → Skill::damage
진짜 원인:     Backstab::damage에 const가 없어 Skill::damage(const Target&) const와 다른 함수. Skill&로 부르면 기반 버전
```
**수정:** `int damage(const Target& t) const override { ... }`
**교훈:** 재정의하려는 함수에는 항상 `override`. 붙이는 순간 `const` 누락, 매개변수 형식 차이(`int` vs `long`, `const&` vs 값), 기반 쪽 이름 변경을 컴파일러가 오류로 알려 준다. clang은 `-Wall`에서 `-Woverloaded-virtual` 경고를 내지만, MSVC는 기본 경고 수준(/W3)에서 아무 말이 없다.

## Lab 73 — `vector<Monster>`에 담아 Boss가 잘림 (슬라이싱)
```
틀린 결과:     전리품 3개, 황금 왕관 없음 (기대 4개)
멈춘 위치:     Boss::loot 중단점이 걸리지 않음 → collectLoot에서 wave[2]를 펼치면 형식이 Monster, rare_ 없음
진짜 원인:     wave.push_back(Boss(...))가 Boss의 Monster 부분만 복사해 담는다
```
**수정:**
```cpp
std::vector<std::unique_ptr<Monster>> spawnWave(const std::vector<SpawnInfo>& infos)
{
    std::vector<std::unique_ptr<Monster>> wave;
    for (const SpawnInfo& info : infos)
    {
        if (info.rareDrop.empty())
            wave.push_back(std::make_unique<Monster>(info.name, info.hp));
        else
            wave.push_back(std::make_unique<Boss>(info.name, info.hp, info.rareDrop));
    }
    return wave;
}
// collectLoot도 같은 형식을 받고 m->loot()
```
**교훈:** 다형 객체는 포인터(소유는 `unique_ptr`)로 담는다. 값으로 받는 함수 매개변수(`void f(Monster m)`)도 똑같이 자른다. 다형 기반 클래스의 복사를 `= delete`로 막아 두면 이 실수가 컴파일 오류가 된다.

## Lab 74 — 생성자 안의 가상 호출
```
틀린 결과:     저격 탑 사거리 3 (기대 8), 거리 7을 못 쏨
멈춘 위치:     Tower::baseRange 중단점 → 호출 스택에 Tower::Tower ← SniperTower::SniperTower
진짜 원인:     기반 생성자가 도는 동안 객체의 동적 형식은 아직 Tower. 가상 호출도 Tower 버전으로 간다
```
**수정:** 사거리를 필요할 때 묻는다.
```cpp
int range() const { return baseRange(); }
bool canHit(int distance) const { return distance <= range(); }
```
(또는 `Tower(int range)` 생성자로 파생 클래스가 값을 넘긴다)
**교훈:** 생성자와 소멸자 안에서 가상 함수는 "지금 만들고 있는(부수고 있는) 클래스"의 버전이 불린다. 이것은 표준이 정한 동작이라 어느 컴파일러에서나 같다. 소멸자에서 **순수** 가상 함수를 부르는 경우는 정의되지 않은 동작이라 이 랩에서 뺐다(아래 미포함).

## Lab 75 — 가상 함수의 기본 인자는 정적 형식을 따름
```
틀린 결과:     사제 기본 치유 15 (기대 30), 파티 총 25 (기대 40). 직접 priest.heal()은 30
멈춘 위치:     Priest::heal 안, castDefaultHeal에서 들어왔을 때 amount == 10
진짜 원인:     어느 heal이 불릴지는 동적 형식(Priest)으로, 기본 인자는 정적 형식(Healer)으로 정해진다
```
**수정:** 기본값도 가상 함수로 묻는다.
```cpp
// Healer
virtual int defaultAmount() const { return 10; }
// Priest: return 25;  Druid: return 18;
int castDefaultHeal(const Healer& healer)
{
    return healer.heal(healer.defaultAmount());
}
```
**교훈:** 가상 함수에 기본 인자를 두지 않는다(두더라도 기반과 같은 값만). 흔한 정석은 기본값을 쓰는 비가상 함수가 가상 함수를 부르는 NVI(non-virtual interface) 형태다. 기반의 기본값만 25로 바꾸면 드루이드(18)가 틀린다(숨은 테스트).

## Lab 76 — 파생 클래스의 오버로드 하나가 기반 오버로드를 전부 가림
```
틀린 결과:     골드 0 (기대 500), 아이템 2개 (기대 1). 아이템 목록에 500번
멈춘 위치:     box.give(500)에서 Step Into → Item::Item(int)로 들어감
진짜 원인:     EventMailbox가 give(const Item&)를 선언해 Mailbox::give(int)가 가려짐. 500은 explicit 없는 Item(int)로 변환
```
**수정:** `EventMailbox`에 `using Mailbox::give;` (그리고 `Item`의 생성자에 `explicit`)
**교훈:** 이름 찾기가 오버로드 결정보다 먼저다. 파생 클래스에서 같은 이름을 하나라도 선언하면 기반의 같은 이름은 모두 안 보인다. 보이는 후보가 하나뿐이고 암시적 변환이 가능하면 오류 없이 엉뚱한 함수가 불린다. 숫자 하나로 만드는 생성자에는 `explicit`.

## Lab 77 — `dynamic_cast` 결과의 nullptr 확인 누락
```
틀린 결과:     크래시 (액세스 위반 / SIGSEGV)
멈춘 위치:     Mage::restoreMana, this == nullptr → 호출 스택 한 칸 위 drinkManaPotions: unit은 Warrior, mage는 nullptr
진짜 원인:     포인터에 대한 dynamic_cast는 형식이 맞지 않으면 nullptr를 돌려준다. 확인 없이 호출
```
**수정:**
```cpp
if (Mage* mage = dynamic_cast<Mage*>(unit.get()))
{
    mage->restoreMana(amount);
    ++used;
}
```
**교훈:** `dynamic_cast<T*>`는 "형식이 맞는지 묻는" 연산이다. 결과를 확인하지 않을 거라면 질문할 이유가 없다. 실패를 예외로 받고 싶으면 참조 버전(`dynamic_cast<T&>`, 실패 시 `std::bad_cast`). 형식에 따라 분기가 많아지면 가상 함수로 옮길 신호다.

## 미포함 사유

- **다중 상속에서 `reinterpret_cast`/C 캐스트로 기반 포인터 변환**: 두 번째 기반의 오프셋을 무시하는 버그인데, 객체 배치(어느 기반이 어디에 놓이는지, 빈 기반 최적화)는 ABI마다 다르다. MSVC와 Itanium ABI(clang/gcc)에서 결과가 달라 판정을 고정할 수 없다.
- **소멸자(생성자)에서 순수 가상 함수 호출**: 정의되지 않은 동작이다. MSVC는 `_purecall`로 "R6025 pure virtual function call"을 띄우고, clang/gcc는 `__cxa_pure_virtual`로 abort하는 등 증상이 구현마다 다르다.
- **다이아몬드 상속, 접근 지정자가 다른 재정의**: 게임 코드에서 드물고, 이 부의 주제("엉뚱한 함수가 불린다")와 디버거로 보는 방법이 겹친다.

## 第N部: インターフェースと継承

仮想関数は「実際のオブジェクトの型に合った関数が呼ばれる」という約束です。この約束には例外がいくつもあります。
シグネチャーが1文字でも違えばオーバーライドではなく、値でコピーすれば派生部分が切り落とされ、構築中のオブジェクトはまだ派生型ではなく、デフォルト引数は仮想的には選ばれません。
どれもコンパイルは問題なく通り、結果は「別の関数が呼ばれた」です。

この部の共通の道具は、**ステップインで実際にどのクラスの関数に入るかを見ること** と、**ウォッチでオブジェクトの実際の型を見ること** です。

| 道具 | やり方 | いつ |
|---|---|---|
| ステップイン | 仮想呼び出しの行で1段入る | どのクラスの関数が呼ばれるか確認 (ラボ72, 75) |
| 止まらないブレークポイント | 派生クラスの関数にブレークポイント → 止まらなければそれが手がかり | オーバーライドされていない、オブジェクトが切られた (ラボ72, 73, 74) |
| 実際の型を見る | ウォッチ/ローカル ウィンドウでオブジェクトを展開し、型名とvtableを確認 | スライシング、コンストラクター内での型 (ラボ73, 74) |

## やってみよう: ラボ72(バックスタブ)

1. ラボ72を実行します。`[FAIL]`(背後からのバックスタブのダメージ 期待: 60、実際: 20)。
2. **期待を書きます。** オーガは背中を見せているので、バックスタブは 20 × 3 = 60。
3. `Backstab::damage` の中にブレークポイントを置きます。実行すると **止まりません。** 止まらないブレークポイントも手がかりです。
4. `useSkill` の `skill.damage(target)` の行にブレークポイントを置き、2回目(バックスタブ)で止まったらステップインします。`Skill::damage` に入ります。
5. 2つの宣言を並べて見ます。`virtual int damage(const Target&) const` と `virtual int damage(const Target& t)`。末尾の `const` がありません。
6. `Backstab::damage` に `override` を付けてビルドします。コンパイラーが「オーバーライドする関数がない」というエラーを出します。`const` を付けて直し、再実行して [PASS] を確認します。

## 解答の記録表

### Lab 72 — `const` が抜けてオーバーライドではなく隠蔽
```
間違った結果:   背後からのバックスタブ20(期待60)
止めた位置:     Backstab::damage のブレークポイントは止まらない → useSkill からステップイン → Skill::damage
本当の原因:     Backstab::damage に const がなく、Skill::damage(const Target&) const とは別の関数。Skill& で呼ぶと基底版
```
**修正:** `int damage(const Target& t) const override { ... }`
**教訓:** オーバーライドするつもりの関数には必ず `override`。付けた瞬間、`const` 漏れや引数型の違いをコンパイラーがエラーで教えてくれます。clang は `-Wall` で警告しますが、MSVC は既定の警告レベルでは何も言いません。

### Lab 73 — `vector<Monster>` に入れて Boss が切られる(スライシング)
```
間違った結果:   戦利品3個、黄金の王冠なし(期待4個)
止めた位置:     Boss::loot のブレークポイントは止まらない → collectLoot で wave[2] を展開すると型は Monster、rare_ がない
本当の原因:     wave.push_back(Boss(...)) が Boss の Monster 部分だけをコピーして格納する
```
**修正:** `std::vector<std::unique_ptr<Monster>>` と `std::make_unique<Boss>(...)` に変え、collectLoot も同じ型を受け取って `m->loot()`。
**教訓:** ポリモーフィックなオブジェクトはポインター(所有は `unique_ptr`)で格納します。値で受け取る関数引数も同じように切り落とします。基底クラスのコピーを `= delete` にしておくと、このミスはコンパイルエラーになります。

### Lab 74 — コンストラクター内の仮想呼び出し
```
間違った結果:   スナイパータワーの射程3(期待8)、距離7を撃てない
止めた位置:     Tower::baseRange のブレークポイント → 呼び出し履歴に Tower::Tower ← SniperTower::SniperTower
本当の原因:     基底のコンストラクターが動いている間、オブジェクトの動的な型はまだ Tower。仮想呼び出しも Tower 版に行く
```
**修正:** `int range() const { return baseRange(); }` と `canHit` で `range()` を使う(または `Tower(int range)` で派生クラスが値を渡す)。
**教訓:** コンストラクターとデストラクターの中では、「今作っている(壊している)クラス」の仮想関数が呼ばれます。規格で決まった動作なので、どのコンパイラーでも同じです。

### Lab 75 — 仮想関数のデフォルト引数は静的な型に従う
```
間違った結果:   プリーストの基本回復15(期待30)、パーティー合計25(期待40)。直接 priest.heal() は30
止めた位置:     Priest::heal の中、castDefaultHeal から入ったとき amount == 10
本当の原因:     どの heal が呼ばれるかは動的な型(Priest)で、デフォルト引数は静的な型(Healer)で決まる
```
**修正:** 既定値も仮想関数 `defaultAmount()` で問い合わせ、`castDefaultHeal` は `healer.heal(healer.defaultAmount())`。
**教訓:** 仮想関数にデフォルト引数を付けません。基底の既定値だけを25に変えると、ドルイド(18)で間違えます(隠しテスト)。

### Lab 76 — 派生クラスのオーバーロード1つが基底のオーバーロードをすべて隠す
```
間違った結果:   ゴールド0(期待500)、アイテム2個(期待1)。アイテム一覧に500番
止めた位置:     box.give(500) からステップイン → Item::Item(int) に入る
本当の原因:     EventMailbox が give(const Item&) を宣言したため Mailbox::give(int) が隠れ、500 は explicit のない Item(int) で変換された
```
**修正:** `EventMailbox` に `using Mailbox::give;`(そして `Item` のコンストラクターに `explicit`)
**教訓:** 名前探索はオーバーロード解決より先です。派生クラスで同じ名前を1つでも宣言すると、基底の同じ名前はすべて見えなくなります。

### Lab 77 — `dynamic_cast` の結果の nullptr 確認漏れ
```
間違った結果:   クラッシュ(アクセス違反 / SIGSEGV)
止めた位置:     Mage::restoreMana、this == nullptr → 呼び出し履歴の1つ上 drinkManaPotions: unit は Warrior、mage は nullptr
本当の原因:     ポインターに対する dynamic_cast は型が合わなければ nullptr を返す。確認せずに呼んだ
```
**修正:** `if (Mage* mage = dynamic_cast<Mage*>(unit.get())) { mage->restoreMana(amount); ++used; }`
**教訓:** `dynamic_cast<T*>` は「型が合うか尋ねる」演算です。結果を確認しないなら、尋ねる意味がありません。

## 対応表の行

| 種類 | 扱うラボ | 未収録 |
|---|---|---|
| インターフェースと継承 | 72 `override` なしでシグネチャーが違い隠蔽、73 スライシング、74 コンストラクター内の仮想呼び出し、75 仮想関数のデフォルト引数、76 オーバーロードの隠蔽(`using Base::f;`)、77 `dynamic_cast` の nullptr 確認漏れ | 多重継承で `reinterpret_cast`/Cキャストによる基底ポインター変換、デストラクター(コンストラクター)での純粋仮想関数呼び出し、ダイヤモンド継承、アクセス指定子の違うオーバーライド |
| オブジェクトの生成と破棄(修正後) | 12、15、16、40、73 スライシング、74 コンストラクター内の仮想呼び出し | デストラクターから投げた例外、デストラクターでの純粋仮想関数呼び出し |

未収録の理由: 多重継承でのキャストはオブジェクトの配置がABI(MSVCとclang/gcc)ごとに違い、判定を固定できません。デストラクターでの純粋仮想関数呼び出しは未定義動作で、症状が実装ごとに違います(MSVCは R6025、clang/gccは abort)。
