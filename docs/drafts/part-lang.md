# N부: C++ 언어 함정

이 부의 버그는 모두 **컴파일러가 받아들이는 코드**입니다. `std::move`가 복사가 되고, 넘친 정수가 음수가 되고, 소수점이 잘리고, 음수가 아주 큰 양수가 되고, 전역 변수가 0이고, 헤더의 변수가 둘로 갈라지고, 예외가 메모리를 흘리고, 소멸자의 예외가 프로그램을 끄고, 범위 for가 새 원소를 못 봅니다.
문법은 맞지만 언어 규칙을 하나 잘못 알고 있으면 생기는 버그입니다. 그래서 고치는 법보다 **규칙 이름을 아는 것**이 중요합니다. 각 랩의 힌트 2가 그 규칙입니다.

이 부의 공통 도구는 **조사식에 식을 그대로 넣어 계산 단계를 나눠 보기**(`baseExp * multiplier`, `static_cast<std::size_t>(x)`, `&g_saveStats`)와 **경고를 단서로 읽기**입니다.
몇몇 랩은 컴파일러가 이미 경고를 냅니다(87 축소 변환, 92 던지는 소멸자). 경고 목록을 먼저 보는 습관이 가장 싼 디버깅입니다.

> 3부 랩 20(연산자 우선순위)과 3부 끝의 연산자 랩, 2부 랩 3(정수 나눗셈)·14(`unsigned` 언더플로)와 이어집니다. 이 부는 "형식과 수명의 규칙"에 집중합니다.

## Lab 85 — `const`에 `std::move`는 복사, 옮긴 뒤 원본에 기대기
```
틀린 결과:     내 거래 창에 3개가 그대로 (기대 0), 복사 3번 (기대 0)
멈춘 위치:     Item의 복사 생성자 중단점 → 호출 스택 한 칸 위 trade의 push_back(const Item&)
진짜 원인:     from이 const Trader&라 item은 const Item&. std::move(item)은 const Item&&가 되어 복사 생성자로 간다.
               그리고 옮겼더라도 원소를 옮긴 것이지 vector에서 지운 것이 아니다
```
**수정:**
```cpp
void trade(Trader& from, Trader& to)
{
    for (Item& item : from.offer)
        to.received.push_back(std::move(item));
    from.offer.clear();
}
```
**교훈:** `std::move`는 캐스트일 뿐 아무것도 옮기지 않는다. `const` 객체에 쓰면 조용히 복사가 된다. 옮겨진 객체는 "유효하지만 정해지지 않은 상태"라서 대입하거나 비우는 것만 안전하고, 크기나 내용에 기대면 안 된다(use-after-move). 정적 분석 도구에는 두 실수를 모두 찾는 검사가 있다.

## Lab 86 — 부호 있는 정수 오버플로, 넘친 뒤에 하는 검사
```
틀린 결과:     경험치 -2144967296 (기대 2000000000)
멈춘 위치:     addExp의 if 줄, 조건부 중단점 total < 0. current 1950000000, baseExp * multiplier 200000000
진짜 원인:     int 덧셈이 넘쳐 음수가 됐고, 상한 검사는 이미 망가진 값을 본다
```
**수정:**
```cpp
long long total = static_cast<long long>(current) + static_cast<long long>(baseExp) * multiplier;
if (total > kMaxExp)
    total = kMaxExp;
return static_cast<int>(total);
```
**교훈:** 부호 있는 정수의 오버플로는 정의되지 않은 동작이다. 대개 음수로 돌아가지만 컴파일러는 "넘치지 않는다"고 가정해도 되므로, `if (a + b < a)` 같은 "넘쳤는지 보는" 검사는 Release에서 통째로 지워지기도 한다(이 저장소의 랩은 그런 검사를 쓰지 않아 구성마다 결과가 같다). 검사는 넘치기 **전에**: 더 넓은 형식으로 계산하거나 `std::numeric_limits<int>::max() - current < gain`처럼 남은 여유를 본다. 넘친 뒤 `total < 0`을 보는 땜질은 곱셈이 넘쳐 양수로 돌아오는 경우(숨은 테스트)를 놓친다.

## Lab 87 — 축소 변환 두 곳 (`double`→`int`, `int`→`short`)
```
틀린 결과:     물약 1개 은화 114 (기대 115), 300개 묶음 -31336 (기대 34500)
멈춘 위치:     toSilver의 return 줄, 조사식 gold * 100 = 114.99999999999999 / sellBundle에서 toSilver(unitGold) * count와 record.totalSilver
진짜 원인:     1.15는 2진수로 정확히 나타낼 수 없어 1.1499...로 저장되고, double→int는 버림. 총액 필드가 short라 34200이 잘림
```
**수정:** `return static_cast<int>(std::lround(gold * 100));`, `SaleRecord::totalSilver`를 `int`로
**교훈:** `=`와 `return`의 축소 변환은 경고만 나거나(MSVC C4244) 아무 말이 없다. 중괄호 초기화(`int silver{ gold * 100 };`)는 축소 변환을 컴파일 오류로 만들어 두 곳을 한 번에 찾아 준다. 돈은 처음부터 가장 작은 단위의 정수로 들고 다닌다. `+ 1`로 맞춘 땜질은 2.5골드(정확히 250)에서 틀린다.

## Lab 88 — `std::min<std::size_t>`가 음수를 아주 큰 양수로
```
틀린 결과:     궁수 진(평균보다 12 높음) 보너스 20 (기대 0)
멈춘 위치:     levelBonus, 조건부 중단점 myLevel > average. average - myLevel = -12, size_t로는 18446744073709551604
진짜 원인:     컴파일 오류를 피하려고 std::min의 형식을 std::size_t로 정해 두어 음수가 부호 없는 수로 변환됨
```
**수정:** `return std::clamp(average - myLevel, 0, static_cast<int>(maxBonus));`
**교훈:** 부호 있는 값과 없는 값이 만나면 부호 있는 쪽이 부호 없는 형식으로 바뀐다(`-1 < v.size()`가 false인 것과 같은 규칙). 형식이 안 맞아 나는 컴파일 오류를 캐스트로 누르면 그 오류가 알려 주던 문제가 숨는다. 섞어 비교해야 하면 C++20 `std::cmp_less` 등을 쓴다.

## Lab 89 — 두 파일의 전역 변수가 서로를 씀 (초기화 순서)
```
틀린 결과:     전사 체력 0 (기대 300). 파일 순서를 바꿔 빌드하면 보스 공격력 0
멈춘 위치:     g_warriorHp 초기화 줄 중단점, 호출 스택에 main이 없음. 그때 g_baseHp == 0
진짜 원인:     번역 단위 사이의 전역 초기화 순서는 정해져 있지 않다(보통 링크 순서). 두 파일이 서로의 값을 쓰므로 어느 쪽이 먼저든 하나는 0을 읽는다
```
**수정:** 전역 변수 여덟 개를 함수 지역 static으로.
```cpp
int baseAttack() { static const int value = readStat("base_attack", 12); return value; }
int bossAttack() { static const int value = baseAttack() * 4; return value; }
// 나머지 여섯 개도 같은 모양
```
**교훈:** 다른 파일의 전역 객체에 기대는 전역 초기화는 순서에 맡긴 도박이다. 함수 안의 static은 처음 불릴 때 만들어지고(C++11부터 스레드 안전) 의존하는 쪽이 부르는 순간 준비된다. 컴파일할 때 정할 수 있는 값이면 `constexpr`/`constinit`이 가장 좋다. 이 랩은 두 방향으로 의존하게 만들어, 링크 순서가 바뀌어도 버그 상태가 늘 FAIL이다. 화면의 두 값만 상수로 박는 땜질은 숨은 테스트의 다른 두 값에서 걸린다.

## Lab 90 — 헤더의 `static` 변수가 파일마다 따로
```
틀린 결과:     저장 횟수 0, 마지막 슬롯 "" (기대 3, "auto-용의 둥지")
멈춘 위치:     lg06_autosave.cpp의 ++g_saveStats.count와 showSaveScreen에서 &g_saveStats가 서로 다름
```

## Lab 92 — 소멸자에서 던져 `std::terminate`
```

```
**수정:** 실패할 수 있는 쓰기를 `close()`로 꺼낸다.
```cpp
void close()
{
    if (buffer_.size() > freeBytes_)
        throw SaveError(i18n::L("디스크 공간이 모자란다", "ディスク容量が足りない"));
    g_disk[slot_] = buffer_;
    closed_ = true;
}
~SaveFile()
{

    {
        try { close(); } catch (...) {}
    }
}

```

## Lab 93 — 범위 for는 범위를 처음 한 번만 평가한다
```
틀린 결과:     이번 차례 완료 1 (기대 3), 일지 3개 (기대 5)
멈춘 위치:     endTurn의 for. 반복은 두 번, 그 사이 log.size()는 3으로 늘었다. &q는 일지 안이 아니라 entries()가 돌려준 사본 안
진짜 원인:     범위 for는 log.entries()를 한 번 평가하고 그 begin/end를 잡아 둔다. 반복 중에 일지에 붙은 퀘스트는 사본에도, 잡아 둔 끝 안에도 없다
```
**수정:**
```cpp
for (std::size_t i = 0; i < log.size(); ++i)
{
    const Quest q = log.at(i);   // 복사로 받는다 (complete 안의 push_back이 재할당해도 안전)
    if (q.done || achieved.count(q.goal) == 0)
        continue;
    log.complete(q.name, book);
    ++completed;
}
```
**교훈:** 범위 for는 `auto&& r = 범위식; auto b = r.begin(); auto e = r.end();`로 펼쳐진다. 반복 중에 커지는 컨테이너는 인덱스로 돌고 매번 `size()`를 다시 읽는다. `entries()`가 참조를 돌려주게 바꾸는 것은 답이 아니다. 반복 중인 vector에 push_back하면 끝 이터레이터가 무효가 되고(정의되지 않은 동작), 재할당이 일어나면 `q`도 해제된 메모리를 가리킨다(랩 10).

> 설계 메모: 처음에는 `vector`를 직접 범위 for로 돌며 `reserve`해 둔 뒤 push_back하는 랩으로 만들었다. 그런데 이것은 끝 이터레이터 무효화(정의되지 않은 동작)라, 같은 MSVC STL Debug에서도 MSVC로 빌드하면 FAIL, clang++로 빌드하면 "vector iterators incompatible" 어설션으로 CRASH가 되었다. 판정이 컴파일러마다 달라 지금처럼 "사본을 도는" 정의된 형태로 바꾸고, 무효화는 힌트와 교훈에 남겼다.

## 解答の記録表

### Lab 85 — `const` への `std::move` はコピー、移動後の元に頼る
```
間違った結果:   自分のトレード画面に3個がそのまま(期待0)、コピー3回(期待0)
止めた位置:     Item のコピーコンストラクターのブレークポイント → 呼び出し履歴の1つ上、trade の push_back(const Item&)
本当の原因:     from が const Trader& なので item は const Item&。std::move(item) は const Item&& になりコピーコンストラクターへ行く。
                さらに、移動できても要素を移動しただけで vector から消してはいない
```
**修正:** `trade(Trader& from, Trader& to)`、`for (Item& item : from.offer)`、最後に `from.offer.clear();`
**教訓:** `std::move` はキャストにすぎず、何も移動しません。`const` オブジェクトに使うと黙ってコピーになります。移動されたオブジェクトは「有効だが未規定の状態」なので、代入するか空にすることだけが安全です(use-after-move)。

### Lab 86 — 符号付き整数のオーバーフロー、オーバーフロー後のチェック
```
間違った結果:   経験値 -2144967296(期待 2000000000)
止めた位置:     addExp の if の行、条件付きブレークポイント total < 0。current 1950000000、baseExp * multiplier 200000000
本当の原因:     int の足し算がオーバーフローして負の数になり、上限チェックはすでに壊れた値を見ている
```
**修正:** `long long` で計算し(掛ける前に広げる)、上限で切り詰めてから `int` で返す。
**教訓:** 符号付き整数のオーバーフローは未定義動作です。コンパイラーは「オーバーフローしない」と仮定してよいので、`if (a + b < a)` のようなチェックは Release で丸ごと消えることがあります。チェックはオーバーフローする **前に** 行います。後から `total < 0` を見るつぎはぎは、掛け算があふれて正の数に戻る場合(隠しテスト)を見逃します。

### Lab 87 — 縮小変換が二か所(`double`→`int`、`int`→`short`)
```
間違った結果:   ポーション1個の銀貨 114(期待115)、300個まとめ売り -31336(期待34500)
止めた位置:     toSilver の return の行、ウォッチ gold * 100 = 114.99999999999999 / sellBundle で toSilver(unitGold) * count と record.totalSilver
本当の原因:     1.15 は2進数で正確に表せず 1.1499... として保存され、double→int は切り捨て。総額のフィールドが short なので 34200 が切り落とされる
```
**修正:** `return static_cast<int>(std::lround(gold * 100));`、`SaleRecord::totalSilver` を `int` に。
**教訓:** `=` や `return` の縮小変換は警告だけか、何も言われません。波かっこ初期化(`int silver{ gold * 100 };`)は縮小変換をコンパイルエラーにして、二か所を一度に見つけてくれます。`+ 1` で合わせるつぎはぎは 2.5 ゴールド(ちょうど250)で間違えます。

### Lab 88 — `std::min<std::size_t>` が負の数をとても大きな正の数に
```
間違った結果:   弓使いジン(平均より12高い)のボーナス20(期待0)
止めた位置:     levelBonus、条件付きブレークポイント myLevel > average。average - myLevel = -12、size_t では 18446744073709551604
本当の原因:     コンパイルエラーを避けるため std::min の型を std::size_t に決めたので、負の数が符号なしに変換された
```
**修正:** `return std::clamp(average - myLevel, 0, static_cast<int>(maxBonus));`
**教訓:** 符号付きと符号なしの値が出会うと、符号付きの方が符号なしの型に変わります(`-1 < v.size()` が false になるのと同じ規則)。型の不一致によるコンパイルエラーをキャストで黙らせると、エラーが知らせていた問題が隠れます。

### Lab 89 — 二つのファイルのグローバル変数が互いを使う(初期化順序)
```
間違った結果:   戦士のHP 0(期待300)。ファイル順を変えてビルドするとボスの攻撃力が0
止めた位置:     g_warriorHp の初期化の行のブレークポイント、呼び出し履歴に main がない。そのとき g_baseHp == 0
本当の原因:     翻訳単位の間のグローバル初期化の順序は決まっていない(普通はリンク順)。二つのファイルが互いの値を使うので、どちらが先でも一方は0を読む
```
**修正:** グローバル変数八つを関数ローカルの static に(`int baseAttack() { static const int value = readStat("base_attack", 12); return value; }` など)。
**教訓:** 別のファイルのグローバルオブジェクトに頼るグローバル初期化は、順序任せの賭けです。関数の中の static は最初に呼ばれたときに作られ、依存する側が呼んだ瞬間に用意されます。

### Lab 90 — ヘッダーの `static` 変数がファイルごとに別々
```
間違った結果:   セーブ回数0、最後のスロット ""(期待3、"auto-용의 둥지")
止めた位置:     lg06_autosave.cpp の ++g_saveStats.count と showSaveScreen で &g_saveStats が異なる
本当の原因:     名前空間スコープの static は内部リンケージ。ヘッダーをインクルードした .cpp ごとに別の g_saveStats ができる
```
**修正:** ヘッダーで `inline SaveStats g_saveStats;`(C++17 の inline 変数)。または `extern` 宣言と .cpp 一か所での定義。
**教訓:** ヘッダーに定義を置くときの `static` は「一つだけ」ではなく「ファイルごとに一つずつ」です。コンパイラーもリンカーも警告しません。

### Lab 91 — 例外の経路でだけ漏れるテクスチャー
```
間違った結果:   残ったテクスチャー2個(期待0)
止めた位置:     Texture のコンストラクター/デストラクターのブレークポイント: 生成6回、破棄4回。残った二つは「呪われた城」
本当の原因:     loadDungeon がテクスチャーを new した後で countRooms が投げると、生ポインター floor/walls だけが消えて Texture は残る
```
**修正:** `std::make_unique<Texture>(...)` で受け、`Dungeon` を作るときに `release()`(さらに良いのは Dungeon のメンバーも `unique_ptr` にすること)。
**教訓:** 例外が起きるとその間の関数の残りの行は実行されず、デストラクターが呼ばれるのはスタックのオブジェクトだけです。資源は作ったらすぐ所有オブジェクト(RAII)に任せます。

### Lab 92 — デストラクターから投げて `std::terminate`
```
間違った結果:   CRASH、abort()(セーブ失敗のメッセージが出ない)
止めた位置:     例外が投げられた ~SaveFile。呼び出し履歴の下に saveGame の catch ではなく std::terminate
本当の原因:     C++11 からデストラクターは暗黙の noexcept。noexcept の関数の外へ出ようとする例外は catch を探さず terminate
```
**修正:** 失敗しうる書き込みを `close()` に出し、`saveGame` の try の最後で `file.close()`。デストラクターは閉じていなければ `try { close(); } catch (...) {}`。
**教訓:** デストラクターは失敗を知らせる手段がない場所です。`noexcept(false)` にするつぎはぎは、別の例外でスタックを巻き戻している最中にデストラクターがさらに投げると、やはり terminate です(隠しテスト)。

### Lab 93 — 範囲 for は範囲を最初に一度だけ評価する
```
間違った結果:   今回のターンの完了1(期待3)、日誌3個(期待5)
止めた位置:     endTurn の for。ループは2回、その間に log.size() は3に増えた。&q は日誌の中ではなく entries() が返したコピーの中
本当の原因:     範囲 for は log.entries() を一度評価し、その begin/end を取っておく。ループ中に日誌に追加されたクエストはコピーにも、取っておいた終端の内側にもない
```
**修正:** `for (std::size_t i = 0; i < log.size(); ++i) { const Quest q = log.at(i); ... }`
**教訓:** 範囲 for は `auto&& r = 範囲式; auto b = r.begin(); auto e = r.end();` に展開されます。ループ中に大きくなるコンテナーはインデックスで回し、毎回 `size()` を読み直します。`entries()` が参照を返すように変えるのは答えではありません(終端イテレーターの無効化、未定義動作)。
