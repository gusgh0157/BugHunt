## README: 부 소개

# N부: 직렬화 (JSON/XML)

세이브, 설정, 데이터 표는 거의 다 JSON이나 XML입니다. 라이브러리는 대부분 "친절하게" 동작합니다.
없는 키를 물으면 만들어 주고, 실수를 정수로 달라면 잘라 주고, 없는 노드를 찾으면 빈 노드를 돌려줍니다. 예외도 경고도 없습니다.
그 친절함이 버그를 숨깁니다. 이 부에서는 **라이브러리가 조용히 해 준 일**을 디버거로 드러냅니다.

- 쓰는 라이브러리: nlohmann/json (`json`, `ordered_json`), pugixml (`xml_document`, `xml_node`, `xml_attribute`)
- 조사식에서 `json` 값은 내부 구조(`m_data`)로 보입니다. `j.dump()`나 `j.size()`를 계산할 수 없으면 임시 출력 줄을 넣으세요.
- XML 보안(외부 엔티티/XXE, 엔티티 폭탄)은 랩으로 만들지 않고 해답 참고에만 적었습니다. pugixml은 DTD의 외부 엔티티를 처리하지 않습니다.

## N부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 앞뒤 비교 | 같은 객체를 두 지점에서 조사식으로(`save.size()`, `save.dump()`) | "읽기만 했는데 바뀌었다" (랩 65) |
| 조건부 중단점 | `w.name == "단검"` | 표의 한 행만 틀릴 때 (랩 66) |
| 바이트 보기 | `(int)(unsigned char)s[i]`, 메모리 창 | 인코딩이 깨졌을 때 (랩 68) |
| 자릿수 넉넉히 보기 | 디버거의 float 표시 vs 저장된 문자열 | 왕복 오차 (랩 69) |
| 빈 노드 확인 | 조사식에 `node.child("hp").empty()`, `node.attribute("hp").value()` | 값이 조용히 0일 때 (랩 70) |
| 파서 오류 위치 | `result.description()`, `xml.c_str() + result.offset` | 문서가 통째로 안 읽힐 때 (랩 71) |

## 따라 해 보기: 랩 65 (펫 슬롯)

1. 랩 65를 실행합니다. 펫 칸은 "(펫 없음)"인데 `[FAIL] 소환 버튼 (기대: false, 실제: true)`, 다시 저장한 세이브 끝에 `"pet":null`이 붙어 있습니다.
2. **기대를 적습니다.** 세이브를 읽기만 했으니 키는 3개 그대로여야 합니다.
3. `petLabel(save)` 줄과 `canSummonPet(save)` 줄에 중단점을 겁니다. 첫 중단점에서 조사식에 `save.size()`를 넣습니다. 3입니다.
4. 계속 실행해 두 번째 중단점에서 다시 봅니다. 4입니다. 그 사이에 실행된 것은 `petLabel` 하나뿐입니다.
5. `petLabel` 안으로 들어가 `if` 줄을 한 줄씩 넘기며 `save.size()`를 봅니다. `save["pet"]`을 계산하는 순간 늘어납니다.
6. `save.contains("pet")`으로 바꾸고 다시 실행합니다. 4부 랩 29(`map::operator[]`)와 같은 원리입니다.

## SOLUTIONS 기록표

## Lab 65 — `json::operator[]`가 없는 키를 null로 만듦
```
틀린 결과:     소환 버튼 켬 (기대 끔), 다시 저장한 세이브에 "pet":null 추가
멈춘 위치:     petLabel 전후, 조사식 save.size() 3 → 4
처음 어긋난 줄: if (save["pet"].is_null())
진짜 원인:     const가 아닌 json의 []는 없는 키를 null로 삽입한다 (std::map::operator[]와 같음)
```
**수정:** `if (!save.contains("pet"))` (읽기만 하는 함수는 `const json&`로 받고 `contains`/`find`/`at`)
**교훈:** "있는지 확인"과 "꺼내기"를 구분한다. const json에 없는 키로 `[]`를 쓰는 것은 정의되지 않은 동작(Debug에서는 assert)이므로 const로 바꾸기만 해서는 안 되고 `contains`로 확인한다.

## Lab 66 — `value("crit", 1)`이 int로 읽어 1.5를 1로 자름
```
틀린 결과:     단검 치명타 30 (기대 45). 도끼(정수 2)와 지팡이(없음)는 정상
멈춘 위치:     loadWeapon의 return, 조건 w.name == "단검" → w.crit == 1
진짜 원인:     value()의 반환 형식은 기본값 1(int)이 정한다. nlohmann은 실수 → 정수 변환에서 예외 없이 자른다
```
**수정:** `w.crit = j.value("crit", 1.0);` (또는 `j.value<double>("crit", 1)`)
**교훈:** 라이브러리의 변환 함수는 "형식을 어디서 정하는지" 확인한다. `get<int>()`도 1.5를 1로 조용히 자른다. 정수로 저장되던 값을 실수로 바꾸는 데이터 패치에서 잘 터진다. 반올림 땜질은 1.75, 2.25에서 다시 틀린다(숨은 테스트).

## Lab 67 — `json`이 키를 정렬해서 순서가 사라짐
```
틀린 결과:     불러온 순서 "번개 얼음창 치유 화염구" (기대 "화염구 얼음창 번개 치유"), 저장 후에도 정렬됨
멈춘 위치:     loadSkillBar의 for, j를 펼쳐 보면 이미 정렬되어 있음
진짜 원인:     nlohmann::json의 객체는 std::map(키 정렬)에 담긴다. JSON 표준도 객체 키 순서에 의미를 두지 않는다
```
**수정:** `using Json = nlohmann::ordered_json;` (읽기와 저장이 함께 바뀜)
**교훈:** 순서가 의미 있는 데이터는 배열로 저장하는 것이 정석이다. 객체 키 순서에 기대면 라이브러리·언어를 바꿀 때마다 깨진다. 한글 키는 UTF-8 바이트순으로 정렬되어 "가나다순처럼 보이지만 아닌" 결과가 나오기도 한다.

## Lab 68 — UTF-8을 바이트로 잘라 `dump`가 예외를 던짐
```
틀린 결과:     "Lv99용감한전사" 저장 실패: [json.exception.type_error.316] incomplete UTF-8 string; last byte: 0x95
멈춘 위치:     catch 블록 → clampName의 return에서 마지막 바이트 확인 (0xED 0x95 = "한"의 앞 2바이트)
진짜 원인:     4 + 3 + 3 = 10바이트 뒤 "한"(3바이트)의 중간인 12바이트에서 잘림
```
**수정:**
```cpp
size_t cut = kMaxNameBytes;
while (cut > 0 && (static_cast<unsigned char>(name[cut]) & 0xC0) == 0x80)
    --cut;
return name.substr(0, cut);
```
**교훈:** 바이트 수 제한은 글자 경계에서 자른다(이어지는 바이트는 `10xxxxxx`). `dump`의 오류 처리기(`error_handler_t::replace/ignore`)로 예외만 막으면 깨진 이름이 화면과 서버에 남는다. CP949로 읽은 문자열을 그대로 넣어도 같은 예외(type_error 316)가 난다. 원인은 "JSON에 UTF-8이 아닌 바이트가 들어갔다"로 같다.

## Lab 69 — 기본 정밀도 6자리로 float 왕복 손실
```
틀린 결과:     저장한 문자열 {"x":1234.57,"y":-87.6543,"z":3.33333} → 불러온 위치가 1234.56995 등으로 달라짐
멈춘 위치:     savePosition의 return (out.str()), 디버거의 p.x 표시(1234.56775)와 비교
진짜 원인:     ostream의 기본 정밀도는 유효 숫자 6자리. float을 정확히 되살리려면 max_digits10(9)자리가 필요
```
**수정:** `out << std::setprecision(std::numeric_limits<float>::max_digits10);` (`<limits>`) 또는 json 객체에 넣어 `dump()`
**교훈:** 사람이 읽는 출력과 다시 읽을 저장은 다르다. 저장은 왕복(round-trip)이 보장되는 형식으로. `std::fixed`는 소수점 아래 자릿수라 0.0003141 같은 작은 값을 망친다. 숨은 테스트는 7~8자리로는 부족한 값도 넣었다(MSVC와 clang에서 같은 결과를 확인).

## Lab 70 — 속성을 자식 요소로 읽어 빈 노드의 0
```
틀린 결과:     모든 몬스터 HP 0 (공격력은 정상)
멈춘 위치:     m.hp = ... 줄, 조사식 node.child("hp").empty() == true, node.attribute("hp").value() == "320"
진짜 원인:     hp는 속성(hp="320")인데 child("hp")로 찾음 → 빈 노드 → as_int() 0
```
**수정:** `m.hp = node.attribute("hp").as_int();`
**교훈:** pugixml은 없는 노드/속성에 예외 대신 빈 객체를 돌려준다. 오타, 대소문자("Attack"/"attack"), 속성/자식 혼동이 모두 조용한 0이 된다. 필수 값은 `if (!attr)`로 확인하고 데이터 오류로 알린다.

## Lab 71 — 이스케이프하지 않고 이어 붙인 XML
```
틀린 결과:     길드 목록 읽기 실패: Error parsing element attribute → 0개 (기대 3)
멈춘 위치:     loadGuilds 실패 쪽, xml.c_str() + result.offset → "방패>..." 부분
진짜 원인:     이름 "<검과 방패>"의 <가 새 태그 시작으로 해석됨
```
**수정:** 이름을 넣기 전에 `&` → `&amp;`(가장 먼저), `<` → `&lt;`, `>` → `&gt;`, `"` → `&quot;`, `'` → `&apos;` (또는 pugixml로 문서를 만들어 `doc.save()`)
**교훈:** 문자열 이어 붙이기로 구조화된 형식(XML, JSON, SQL, HTML)을 만들면 이스케이프를 빠뜨린다. 더 무서운 경우는 오류가 없는 쪽이다: 이름 "I &lt;3 PvP"는 "I <3 PvP"로 조용히 바뀐다(숨은 테스트). pugixml은 짝 없는 `&`를 너그럽게 넘겨서 "Tom & Jerry"는 읽히지만, 다른 파서에서는 오류다.
**참고(보안):** 외부에서 받은 XML을 읽을 때는 외부 엔티티(XXE)와 엔티티 확장 폭탄을 조심한다. pugixml은 DTD 안의 엔티티를 처리하지 않아 이 두 공격에 해당하지 않지만, 다른 파서(libxml2, MSXML, .NET의 예전 기본값)는 설정에 따라 파일을 읽거나 메모리를 다 쓸 수 있다.

## 미포함 사유

- **세이브 호환성, 문화권 파싱**: 사용자 결정으로 제외.
- **큰 정수 정밀도**: nlohmann은 정수를 int64/uint64로 정확히 보관하므로, 버그를 만들려면 일부러 `get<double>()`을 거치거나 JavaScript 같은 다른 언어의 쓰기 쪽이 필요하다. C++ 단독 랩으로는 억지스러워 해설로만 둔다.
- **공백 텍스트 노드**: pugixml 기본 설정이 공백만 있는 PCDATA를 버려서, 버그를 재현하려면 파싱 옵션을 일부러 바꿔야 한다. 다른 파서와 동작이 달라 "라이브러리 설정 문제"에 가깝다.
- **XXE/엔티티 폭탄**: 보안 주제이고 pugixml에서는 재현되지 않는다. 랩 71 해답의 참고로만.

## 第N部: シリアライズ (JSON/XML)

セーブ、設定、データ表のほとんどはJSONかXMLです。ライブラリの多くは「親切に」動きます。
ないキーを尋ねれば作ってくれ、小数を整数で欲しいと言えば切り捨ててくれ、ないノードを探せば空のノードを返してくれます。例外も警告もありません。
その親切さがバグを隠します。この部では **ライブラリが黙ってやったこと** をデバッガーで明らかにします。

- 使うライブラリ: nlohmann/json(`json`、`ordered_json`)、pugixml(`xml_document`、`xml_node`、`xml_attribute`)
- ウォッチでは `json` の値は内部構造(`m_data`)として見えます。`j.dump()` や `j.size()` を評価できなければ、一時的な出力行を入れてください。
- XMLのセキュリティ(外部エンティティ/XXE、エンティティ爆弾)はラボにせず、解答の参考にだけ書きました。

## 解答の記録表

### Lab 65 — `json::operator[]` がないキーを null で作る
```
間違った結果:   召喚ボタン有効(期待は無効)、保存し直したセーブに "pet":null が追加
止めた位置:     petLabel の前後、ウォッチ save.size() 3 → 4
最初にずれた行: if (save["pet"].is_null())
本当の原因:     const でない json の [] は、ないキーを null で挿入する(std::map::operator[] と同じ)
```
**修正:** `if (!save.contains("pet"))`
**教訓:** 「あるか確認する」と「取り出す」を区別します。const json にないキーで `[]` を使うのは未定義動作なので、const にするだけでなく `contains` で確認します。

### Lab 66 — `value("crit", 1)` が int で読んで1.5を1に切り捨てる
```
間違った結果:   短剣のクリティカル30(期待45)。斧(整数2)と杖(なし)は正常
止めた位置:     loadWeapon の return、条件 w.name == "단검" → w.crit == 1
本当の原因:     value() の戻り値の型は既定値1(int)が決める。nlohmann は小数 → 整数の変換で例外を出さずに切り捨てる
```
**修正:** `w.crit = j.value("crit", 1.0);`
**教訓:** ライブラリの変換関数は「型をどこで決めるか」を確認します。四捨五入のその場しのぎは1.75、2.25でまた間違えます(隠しテスト)。

### Lab 67 — `json` がキーを並べ替えて順番が消える
```
間違った結果:   読み込んだ順番が辞書順(UTF-8バイト順)、保存後も並べ替えられる
止めた位置:     loadSkillBar の for、j を展開するとすでに並べ替えられている
本当の原因:     nlohmann::json のオブジェクトは std::map(キー順)に入る。JSONの規格もキーの順番に意味を持たせない
```
**修正:** `using Json = nlohmann::ordered_json;`
**教訓:** 順番に意味があるデータは配列で保存するのが定石です。

### Lab 68 — UTF-8をバイトで切って `dump` が例外を投げる
```
間違った結果:   "Lv99용감한전사" の保存失敗: [json.exception.type_error.316] incomplete UTF-8 string
止めた位置:     catch ブロック → clampName の return で最後のバイトを確認
本当の原因:     4 + 3 + 3 = 10バイトの後の3バイト文字の途中、12バイト目で切れた
```
**修正:** 切る位置が後続バイト(`(b & 0xC0) == 0x80`)の間は前に戻る。
**教訓:** バイト数の制限は文字の境界で切ります。`dump` のエラーハンドラーで例外だけを止めると、壊れた名前が画面とサーバーに残ります。CP949の文字列をそのまま入れても同じ例外になります。

### Lab 69 — 既定精度6桁で float の往復が壊れる
```
間違った結果:   保存した文字列 {"x":1234.57,...} → 読み込んだ位置がずれる
止めた位置:     savePosition の return(out.str())、デバッガーの p.x 表示(1234.56775)と比較
本当の原因:     ostream の既定精度は有効数字6桁。float を正確に復元するには max_digits10(9)桁が必要
```
**修正:** `out << std::setprecision(std::numeric_limits<float>::max_digits10);`
**教訓:** 人が読む出力と、読み直す保存は別物です。保存は往復が保証される形式で。`std::fixed` は小さい値を壊します。

### Lab 70 — 属性を子要素として読んで空のノードの0
```
間違った結果:   すべてのモンスターのHPが0(攻撃力は正常)
止めた位置:     m.hp = ... の行、ウォッチ node.child("hp").empty() == true、node.attribute("hp").value() == "320"
本当の原因:     hp は属性(hp="320")なのに child("hp") で探した → 空のノード → as_int() は0
```
**修正:** `m.hp = node.attribute("hp").as_int();`
**教訓:** pugixml はないノード/属性に例外ではなく空のオブジェクトを返します。タイプミス、大文字小文字、属性と子要素の取り違えはすべて黙った0になります。

### Lab 71 — エスケープせずに連結したXML
```
間違った結果:   ギルド一覧の読み込み失敗 → 0件(期待3)
止めた位置:     loadGuilds の失敗側、xml.c_str() + result.offset
本当の原因:     名前 "<검과 방패>" の < が新しいタグの始まりとして解釈された
```
**修正:** 名前を入れる前に `&`(最初に)、`<`、`>`、`"`、`'` をエスケープする(または pugixml で文書を組み立てて `doc.save()`)。
**教訓:** 文字列の連結で構造化された形式(XML、JSON、SQL、HTML)を作るとエスケープを忘れます。もっと怖いのはエラーにならない場合で、"I &lt;3 PvP" は黙って "I <3 PvP" に変わります。
**参考(セキュリティ):** 外部から受け取ったXMLを読むときは、外部エンティティ(XXE)とエンティティ展開爆弾に注意します。pugixml はDTD内のエンティティを処理しませんが、他のパーサーは設定によって危険です。
