# N부: 파일 입출력

파일 입출력 버그는 "파일은 멀쩡한데 프로그램이 다르게 읽는" 경우가 대부분입니다. 크래시도 없고 예외도 없습니다.
스트림은 실패해도 조용히 상태 비트만 켜고, 경로는 실행한 위치에 따라 다른 파일을 가리키고, 쓴 내용은 버퍼에 머물러 있습니다.
그래서 이 부에서는 변수 대신 **스트림의 상태**와 **디스크에 실제로 있는 바이트**를 함께 봅니다.

- 모든 랩은 `임시 폴더/BugHunt/<랩 이름>/` 아래에만 파일을 만들고, 끝나면 지웁니다(`std::filesystem::temp_directory_path()`).
  중단점에서 멈춰 있는 동안에는 파일이 남아 있으니 탐색기나 편집기로 직접 열어 볼 수 있습니다.
- 판정은 운영체제와 컴파일러에 상관없이 같도록 만들었습니다. 그래서 OS마다 결과가 다른 주제(텍스트 모드 줄바꿈 변환 등)는 "미포함"에 이유와 함께 적었습니다.

|---|---|---|

| 문자열의 바이트 보기 | 조사식에 `s.size()`, `(int)(unsigned char)s[0]`, 메모리 창에 `s.data()` | 보이는 글자와 실제 바이트가 다를 때 (랩 63의 BOM) |

## 따라 해 보기: 랩 60 (점수판)

1. 랩 60을 실행합니다. 순위표에 `4위 도윤 7100`이 한 번 더 나오고 `[FAIL] 순위표 줄 수 (기대: 3, 실제: 4)`.
2. **기대를 적습니다.** 파일은 세 줄. 루프는 세 바퀴 돌고, 네 번째 조건 검사에서 끝나야 합니다.
3. `loadScores`의 `scores.push_back` 줄에 중단점을 걸고 **조건부 중단점**으로 바꿉니다. 조건: `scores.size() == 3`.
4. 실행하면 네 번째로 넣으려는 순간에 멈춥니다. 조사식에 `in.eof()`, `in.fail()`, `name`, `points`를 넣습니다.
   `fail`은 true인데 `name`과 `points`는 여전히 도윤, 7100입니다. 읽기는 실패했고 변수는 지난 값 그대로입니다.
5. 조건을 `scores.size() == 2`로 바꿔 다시 실행하고, 세 번째 줄을 읽은 직후 `in.eof()`를 봅니다. false입니다.
   파일 끝의 줄바꿈 한 글자가 남아 있어서 아직 "끝을 넘어 읽으려다 실패한" 적이 없기 때문입니다.
6. `while (in >> name >> points)`로 바꾸고 다시 실행해 [PASS]를 확인합니다.
7. `pop_back()`으로 마지막 줄을 지우는 땜질은 화면에서는 통과하지만, 숨은 테스트(줄바꿈 없이 끝나는 파일, 빈 파일)에서 걸립니다.

## Lab 60 — `while (!in.eof())`로 마지막 기록이 두 번
```
틀린 결과:     4줄, 마지막에 "도윤 7100" 한 번 더, 총점 32100 (기대 25000)
멈춘 위치:     push_back, 조건 scores.size() == 3
기대값 → 실제값: 네 번째 바퀴는 없어야 함 / 실제 in.fail() == true인데 지난 값으로 push_back
진짜 원인:     eof()는 끝을 넘어 읽으려다 실패한 "뒤에" 켜진다. 마지막 줄바꿈이 남아 한 바퀴 더 돈다
```
**수정:** `while (in >> name >> points) scores.push_back({ name, points });`
**교훈:** 읽기는 "읽고 → 성공했는지 확인 → 쓴다" 순서. 실패한 `>>`는 변수를 그대로 두므로(이 랩) 지난 값이 한 번 더 들어간다. `pop_back` 땜질은 줄바꿈 없이 끝나는 파일에서 진짜 기록을 지운다.

## Lab 61 — `>>` 뒤의 `getline`이 남은 줄바꿈을 읽음
```
틀린 결과:     첫 대사 "" (빈 줄), 셋째 대사 자리에 둘째 대사, 마지막 대사 없음
멈춘 위치:     push_back, 첫 바퀴 line.size() == 0
진짜 원인:     in >> count는 "3"까지만 읽고 줄바꿈을 남긴다. getline은 그 줄바꿈까지를 빈 줄로 읽는다
```
**수정:** `in >> count;` 다음에 `in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');` (`<limits>`)
**교훈:** `>>`(토큰 단위)와 `getline`(줄 단위)을 섞으면 경계의 줄바꿈을 직접 처리해야 한다. `in >> std::ws`도 통과처럼 보이지만 다음 줄 앞의 공백까지 먹어서 들여 쓴 대사를 망친다(숨은 테스트).

## Lab 62 — failbit가 남아 이후 읽기가 모두 무시됨
```
틀린 결과:     몬스터 3종, 보상 0개 (기대 3), 102번 보상 0
멈춘 위치:     in >> header 줄, 조사식 in.fail() == true
진짜 원인:     첫 while이 "보상"을 숫자로 읽으려다 실패 → failbit. 지우지 않아 header와 골드 읽기가 전부 그냥 넘어감
```
**수정:** `std::string header;` 앞에 `in.clear();`
**교훈:** 실패 표시는 저절로 꺼지지 않는다. 실패를 "예상한" 지점(섹션 끝)에서는 `clear()`로 지우고 계속 읽는다. `clear()`는 글자를 버리지 않으므로 실패를 일으킨 토큰("보상")은 그대로 다음 읽기에 들어간다.

## Lab 64 — 저장 도중 실패로 반쯤 쓴 세이브
```
틀린 결과:     저장 실패 뒤 불러온 아이템 3종 (기대 5종)
멈춘 위치:     writeItem의 throw 줄, 멈춘 채로 save.txt 열기 → 이미 지워지고 앞의 몇 줄만 있음
진짜 원인:     trunc로 여는 순간 옛 세이브가 지워지고, 예외로 빠져나갈 때 ofstream 소멸자가 앞부분만 쓴 파일을 닫는다
```
**수정:** 임시 파일에 끝까지 쓰고 닫은 뒤에만 바꿔치기한다.
```cpp
fs::path temp = file;
temp += ".tmp";
try
{
    {
        std::ofstream out(temp, std::ios::trunc);
        for (const Item& item : items)
            writeItem(out, item);
        out.close();
        if (!out)
            throw std::runtime_error("쓰기 실패");
    }
    fs::rename(temp, file);          // 같은 폴더 안에서 바꿔치기
    return true;
}
catch (const std::exception& e)
{
    std::cout << "  저장 실패: " << e.what() << '\n';
    std::error_code ec;
    fs::remove(temp, ec);            // 실패한 임시 파일 정리
    return false;
}
```
**교훈:** 저장은 "전부 아니면 전무"여야 한다. 새 내용은 임시 파일에, 성공한 뒤에만 `rename`. 임시 파일은 같은 폴더(같은 드라이브)에 둬야 rename이 복사 없이 바꿔치기가 된다. rename 전에 스트림을 닫아야 한다(열린 파일은 OS에 따라 이름을 바꿀 수 없다). 실제 게임에서는 전원이 꺼지는 경우까지 대비해 rename 전에 디스크 동기화(OS API)를 하기도 한다. 이 랩은 표준 C++ 범위에서 예외 경로만 다룬다.

## 미포함 사유

- **텍스트/바이너리 모드 `\r\n`**: Windows에서만 변환이 일어나고 Linux/macOS에서는 두 모드가 같다. 같은 코드가 OS에 따라 [PASS]/[FAIL]이 갈리므로 판정할 수 없다. 해설 후보: 텍스트 모드로 연 파일에서 `tellg`로 잰 위치를 바이너리 오프셋으로 쓰는 버그.
- **구조체 통째 저장(`write(&s, sizeof s)`)의 패딩**: 패딩과 `long` 크기, 정렬은 ABI(컴파일러·OS·비트 수)마다 다르다. "같은 빌드에서는 맞고 다른 빌드에서 깨진다"가 본질이라 한 실행 안의 판정으로 만들기 어렵다. 해설 후보: `sizeof`와 `offsetof`를 조사식으로 보는 법.
- **예외 경로의 핸들 누수(RAII 없음)**: 누수를 관찰하는 방법(열린 파일은 지울 수 없음, 핸들 수 세기)이 OS마다 다르다. Windows에서는 지우기 실패, POSIX에서는 지우기 성공이라 판정이 갈린다. 랩 64가 "예외 경로의 정리"를 대신 다룬다.
- **CP949와 UTF-8 혼용**: 표준 C++에는 CP949 변환기가 없어 랩 코드를 표준 라이브러리만으로 만들 수 없다. BOM(랩 63)이 "보이지 않는 인코딩 바이트"를 대신 다루고, 직렬화 부 랩 68(UTF-8 중간에서 자른 문자열)이 "잘못된 인코딩 → 저장 실패"를 다룬다.
- **동시 쓰기**: 결과가 스케줄링에 따라 달라져 판정을 고정할 수 없다.

## 第N部: ファイル入出力

ファイル入出力のバグの多くは「ファイルは無事なのに、プログラムの読み方が違う」ケースです。クラッシュも例外もありません。
ストリームは失敗しても黙って状態ビットを立てるだけで、パスは起動した場所によって別のファイルを指し、書いた内容はバッファーに留まっています。
そこでこの部では、変数と一緒に **ストリームの状態** と **ディスクに実際にあるバイト** を見ます。

- すべてのラボは `一時フォルダー/BugHunt/<ラボ名>/` の下にだけファイルを作り、終わったら削除します。ブレークポイントで止まっている間はファイルが残っているので、エクスプローラーやエディターで直接開けます。
- 判定はOSとコンパイラーに関係なく同じになるようにしました。OSによって結果が違うテーマ(テキストモードの改行変換など)は「未収録」に理由と一緒に書いています。

## やってみよう: ラボ60(スコアボード)

1. ラボ60を実行します。ランキングに `4位 ドユン 7100` がもう一度出て、`[FAIL]`(ランキングの行数 期待: 3、実際: 4)。
2. **期待を書きます。** ファイルは3行。ループは3周して、4回目の条件チェックで終わるはずです。
3. `loadScores` の `scores.push_back` 行にブレークポイントを置き、**条件付きブレークポイント** にします。条件: `scores.size() == 3`。
4. 実行すると、4件目を入れようとした瞬間に止まります。ウォッチに `in.eof()`、`in.fail()`、`name`、`points` を入れます。`fail` は true なのに、`name` と `points` はドユン、7100のままです。読み込みは失敗し、変数は前の値のままです。
5. 条件を `scores.size() == 2` に変えて再実行し、3行目を読んだ直後の `in.eof()` を見ます。false です。末尾の改行1文字が残っているので、まだ「末尾を越えて読もうとして失敗」していないからです。
6. `while (in >> name >> points)` に直して再実行し、[PASS] を確認します。
7. `pop_back()` で最後の行を消すその場しのぎは画面では通りますが、隠しテスト(改行なしで終わるファイル、空ファイル)で捕まります。

## 解答の記録表

### Lab 58 — 相対パスが作業ディレクトリ基準で開かれる
```
間違った結果:   ポーション100(期待120)、帰還の書 -1(価格表にない)
止めた位置:     loadPrices の std::ifstream 行
期待値 → 実際:  開くファイル game/data/prices.txt を期待 / 実際は workspace/data/prices.txt(古いコピー)
本当の原因:     "data/prices.txt" は実行ファイルのフォルダーではなく現在の作業ディレクトリ基準
```
**修正:** `std::ifstream in(gameDir() / "data/prices.txt");`
**教訓:** 作業ディレクトリはプログラムを起動した側(IDE、ショートカット、別のプログラム)が決めます。実行ファイルの隣のデータは、実行ファイルの場所を基準に絶対パスを作ります。開けなかったときに空のリストを黙って返さず、知らせます。

### Lab 59 — バッファーにだけあってファイルにはまだない内容を読み直す
```
間違った結果:   日誌ウィンドウ0行(期待3)
止めた位置:     readJournal を呼ぶ行で止めて journal.txt を確認 → 0バイト
本当の原因:     ofstream が開いている間に書いた内容はストリームのバッファーにあり、flush/close するまでディスクにはない
```
**修正:** `record` で書いた後に `out_.flush();`(または読む前に flush/close)
**教訓:** 同じプログラムの中で書いて読み直すなら、読む前に書いた内容がディスクにあることを保証します。第7部ラボ51(`std::endl` が毎回flushして遅い)と対になります: flushは必要な瞬間にだけ。

### Lab 60 — `while (!in.eof())` で最後の記録が2回
```
間違った結果:   4行、最後に「ドユン 7100」がもう一度、合計32100(期待25000)
止めた位置:     push_back、条件 scores.size() == 3
期待値 → 実際:  4周目はないはず / 実際は in.fail() == true なのに前の値で push_back
本当の原因:     eof() は末尾を越えて読もうとして失敗した「後で」立つ。最後の改行が残っていて1周多く回る
```
**修正:** `while (in >> name >> points) scores.push_back({ name, points });`
**教訓:** 読み込みは「読む → 成功を確認 → 使う」の順番です。失敗した `>>` は変数をそのままにするので、前の値がもう一度入ります。

### Lab 61 — `>>` の後の `getline` が残った改行を読む
```
間違った結果:   最初のセリフ ""(空行)、3番目の位置に2番目のセリフ、最後のセリフなし
止めた位置:     push_back、1周目で line.size() == 0
本当の原因:     in >> count は「3」までしか読まず改行を残す。getline はその改行までを空行として読む
```
**修正:** `in >> count;` の後に `in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');`(`<limits>`)
**教訓:** `>>`(トークン単位)と `getline`(行単位)を混ぜるなら、境目の改行を自分で処理します。`in >> std::ws` も通ったように見えますが、次の行の先頭の空白まで食べて字下げしたセリフを壊します(隠しテスト)。

### Lab 62 — failbit が残って以降の読み込みがすべて無視される
```
間違った結果:   モンスター3種、報酬0個(期待3)、102番の報酬0
止めた位置:     in >> header 行、ウォッチ in.fail() == true
本当の原因:     最初の while が「보상」を数値として読もうとして失敗 → failbit。消さなかったので header とゴールドの読み込みが全部素通り
```
**修正:** `std::string header;` の前に `in.clear();`
**教訓:** 失敗フラグは自然には消えません。失敗を「想定した」地点(セクションの終わり)では `clear()` で消してから読み続けます。

### Lab 63 — UTF-8のBOMが最初のキーにくっつく
```
間違った結果:   音量80(既定値、期待30)。全画面(2行目)は正常
止めた位置:     getInt、条件 key == "volume" → settings の最初のキーは "volume" に見えるが size() == 9
本当の原因:     ファイル先頭のBOM(EF BB BF)3バイトが1行目のキーの前に付いて "\xEF\xBB\xBFvolume" になる
```
**修正:** 1行目が `"\xEF\xBB\xBF"` で始まるときだけ3バイトを消す。
**教訓:** 「1行目だけがおかしい」なら、ファイル先頭の見えないバイトを疑います。デバッガーが見せる文字より `size()` とバイト値を信じます。無条件に3バイト捨てるその場しのぎは、BOMのないファイルの最初のキーを壊します(隠しテスト)。

### Lab 64 — 保存中の失敗で半分だけ書かれたセーブ
```
間違った結果:   保存失敗の後に読み込んだアイテム3種(期待5種)
止めた位置:     writeItem の throw 行、止めたまま save.txt を開く → すでに消えて前の数行だけ
本当の原因:     trunc で開いた瞬間に古いセーブが消え、例外で抜けるときに ofstream のデストラクターが前半だけのファイルを閉じる
```
**修正:** 一時ファイルに最後まで書いて閉じた後でだけ置き換える(コードは韓国語版と同じ)。
**教訓:** 保存は「全部か無か」でなければなりません。新しい内容は一時ファイルに、成功した後でだけ `rename`。一時ファイルは同じフォルダー(同じドライブ)に置きます。rename の前にストリームを閉じます。
